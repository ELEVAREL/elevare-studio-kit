# Elevare Studio — House Standards

Every studio agent reads this file first and holds to it. These are the defaults that make our work consistent and high-value across every client and personal project on this drive.

## The process & the skills
- **How we operate:** the studio runs the flow in [PLAYBOOK.md](PLAYBOOK.md) — intake → triage → plan → execute → gate → ship → measure → **learn**, with a concrete playbook per job type. The learn step is the one that gets skipped; it is not optional. Conductors (delivery-lead, marketing-strategist) drive it; every agent uses its handoff-report format.
- **The skills** are installed at `%USERPROFILE%\.claude\skills\<name>\SKILL.md`. They are AUTHORED at `%USERPROFILE%\.claude\skills\`, but **`C:` is the copy Claude Code loads, and a skill that exists only on `D:` is not installed — it is invisible to every session, with no error.** (That is not hypothetical: 15 skills sat unloadable for weeks, five of them cited by name in this file.) **The directory is the count, never a number written in a doc** — every hardcoded total in this studio has been wrong within a fortnight. **Read the SKILL.md file directly** for any skill — that always works, with or without the `Skill` tool. [SKILLS-MAP.md](SKILLS-MAP.md) routes every skill to the agent that owns it (incl. language stacks and industry verticals), so the whole library is usable. For anything with multiple actor roles, hardware, money movement, or offline operation, [SYSTEMS.md](SYSTEMS.md) is the design bar that comes BEFORE these implementation standards. Provenance: `D:\Skills\skills`.

## Product defaults (how we build unless told otherwise)
- **Static-first.** Plain HTML/CSS/JS, no build step, no framework, deploy to Vercel as-is. This is the default for marketing sites, shops, portals, landing pages. The canonical structure: `data.js` (content), `app.js` (shared header/footer injection + interactions), `styles.css` (tokenized design system), one HTML file per page.
- **App-scale only when justified.** Reach for Next.js + Supabase + Stripe only when there's real auth, a database, payments, or server logic. Say why before adding tooling.
- **★ Every capability added to the ENGINE ships a surface in the DASHBOARD, in the same change.** An owner-standing rule, stated explicitly during the server-watchdog run and now a default: a check type, an action, a policy, a learned behaviour, a new alert class that exists only in the CLI/config/daemon is invisible to the person who bought the product — and the person who bought it is not going to read a YAML file to find out what it can do. Ship the reader (a page, a card, a badge, a row) with the writer; if a capability genuinely cannot be surfaced this wave, say so in the handoff and name what blocks it. This is the constructive twin of claim–reality parity below — that rule stops the UI claiming what the engine cannot do; this one stops the engine doing what the UI never admits. See [[engine-capability-needs-dashboard-surface]].
- **Payments are in-app and theme-matched by default — but decide WHOSE MONEY IT IS first.** Any project that charges money takes payment **on our page** (no off-site redirect) and the payment UI **looks like the site**, not a stock processor.
  - **A CLIENT's project** uses the **client's own Stripe account**; Elevare joins as a Stripe **Developer** (keys and webhooks, no money movement). Default surface = **Stripe Payment Element themed via the Appearance API**.
  - **An ELEVARE-OWNED surface** (elevarestudio.co, Lanwright, SentinelBox, Asky, a founder brand) uses **Square** — Web Payments SDK themed from the site's own `:root` tokens, Square Subscriptions for recurring, Square webhooks, and the `mcp__claude_ai_Square__*` MCP tools for real account operations. **Elevare has no Stripe platform capability: permanently revoked 2026-08-21, appeal denied, final. Do not reapply, do not open a second account.**
  - **Elevare's own fee is never taken at checkout.** It is INVOICED monthly in arrears — 10% on deposits/bookings, 5% on everything else. A checkout that skims a platform fee is a blocker, not a feature.

  Whichever rail: the payment UI is built from the site's own design tokens (a `buildStripeAppearance()` that reads `:root` custom properties — never hardcoded hexes). Use Embedded Checkout only when Stripe-run shipping/tax/methods matter more than exact brand match; use hosted redirect only when the user explicitly asks. The money spine is non-negotiable regardless of surface: amount rebuilt from the DB, webhook is fulfillment, success marker + confirming poller. Start from the library: [`ecommerce-supabase-stripe/themed-inapp-payments.md`](library/ecommerce-supabase-stripe/themed-inapp-payments.md).
- **For an existing client, the LIVE SITE SOURCE is the only brand truth — not memory, not an old repo template.** Before designing anything (marketing assets, a new surface, an email), pull the real tokens from the site's own source — `src/index.css` / `tailwind.config` / `:root` custom properties — and name the file you pulled from. Do NOT trust: a memory note (may be stale/approximate), an *older* social-media/template folder in the same repo (often an abandoned off-brand system), or your own guess. Fanta shipped two wrong brand guesses (dark + Playfair, from stale repo templates) before the canonical editorial system (cream paper, emerald `#1D8C5A`, gold `#E5A825`, Cormorant Garamond + Montserrat) was read straight out of `src/index.css`. Old templates in a repo are suspects, not sources.
- **★ THE SENDING IDENTITY IS PER-PROJECT AND PER-PURPOSE — NEVER CARRY A CHANNEL FORWARD FROM THE PREVIOUS REQUEST.** On 2026-09-08 a **Whyza** readiness report was emailed to the owner from **`<alerts-inbox>`** — a *client's* booking-alert identity, borrowed for an unrelated internal message. Owner: *"First of why did you use Fanta email alerts to send me the email when it's always been using resend don't forget you flows and proccesed."* The agent's own diagnosis is the rule: *"I carried Inkbox forward from your 'text my phone' request without re-checking the channel for email."* **A channel chosen for one request does not transfer to the next one** — medium, project and purpose each re-decide it. Before any send, read the project's own established path from source (`supabase/functions/_shared/*` — e.g. `email-shell.ts:29` holds Whyza's `FROM = "Whyza <hello@send.whyza.app>"`) and name the file. A client's alert identity is reserved for that client's alerts: borrowing it puts studio traffic in a client's sending reputation and their logs.
- **Check the client's own repo/assets for prior work before regenerating from scratch.** An existing client repo may already hold a prior marketing report, brand doc, template set, or asset library (Fanta's April organic strategy report + HTML templates were already in the client's `Skills` repo). Grep/list the repo for `marketing*`, `brand*`, `*report*`, `*template*`, existing asset dirs FIRST — reuse or extend beats re-deriving, and it prevents shipping something that contradicts work the client already has.
  - **★ THE CLIENT'S OWN PUBLISHED OUTPUT IS THE STYLE REFERENCE FOR ANY NEW PIECE IN THE SAME MEDIUM — this rule is not limited to repo files, and the medium it keeps getting skipped in is VIDEO.** The rule above was already written, citing Fanta, and on 2026-09-08 a Fanta reel shipped as a generic crossfade slideshow. Owner: *"man wth that reel is not our styke for fanta refernce the other ones."* The agent's own post-mortem names the skipped step exactly — *"I built a generic crossfade slideshow and never looked at what her reels actually look like."* Before producing a reel, ad, carousel, post or email for an existing client, **open the pieces they have already published in that format** (their feed, their prior exports, the asset dir) and name the specific ones you matched — cut rhythm, text treatment, transition vocabulary, pacing, music feel. A brand token file tells you the colors; it does not tell you how their video moves. Binds `video-producer`, `motion-ad-director`, `graphic-asset-designer`, `social-media-manager`, `ai-media-producer`.
- **Match the canonical token source — don't re-derive it.** When a reference/landing design already exists (e.g. `site/index.html`), extract its exact tokens FIRST — ground hex, accent hue, display font *and its weight*, easings — and build the new surface against those values. Re-deriving an approximation drifts the brand (a SentinelBox app shipped ground `#0B1020` vs the site's `#10172A`, slate eyebrows vs the site's amber, display 600 vs the site's 800). If a canonical design exists, name the token file you pulled from before building. Adjacent to [[redesign-integration-playbook]]. **Reused code carries the palette of the project it came from, and the artifacts that get away with it are the ones no design agent ever looks at** — a transactional email, a PDF, an OG image, an error page, a receipt. Whyza's auth email shipped the project's *abandoned* violet brand (`#5B1FE0`) white-on-accent, lifted from a studio template and never re-derived; it passed a build, a review and a screenshot because nobody classes an Edge function as a design surface. Two rules, both cheap: **the moment you paste a template from another project, re-point every color/font/radius at THIS project's token file before anything else**, and **any rendered human-facing artifact goes on the design-auditor list no matter which agent built it.**
  - **★ AND THE JUSTIFICATION THAT SHIPPED WITH THAT FIX WAS FABRICATED — this bullet said "at 3.04:1, below AA" until 2026-09-10, and it is false twice.** White on `#5B1FE0` is **7.73:1**; it passed AA comfortably. The defect was pure brand drift — the right fix, recorded with a measurement nobody took, in the studio's own quality bar, cited as evidence for a rule. **A correct fix justified by an invented number is not a small error: the fix gets kept and the number gets copied**, and this one was copied out of a Whyza commit message into `WAVES.md` and into this file. The general rule: **when you write a ratio, a percentage, a count or a duration into a commit message, a report or a standards bullet, you either ran the computation in that session or you write the figure as unmeasured.** A number is the one part of a claim a reader cannot sanity-check by reading, which is exactly why it travels furthest. Pairs with §"Verify before you claim done".
- **No secrets in ANY tracked file.** API keys/tokens/RPC secrets live in env vars / serverless functions, never in shipped JS — and never hardcoded in a git-tracked helper/vault/deploy script (`.ps1`, `.sh`, `.mjs`, seed files) either. A secret baked into a tracked `.ps1` is committed history and must be rotated. Helper scripts **prompt for** the secret or read it from a gitignored `.env`; never inline it.
- **★ A FALLBACK TO SEED / DEMO / CACHED DATA MUST BE VISIBLE IN THE RESPONSE — a `console.error` is invisible to every check you own, and it converts a loud outage into silent fabrication.** Thames Coast's `src/lib/data.ts` does `console.error("[data] loadUpcoming DB error, falling back to seed:", ...)` and returns seed rows with a **200**. When its database was deleted on 2026-09-05, the site showed **fabricated events to 83 real visitors for nearly four days** and every external check said healthy. The server log was correct and nobody reads server logs. Any degraded path must be observable from outside the process: a response header (`x-data-source: seed`), a `/api/health` that returns non-200 when the primary store is unreachable, and a visible notice on any surface presenting the substituted data as real. **A demo fallback is acceptable ONLY where fabricated content cannot be mistaken for live content** — never for events, prices, inventory, availability or anything a visitor may act on. Verified in source 2026-09-10.
- **★ AUTH THAT MINTS A SESSION BY CLICKING AN EMAILED LINK IS BROKEN IN AN INSTALLED PWA — default to a typed CODE.** The link opens the system browser, not the installed app, so the session lands in a different cookie jar and the user is bounced back to a signed-out shell. Owner, 2026-09-08, mid-build: *"the pwa has you go to the link and then it takes you to the browser and not th epwa again can we just do codes instead of magic links?"* This binds **every** link-minted flow, not just magic-link sign-in — **password reset, email confirmation and device verification all have the same defect**, which is how it survived the 2026-09-06 "no magic links" instruction: sign-in was removed, reset kept the link. On Supabase use `verifyOtp` with a 6-digit token so the session is minted inside the app. If any installed/standalone surface exists, a link-minted session is a defect, not a preference.
- **Don't lose the user's work.** Any surface with a long editing session (page builder, form, editor) needs **autosave** (debounced to storage) plus an unsaved-work guard (`beforeunload` / re-lock recovery) so an idle-lock, reload, or accidental close can't wipe 20 minutes. Destructive editor actions get **undo/redo**, not just a confirm. **Scope recovery state to the client:** a crash-recovery draft (`_wip`) is single-user state — persist it to localStorage/IndexedDB, never the shared/synced store, where it doubles payload and ships one user's half-typed draft to every client.
- **A dev/mock/bypass switch must be SESSION-scoped and visibly badged — a sticky one fools your own team.** HausAI's `?mock=1` wrote `hausai:mock` to **localStorage** and never expired, so it silently served fixtures on `/builder`, `/designs` and the print sheet through an entire QA run — the most plausible reason two agents believed unverified work was verified. Any fixture / mock / preview / feature-bypass flag: `sessionStorage` or a URL param only (never `localStorage`), a persistent on-screen badge whenever it is on, and hard-off by `NODE_ENV` in production.
- **★ A TEST WRITE INTO A LIVE SYSTEM NAMES A RECORD THAT CANNOT EXIST.** A row in a production table is read by everything else that reads that table: stock holds, double-sell guards, owner alerts, counts, feeds, invoices. On 2026-10-10 a QA order on Lit on Fire Coins named a REAL listing id and blocked that coin's checkout for real buyers for ~8 minutes. Any script or test that inserts into a real database uses a sentinel id that passes validation but is absent from the real catalogue, asserts that before writing, and has a test that fails if a QA script carries a real id (reference: Lit on Fire `scripts/qa/qa-listing.mjs` + `tests/qa-listing-guard.test.ts`). Test orders also route their alerts to Elevare, never the client.
- **Poll/refresh must not clobber live edits (lost-update class, not a one-off).** Any background refresh loop that wholesale-reassigns shared in-memory state (`DB = fetched`) can silently defeat a queued/debounced save — the pending edit lives in the object the poll just threw away. Serialize the refresh with the write path (skip/defer the poll while a save is pending or an editor is dirty) and merge per-unit with a dirty guard; never wholesale-replace state the user is editing live in.

## Quality bar (non-negotiable)
- **Design:** tokenized colors/spacing/type (CSS custom properties), consistent components, calm and refined — **never** AI-slop. The auto-reject list and the universal test ("swap the logo — could this page belong to any competitor in the same industry?") live in ONE place, [CRAFT.md](CRAFT.md) §Anti-slop, including the per-industry slop signatures; do not keep a second copy here. Match the client's brand; when none exists, default to restrained and editorial.
- **Accessibility:** semantic HTML, one `<h1>`, labelled controls, visible `:focus-visible` ring, skip link, `aria-hidden` on decorative SVG, WCAG **AA** text contrast. **Compute the ratio numerically (never eyeball) for every color TOKEN used as text, the moment you add or reuse it — not at the gate.** **★ AND COMPUTE IT AGAINST THE COMPOSITED PIXELS THE EYE ACTUALLY RECEIVES, NOT THE TOKEN PAIR — every layer between the colour and the viewer is part of the ratio or the ratio is fiction.** A token-pair calculation is correct only when nothing sits between them; opacity, a gradient, a translucent card, a blur, a photo, an animated overlay each move the delivered number, always downward, and always silently. Whyza's Theme Studio printed three at once: with the `aurora` overlay on, `acid-lime` **printed 4.67:1 and delivered 2.79:1**; `card.opacity` (60–100) had been applied by the stylesheet since an earlier migration while every text colour was still resolved against the **opaque** surface, so *every translucent-card ratio the product had ever printed was optimistic* — and the shipped preset uses opacity 80, so it was live, not hypothetical; and a proposed photo background **printed 14.79:1 and delivered 1.20:1**, which is why that feature was correctly refused rather than built. The rule: **resolve the ratio in the render path against the final composite, not at save time against the source tokens** — and if a treatment's effective contrast cannot be computed honestly (a gradient fill, an outlined or shadowed headline, text over an arbitrary user image), **the treatment does not ship**. "We could not compute it" is a valid reason to refuse a feature; printing a number you cannot stand behind is not. A `--dim`/`--muted` token defined once and reused everywhere means one failing value (e.g. 2.3–4.4:1) silently fails AA across the whole app, and a newly-added `--slate-dim` fails *everywhere it is used at once*: catching it up front is one edit, catching it at QA is a sweep. **The target is WCAG 2.2 Level AA — the legal compliance target for effectively every global accessibility regulation in 2026** (ADA, EAA, EN 301 549). Three 2.2 criteria are new enough that they're routinely missed and are hard blockers on any checkout, booking, or multi-step form: **2.4.11 Focus Not Obscured** — a focused control must never be fully hidden behind a sticky header, cookie bar, or chat widget (tab through the whole flow *with* the sticky chrome present, not with it dismissed); **2.5.8 Target Size (Minimum)** — interactive targets ≥ **24×24 CSS px** (size selectors, qty steppers, calendar day cells, icon-only buttons, and close "×"s are the usual offenders); **3.3.7 Redundant Entry** — never make a user re-type information already given in the same session (shipping → billing must offer copy/autofill, not a blank second form).
- **SEO:** per-page `<title>`/description/canonical, OpenGraph + Twitter card, `robots.txt`, `sitemap.xml`, JSON-LD structured data (Organization/LocalBusiness, BreadcrumbList, Product/Article as relevant), `site.webmanifest`.
- **Security:** the audit baseline is the **OWASP Top 10:2025** (owned + walked by security-reviewer), plus a mandatory **non-destructive protocol** on any LIVE site — backup (tag + D: bundle) → branch → SAFE-AUTOFIX-only vs BEHAVIORAL-RISK (needs sign-off) → verify build → never deploy/merge to `main` without explicit human sign-off. Concretely: escape any dynamic value before it touches `innerHTML` **or an HTML attribute** — a stray `"` in a `data-` attribute silently breaks the markup and the handlers that read it (and is an injection vector); escape `& < > " '`. Set security headers (CSP, HSTS, nosniff, frame-options) in `vercel.json`; no reflected query params written to the DOM. **Rich HTML from `contenteditable`/editors is a stored-XSS boundary** — never trust editor HTML: run it through an **allowlist sanitizer** (permit only known tags, drop every attribute except a scheme-checked `href` — reject `javascript:`, strip `<script>`/`<style>`/event handlers) and sanitize on **both save and render**, not just one side.
- **Performance — the budget is numeric, and it is a gate.** Core Web Vitals at the **75th percentile of real users**: **LCP ≤ 2.5s · INP ≤ 200ms · CLS ≤ 0.1**. (INP fully replaced FID in March 2024 — any guidance still citing FID is stale.) Measure, don't assert: run Lighthouse on the deployed URL and state the three numbers in the ship report. **Archetype-specific floors** (see [ARCHETYPES.md](ARCHETYPES.md)): a *local trust/service* site must be interactive in **under 2 seconds on a mid-range phone over 4G** — this customer is standing in a parking lot and the competitor is one back-button away, so hero video that delays LCP is a defect, not a flourish; an *immersive/WebGL* build must hold the same LCP/INP on a **mid-range Android**, not on the builder's laptop, or it isn't award-tier, it's unfinished. Reserve space for every image, embed, and ad slot — CLS is almost always injected chrome, not the design. Then the mechanics: preconnect + `display=swap` fonts, inline/lightweight SVG over images, no heavy dependencies, cache static assets. **Hot-route hygiene:** dynamic-import rarely-used heavy modals/SDKs (e.g. a Stripe buy-modal) instead of static-importing them into a hot route; ship only the font **weights and subsets the UI actually uses** (audit before shipping — 5 weights × 3 subsets when the UI uses latin + 4 weights is dead payload).
- **Every shipped SVG must PARSE AS XML, not merely render when inlined.** Browsers parse inlined SVG with the lenient HTML parser, so a file that looks perfect on the page can be invalid XML and break the moment it's used as `<img src>`, opened in Illustrator/Inkscape, sent to a vinyl cutter, or read by any non-browser tool. Two independent identity trials shipped exactly this, each via a different route: a raw `&` inside an `aria-label`, and an XML comment containing a double hyphen (`--`, illegal in XML comments) added as a decorative rule. Both were invisible in-browser. **Run every SVG through a real XML parser before delivery** and escape `&` `<` `>` in every attribute value. Related delivery rule for logo work: lockups carrying live `<text>` must be **outlined to paths before any print, vinyl, embroidery, or `<img>` use** — external fonts don't load inside a referenced SVG, so a vendor gets Arial.
- **Serialization correctness:** when persisting a `Set`/`Map` to JSON, use `Array.from(set)` / `[...set]` — `[].slice.call(set)` and `Array.prototype.slice` return `[]` for a Set (no indexed props), silently shipping a dead feature (a notifications ack-set saved as `[]`, so acks never persisted). Any collection→JSON path must round-trip a real value, not an empty array.
- **Destructive prune/cap correctness:** any cleanup that **deletes** to enforce a cap ("keep N backups", "trim history", retention-by-age/disk%) must delete the RIGHT items — sort by the real axis (oldest-by-time, per-type), never by a proxy like lexicographic filename order, which can silently delete the most-irreplaceable data (a backup pruner's string sort dropped the oldest/only full backups; a retention pruner with an off-by-one bound deleted *all* footage). **This is a hard merge gate: any delete/prune/retention path REQUIRES a named-survivor test before merge** — a test that seeds a known set, runs the pruner, and asserts by name *which items remain and which are gone* (never just a count). A "keep N" that ships without this test is a blocker, not a nit.
- **Tailwind v4 cascade (unlayered beats @layer):** never write an unlayered global rule that sets `position`/`z-index` on a broad selector (`body > *`, `*`, `main *`). Tailwind v4 puts its utilities in `@layer`, and **any unlayered CSS wins over layered CSS regardless of specificity** — so a stray `body > * { position: relative; z-index: 1 }` (added to keep a decorative `::before` behind content) silently overrides `.fixed`/`.sticky`/`.z-*` utilities everywhere, collapsing a fixed drawer/sticky header into page flow. Fix the decorative case at the source: put the overlay at `z-index:-1` on a `::before`/`::after` (no stacking forced on siblings); keep any real helper inside `@layer` or scope it to one element. Grep the global stylesheet for unlayered `position`/`z-index` on multi-element selectors before shipping.
- **Never pass user-controlled input into a command interpreter that has an exec/command mode without a strict allowlist.** Many "config" or "URL" sinks are secretly command runners: go2rtc treats an `rtsp_url` beginning `exec:`/`ffmpeg:` as *run this shell command*, so a camera URL taken verbatim from an API is remote code execution. Same class: `ffmpeg` protocol prefixes, YAML/`!!python` tags, template engines, `child_process`, spreadsheet formulas. Validate against an allowlist of expected shapes (e.g. `rtsp://`/`http(s)://` only, reject any other scheme/prefix) at the boundary — a denylist misses the next prefix.
- **Loopback/localhost APIs still need CSRF protection and auth — "it only listens on 127.0.0.1" is not a security boundary.** Any website the user visits can `POST` to `http://127.0.0.1:<port>`; the browser sends the request and the local server executes it (CORS blocks the attacker *reading the response*, not the request *running*). A local, unauthenticated, CORS-open engine API is one malicious tab away from driving it. Require a token/origin check on state-changing local endpoints, or bind to a random port + per-launch secret the UI knows and a web page can't guess.
- **Scraped third-party HTML is untrusted input — fetch it to `D:\.scrape-cache`, scan it, and never open it in the daily browser.** A prospecting/research run pulls pages from local-business directories and aggregators (`loc8nearme.com`, `*.wsite.top`, Bing/DDG SERPs), and those are the single most common carrier of obfuscated redirect JS — on 2026-08-14 Defender quarantined `Trojan:HTML/Redirector.JBA!MTB` out of a page one such run wrote into `%TEMP%`. Nothing executed (inert HTML can't run until a browser opens it) but that run had left **164 untrusted HTML files loose in `%TEMP%` with two-letter scratch names, no scan step and no expiry** — one careless "let me look at what we scraped" away from executing in a profile holding live Stripe/Supabase/Vercel/Meta logins. Use `D:\.claude\agents\tools\scrape-guard.ps1` (`-Fetch` / `-ScanDir` / `-Purge -IncludeTemp` / `-Audit`); parse scraped HTML, don't render it, and if it must render use headless Chrome in a throwaway profile. **A Defender hit on a scraped page means the SOURCE SITE is compromised — blocklist the domain and drop the prospect; it does not mean the machine is infected.** The guard **fails closed**: exit 0 = scanned+clean, 2 = malicious, 3 = UNVERIFIED (scan never ran) — and 3 is not a pass. Its first version returned "clean" when the scan couldn't run at all; the positive-control run is what caught it ([[negative-controls-catch-always-true]], [[untrusted-html-fetch-hygiene]]). The packaged procedure is the `untrusted-fetch-quarantine` skill — read it before any prospecting or competitor fetch, and for the triage when the scan cannot run.
- **Constraint drift:** a modern CSS/JS feature can quietly move a stated support floor — e.g. `color-mix()` raised a project's min-browser target from Chrome 102 to 111. Whoever introduces such a feature must name the new floor and confirm it's still within the target, not let the constraint drift silently. **Match new JS/regex features to the repo's `tsconfig` target too:** a `/s` (dotAll) regex flag needs ES2018, so it breaks the build on an ES2017 target (caught by tsc, but don't rely on luck — check `compilerOptions.target` before using a newer language/regex feature).
- **★ COPY: NO EM DASH, IN ANY SPELLING, ANYWHERE A HUMAN READS IT.** Not the character, not the en dash, not any HTML entity spelling of either (the named `mdash`/`ndash` entities, the decimal 8212/8211 entities, the hex 2014/2013 entities), and not `--` used as one. This bullet deliberately does not spell those entities out: a rule that contains its own needle flags itself, and the usual fix is a self-exemption, which is the hole the ban exists to close. The exact literals live in the gate below. Use a colon, a semicolon, a comma or a full stop. **This rule had no home in STANDARDS or CRAFT until 2026-09-13**, so it only ever reached the six copy/social/brand specialists that happened to carry their own copy of it, and every build, data or generator lane shipped without ever seeing it. The $49-report wave was told in a binding direction doc that the ban was "studio-wide and carried independently by CRAFT.md and STANDARDS.md"; a grep of both files returned **zero** mentions (control: the same grep found "AI tell" in five other files, so it reaches). A same-day sweep of the live client fleet, with a fired positive control and a silent negative control, found a literal em dash served by **2 of the 4 reachable sites**: ProCraft VA inside its JSON-LD `description`, and Coffee Baby **four times inside `og:image:alt` and `twitter:image:alt`**, which is the text Facebook, X and LinkedIn render when the site is shared. **Do not re-forge a detector: one is installed** at `D:\.claude\agents\library\verification\_gates\emdash-check.mjs` (two tiers, prints its own controls and every exclusion, and refuses to report at all if its control does not fire). **`grep -P` errors on this machine and its error reads as a clean pass**, so never use it for this. Check the **served bytes**, not the source: an entity spelling is invisible to a source scan, and the entity form is how this was broken on a live client email. **AND THE BASH TRAP THAT MANUFACTURED A CLEAN RUN, MEASURED 2026-09-18: `$'—'` DOES NOT PRODUCE AN EM DASH ON THIS MACHINE.** A dash check built on it fires its positive control on a needle that is not an em dash, then reports zero occurrences, and the zero is false. On one night this fooled three separate agents and one eval check: two copy deliverables shipped with a written in-file guarantee that no em dash appeared while their own H1 carried six and one respectively, and both return messages reported a dash gate run with a fired positive control. Use the installed detector (`library/verification/_gates/emdash-check.mjs`) or a real codepoint check in Node or Python; never hand-forge the needle in bash. Scope, ruled 2026-09-18: this ban is on SERVED BYTES and user-facing copy, not on internal studio docs - STANDARDS, PLAYBOOK and the library index all use them freely and reflowing them is not a gate's job.
- **Fonts / type tokens:** the `font-weight` in CSS must match a weight actually loaded in `@font-face`/`next/font` — asking for `800` when only `400–700` are loaded gives synthesized faux-bold. Keep the loaded-weight list and the CSS weights in sync. **For desktop/offline surfaces (installers, packaged apps, kiosks) self-host the fonts from the start** — CDN-loaded fonts cause FOUC and break entirely offline, which is unacceptable for a shipped installer; bundle only the weights + subsets the UI uses. And **every scale/token you define must be referenced** — defined type-scale/spacing tokens with sizes still hard-coded inline are dead tokens; apply the scale or delete it.

## Sensitive data — we do not collect it (owner rule, 2026-08-30)

**Owner directive: "let's not include health forms or store health data."** This is
a BUILD rule, not just a contract clause — the contract describes what we do; this
decides what gets built. It applies to **every client in every vertical**, because
Connecticut's CTDPA (as amended 1 July 2026) fires on a **data category**, not an
industry, and **with no volume threshold**. One field on one form for one customer
pulls the statute onto Elevare.

**Never build a field that asks for:**
- health or medical information of any kind — allergies, conditions, injuries,
  medications, pregnancy, treatment, disability
- biometric or genetic data; neural data
- precise geolocation
- race or ethnicity, religion, sexual orientation, transgender or nonbinary status,
  immigration status
- government identifiers — driver's licence, passport, SSN
- financial-account details. **Card data goes to the processor, never to our
  database** — store the Stripe/Square reference, never the instrument. This is
  already how every client checkout is built; keep it that way.
- a date of birth that identifies a child

**The real leak is free text, not fields.** You can ban the question; you cannot ban
the sentence. A customer will type *"table by the door, I'm diabetic"* into a notes
box. So:
- Label free-text boxes **narrowly** — "Delivery instructions", not "Anything else
  we should know?" A broad label invites the disclosure.
- Put a one-line note under any customer-facing free-text field asking them not to
  enter health or identity information.
- Free-text boxes that exist today and need this treatment: West Side Tavern
  `orders.notes` / `reservations.notes` / `tickets.notes`, Styled by Myiah
  `bookings.notes`, Petal & Threads `orders.customer_note`.

**If a client asks for one of these fields** — and the unlimited-changes promise makes
*"can you add a quick allergies box?"* the likeliest way this ever happens — it is
**not** a routine change. It stops, goes to the owner, and is recorded in the client's
Schedule A before it ships. See `legal/DATA-PROTECTION-ADDENDUM-template.md` Schedule A
for the nine-question intake check that runs on every client before launch and again
whenever a form changes.

**Verified clean as of 2026-08-30:** American Karate Center, Fanta, Styled by Myiah,
West Side Tavern and Petal & Threads hold no sensitive-category columns.

## Claim–reality parity (honesty gate on every ship)
The UI/marketing must not claim a capability that is off, unreachable, or unbuilt. An NVR shipped "All clear" while its AI was dead, a trial that couldn't be downloaded, and "staff logins coming soon" *after* they shipped. Rule: **every user-visible claim, status, badge, feature bullet, and "coming soon" must be reconciled against the actual runtime state before ship** — if a feature is gated OFF, say so or hide it; if it's live, don't market it as "soon"; if a status is shown, it must be measured (see liveness, above). Owner: design-auditor + marketing gate; a mismatch is a blocker, not copy polish.
- **A claim that names a SURFACE must cite the file that implements it — this is the studio's single most common defect class and no automated gate can see it.** Six surfaces drifted in one Thames Coast run: `/community/[id]` told readers "replies live on the event page" while the event page had no link to the thread; one agent's copy said Save was "on every event card and every event page" after another agent had removed it from event pages; `/membership` sold "follow venues" for a control that rendered nowhere. **Every file compiled and every test passed.** The rule: any copy that enumerates *where* a capability appears is a claim about files you probably do not own — either verify it against those files and cite `file:line`, or write the sentence without the enumeration. At the gate this becomes the **claims ledger** (PLAYBOOK §4b): claim → implementing `file:line` → verified reachable; a row with no implementing file is a blocker. Corollary: **when a feature is descoped, the copy that sells it is part of the descope** — sweep every surface in the same change, never in a follow-up.
- **A COMMENT that asserts a control exists IS a claim — and it is worse than a false UI claim, because it actively suppresses the review that would have caught the gap.** HausAI shipped eight in one run: `"Pro-gated SERVER-SIDE"` on a route with no gate anywhere (a Free user could take the paid artifact), `"no inline HTML (checked)"` on a markdown renderer that had it, `"there are no inline scripts on static pages"` on a CSP that then killed every prerendered page, `"position: fixed repeats per page"` on a print footer that printed once, `"every layout below renders <main id='main'>"` where none did — and the conductor's own *"zero placeholders now render"*, which shipped **16 visible `[NEEDS…]` notes on `/legal/privacy` and 10 on `/legal/terms`**, one publicly announcing the §10 liability clause was unreviewed by counsel, on the page whose entire job is to be trustworthy. Every reviewer read the comment and moved on. **The rule: if you assert a control exists in a file you do not own, cite `file:line` or do not write the sentence.** If it is in your own file, the control must be visible in that file or one it directly calls. "Validated / gated / sanitised / repeats / checked elsewhere" with no reference is not documentation — it is an unverified claim, and it is load-bearing in exactly the way a false pricing bullet is. Applies to your own retro notes and decision docs too. The mechanical sweep is `claims-ledger-sweep` (advisory, never a build-blocker) — run it at the ship gate and after any wave where several agents wrote headers about each other's files.
  - **★ THE NEGATIVE FORM IS THE ONE THAT SURVIVES REVIEW — a comment or a line of copy asserting a control is ABSENT is a claim, and nothing anywhere gets built to make it true.** A positive claim ("gated server-side") at least has a thing to point at; "there is no crawler policy at all", "it arms nothing", "the automatic check added no strike", "we don't store that", "no email is sent" describe work nobody did, so there is no file to open and the sentence ships. Whyza produced three in one wave, all from the enforcing side: a permanent comment in `src/lib/seo.ts` saying `/held` shipped *"with no crawler policy at all"* when both routes shipped `robots:{index:false,follow:false}` (what was missing was the AI-crawler disallow — a different mechanism); a migration header reading *"It arms nothing"* over a grant to `authenticated`; and copy saying no strike was added where a trigger opens a strike window on **every** hide. **Cite the `file:line` that makes the absence true, or delete the assertion** — and note who writes these: the same person who is enforcing the rule against false claims, in the file where they are enforcing it.
  - **★ "OFF BY DEFAULT" / "BEHIND A FLAG" IS A PER-LAYER CLAIM, AND THE DATABASE IS A LAYER.** A feature gated `off | shadow | enforce` in app code is off only where the mode variable is read. Whyza's moderation classifier was correctly gated in the app while the same change granted a user-callable write-and-notify RPC to `authenticated` **with no notion of the mode at all**. Before anyone reports a feature dormant, enumerate every layer that can invoke the path and say where the mode is read in each: app code, function/RPC grants, RLS policies, triggers, cron and queue drains, edge functions, webhooks, admin surfaces. A layer that cannot see the flag is not gated by it. This is the creation-side mirror of PLAYBOOK §Playbook O, where deleting a route leaves its grants behind.
  - **★ AND WHEN THE FALSE CLAIM LIVES IN A TOOL, IT IS READ ALOUD TO THE OPERATOR AT THE MOMENT OF THE IRREVERSIBLE ACTION.** elevare-app's `scripts/verify/ota-safe.mjs` carried a `STANDING_DECISION` constant quoting taste-gate "section 12" and printed *"Wave 4 ships ... NOT as an over the air update"* as its concluding note on **every run, including the run that publishes the OTA**. Section 12a had already reversed section 12, and the script **disproves section 12's premise on every run**, because reading the signed Xcode logs is the thing the script does. A constant, banner, usage string, help text or failure message that quotes a ruling, policy, threshold or decision from another file is a claim about that file, and it is the worst-placed claim in the studio: a comment gets a reviewer with time, a tool's banner gets an operator mid-publish who is reading it as the current state of the world. **Whoever changes the ruling changes the string in the same commit**, and a tool that can measure its own quoted premise asserts it rather than printing it. Fixed at `e7efb7d`, which kept the superseded constant as a named example instead of quietly deleting it; copy that, because a silent rewrite destroys the only record of how the error was made.
- **★ A CONTROL A PERSON CAN SWITCH ON IS A CLAIM THAT SOMETHING HAPPENS — and a switch with no render site is the same defect as a false pricing bullet, told in a language no gate speaks.** Every option in a settings enum, block catalog, toggle list, effect vocabulary or feature menu must have a **consumer proven in the same change**: grep for the `case`/branch/render site that reads it and confirm the count is ≥1 before it appears in any list a person can see. This is §4b's *a write with no reader is a dead feature* applied to UI controls, and it is invisible to typecheck, tests, lint and the console — the switch flips, the state saves, the page renders, and nothing appears. Whyza's profile shipped **four of them at once** (`gallery`, `celebrate`, `now`, plus four theme blocks that rendered an owner-only "add something here" prompt and nothing else), next to a dead Follow button, a dead Connect button and a hardcoded `role="tab"` pair with no panel — an accessibility lie, not an unfinished feature. **`defaultOn: true` on a dead option is the aggravated form:** `now` was default-on, so the product handed the broken control to *every new account* without anyone choosing it. Two consequences: **a default is a claim made to every future user — audit the default set separately from the catalog**, and **an option whose consumer is not built yet is not "off", it is absent** — take it out of the list and out of the DB's allowed set until something renders it.
- **Success confirmations are SERVER-AUTHORED from the actual applied diff — never canned client strings.** A client that prints "Done. I restyled your site" regardless of what the server applied is the client-side variant of this class (the Site Builder chat shipped exactly that while an edit silently no-op'd). Any user-facing "done"/success message for a server-side action must be composed by the server from the real outcome — what applied, what was adjusted (e.g. a clamped color), what could not be honored — returned alongside a machine-readable `applied` diff; canned client copy is a fallback only, never the primary path. Run `outcome-integrity-sweep` before shipping anything that writes, sends, charges, notifies or archives — and before writing any success toast, `sent: true`, or `200`. A library that RESOLVES with `{ error }` instead of throwing means the try/catch caught nothing and the success path ran unconditionally.
- **A humanized freshness string ("answered 33s ago", "last seen", "as of", "updated just now") is a CLAIM ABOUT AN OBSERVATION — never render one from a stored field the CURRENT state contradicts.** A peer-health card rendered "answered this watchdog 33s ago" for a peer whose state was **UNKNOWN**, reading a `last_ok_at` left over from the last time it *had* answered. The timestamp was real, the sentence was false, and it was the most reassuring thing on the page. Whenever a state means *we do not know* — UNKNOWN, STALE, ERROR, unreachable, never-run, cache-only — the stored recency field is by definition not evidence about now: render the uncertainty ("no reply since 33s ago") or render nothing. Same rule as measured liveness, one layer up: the engine can be scrupulous about only asserting what it saw and the UI can still launder a stale field into a fresh-sounding claim.
- **Deferred/dormant billing must be disclosed plainly and repeatedly across EVERY surface that touches the offer.** When a product is free now but will charge later (site-factory "free at launch, pay the platform fee later", a founder rate-lock, a dormant checkout), the deferral + what locks + "we'll email you before any charge / no card required now" must appear on the offer/pricing page, the claim/signup form, AND the confirmation email — not buried in one place. Silence about the future charge reads as a bait-and-switch even when the mechanic is honest; stating it repeatedly is both the honesty gate and the core of the sell (Thames Coast "Founding 50: free now, lock the rate, billing flips on ~month 2"). Owner: conversion-copywriter + the marketing gate.
- **Seeded/imported data is a CLAIM, and a money/consent column is the worst place to guess.** A Good News USA prospects seed was a keystroke from setting `paid='yes'` on the 16 advertisers currently running in the paper — because the brief said they are *in the paper*. It never said anyone had paid. That would have been the app asserting a payment nobody confirmed, on a money column, to everyone who opens the admin (caught before applying, 2026-08-19). Whenever a seed maps a source fact ("running", "listed", "contacted", "responded") onto a **stronger** column ("paid", "agreed", "consented", "verified", "approved"), the source must actually say the stronger thing — otherwise seed the weaker truth and leave the strong column at its unknown default. An inferred `true` in a database reads exactly like a recorded one.
- **★ A DERIVED NUMBER WRITTEN INTO A COMMENT IS A CACHED COMPUTATION WITH NO INVALIDATION — write the inputs beside it or do not write it.** `--on-accent: /* paper on tangerine is 3.04:1 */` was true of a draft palette; the ground later changed to `#FAF6F0` and the comment kept its old answer, silently, in **seven** files across Whyza's `tokens.css`, `DIRECTION.md`, two components, a mail script, a standards bullet and an Edge function. Nothing was broken — the *rule* the number supported ("text on the accent is always ink") was right the whole time — which is exactly why it survived: a wrong number that agrees with a correct conclusion is never re-derived by anyone. Contrast ratios, DPI, bundle sizes, row counts, percentages, timings and "N% of X" are all this class. **The fix is one clause, not a process: state the operands.** `/* white #FFFFFF on #F25A0E = 3.36 — recomputed 2026-09-10 */` fails visibly the moment either hex moves, and any reader can re-run it in ten seconds; `/* 3.04 */` is unfalsifiable forever. Where the number can be computed at build or test time, assert it there instead of narrating it. Binds every agent that writes a token file, a design doc or a header comment — `ui-designer`, `design-engineer`, `frontend-builder`, `brand-identity-designer` most of all.
  - **★ AND WHEN YOU CORRECT A PROPAGATED FACT, THE SWEEP IS `grep <the wrong value>` OVER THE WHOLE REPO — INCLUDING THE FILE YOUR NEW COMMENT CITES AS THE AUTHORITY.** Whyza's 2026-09-09 correction fixed six copies of `3.04` and its own commit message predicted the seventh. The seventh was already written: the corrected `send-story-email.mjs` comment says *"email-shell.ts says so at its own definition"* — and `email-shell.ts` still said 3.04, uncorrected, for another day (fixed 2026-09-10 as `0d8deb2`). **Correcting the copies you happened to have open and then pointing at one you did not open re-seeds the error with a citation attached**, which is strictly worse than leaving it alone: the next reader follows the pointer and finds "confirmation". Mechanically: grep the literal old value across the whole tree (source, docs, scripts, migrations, edge functions, gate reports), fix every hit in the same change, and if your correction adds a "see X" pointer, open X before you write the pointer. **For a false sentence in prose, the wrong value is the CLAIM, not the string:** grep its key nouns across every field. Elevare iOS 1.0's description lost "Your conversations stay on your phone" and went to App Review with "Conversations stay on the phone" still in the review notes (2026-10-01). Same rule as the descope corollary above — the copies are part of the change, never a follow-up.
  - **★ AND A `file:line` IS A DERIVED NUMBER TOO, WHICH MAKES THE REMEDY THIS FILE PRESCRIBES THE ROT-PRONE FORM.** elevare-app wave 4 adjudicated **33** cross-file assertions written under the "cite `file:line` or do not write the sentence" rule above and found **18 defective**: six stale line numbers, four stale counts, two unfollowable, and one live contradiction where `src/lib/ai.ts` quoted an error message `src/lib/supabase.ts` had stopped throwing **in the same commit** (and that comment then became the only place in `src/` where the leaked env-var names still appeared, so the warning re-seeded the thing it warned about). One citation went stale **between two commits of its own wave**: a test cited `index.ts:406`, correct at `a1846fa`, moved to `:483` at `bb7d434` when the file grew from 423 to 499 lines. **So cite the ANCHOR, not the ordinal: quote the unique string, give the path, and let the line number be a hint after it.** A quoted sentence survives any edit elsewhere in the file; `supabase.ts:74` does not survive one inserted import. For counts, state the number that is actually load-bearing (call sites, not occurrences), and remember that a comment quoting its own needle inflates its own grep by one, so a claim true about the code ships false about the measurement it names.
- **Never fabricate a breakdown to reconcile a given total.** When a brief supplies a TOTAL (a price, a saving, a count) but not its line items, do NOT invent sub-figures that sum to it — a Launch Kit ad fabricated $420/$350/$260/$150 to hit an $1,180 total under a "real numbers only" brief. Show the labels/names without figures, or use only real per-item numbers you can source. A made-up breakdown reads as precise and authoritative, which makes it a *worse* honesty violation than a vague claim. Applies to every surface that shows numbers — ads, decks, graphics, dashboards, copy — not just marketing headlines.

## Supabase + Next.js (app-scale)

**The full invariants moved to [`library/supabase-nextjs-app-scale-invariants.md`](library/supabase-nextjs-app-scale-invariants.md)** (2026-09-06) — read it before any app-scale build. Four of its rules bind work that never touches Supabase, so they stay here:

- **Default-deny on tenant identity.** A policy that checks *authentication* rather than *tenancy* is open. Run `rls-tenant-isolation` before shipping any tenant-scoped table, view or RPC: the load-bearing test row is a member of tenant B, and the assertion is **row count and post-state**, never absence of an exception — a blocked UPDATE raises no error and affects zero rows, so "no exception" passes against a table with no RLS at all.
- **Capability tokens are random, single-purpose and revocable** — never a guessable id, never reused across concerns.
- **Migrations are atomic and forward-only**; one concern per migration, and every object is verified applied against the live system rather than assumed from an exit code.
  - **★ A MIGRATION THAT NARROWS WHAT THE DATABASE ACCEPTS INVERTS THE DEPLOY ORDER: the code that stops producing the old shape ships FIRST, and the SQL is applied second.** The instinct is migrate-then-deploy, and it is correct only for *widening* changes (a new nullable column, a new enum member, a looser bound) where the currently-deployed client keeps working. **Narrowing is the opposite** — a tightened `check`, a dropped enum member, a `not null`, a stricter validator function, a revoked grant — because for the whole window between the two steps the live client is emitting a payload the database now refuses, and it fails as a 500 on a write path the user was already using. Whyza's `0027` refuses a theme block the **currently-deployed** client writes into every new profile by default, so applying that SQL before shipping the code breaks every Theme Studio save (verified against production: the old client's default theme returns `blocks: "now" is not available yet`, the new one returns null). **So classify every migration as WIDENING or NARROWING in its header comment, and state the order in the handoff:** *"NARROWING — rejects `<shape>` that deployed client `<sha>` still emits. Deploy code, then apply."* Expand/contract when both must be safe: widen → deploy the new writer → backfill → narrow. And the ordering claim is Tier 1 or it is nothing — read the shape the *deployed* artifact emits, not the shape in your working tree.
- **Render/cache mode is a cross-agent contract.** Changing static vs dynamic, `force-dynamic`, ISR or `generateStaticParams` changes what other agents' code can assume — declare it in the handoff, and re-run `hydration-assertion` per route afterwards.

## Verify before you claim done

Every rule below is load-bearing and stays. The worked incidents behind them — the exact commands,
repos, dates and post-mortems — moved to
[`library/verification/false-green-casebook.md`](library/verification/false-green-casebook.md)
on 2026-09-06, because this section is injected into all 80 agents and the evidence is only needed
when you are diagnosing one of these. **Read the casebook when a check surprises you.**

- **★ A MISSING CREDENTIAL IS NOT A BLOCKER UNTIL YOU HAVE READ THE VAULT AND THE TOOL'S OWN CONFIG STORE. Reporting a key as absent, or asking the owner to go get one, without doing that is the single fastest way to waste his time.** Owner, 2026-09-06, after an agent reported `RESEND_API_KEY` empty in `.env.local` and `CRON_SECRET` absent from Vercel and stopped: *"why are you acting brand new you do it everyhting i need the keys to do all of this ar eint he vault."* **He was right — the vault held 233 keys, including `ELEVARE_STUDIO_CRON_SECRET`, the exact secret reported missing.** It was invisible because the vault stores per-project secrets **PROJECT-PREFIXED** and the agent searched the unprefixed name. Before declaring any credential unavailable:
  1. `powershell -ExecutionPolicy Bypass -File "$HOME\.keyvault\keyvault.ps1" list` — then grep that list for the **key name AND the project prefix** (`FANTA_`, `ELEVARE_STUDIO_`, `LANWRIGHT_`, `THAMESCOAST_`…). `get <NAME>` prints one value to stdout only.
  2. The tool's own store: `~/.config/stripe/config.toml`, `~/.vercel`, `gh auth token`, `~/.supabase`, `~/.aws/credentials`, `%APPDATA%` app dirs, and the project's own Vercel env (a value that reads back empty is a **read limit, not a missing write**).
  3. Only then is it a blocker — and say which of the three you checked.
  Full command set and the never-overwrite rule: memory `keyvault`. When one copy of a secret disagrees with another, or a job works on one host and not another, run the **`credential-drift`** skill before re-minting anything. Verified live 2026-09-10.
  - **★ THE INVERSE DIRECTION IS UNGUARDED AND IT ENDS IN A GREEN: ASSERTING A KEY NAME THAT DOES NOT EXIST.** Everything above is about reporting a key MISSING. On elevare-app wave 4 a conductor's relaunch brief named the vault credentials as `ELEVARE_SB_URL` and `ELEVARE_SB_SECRET_KEY`. **Those are the CONSUMER'S env var names, not vault keys.** The vault holds `ELEVARE_STUDIO_NEXT_PUBLIC_SUPABASE_URL` and `ELEVARE_STUDIO_SB_SECRET_KEY`, and the mapping was written in the consuming test file's own header three lines above the code that reads the variables. Had the brief been trusted, the suite would have run with two empty strings, **skipped** its live-read guard (correctly, and by design) and printed a green summary, so a wrong key name buys silence rather than an error. **An env var name and a secret's name are two namespaces, and the mapping lives at the consumer.** Before a credential name goes into a brief, a script or a runbook, grep it out of `keyvault list` and cite the consumer line that maps it. Measured 2026-09-14: `ELEVARE_SB_URL` does not exist in a vault of 243 keys.
- **★ AND THE SECOND HALF OF THE SAME WASTE IS A KEY YOU FOUND, CAN USE, AND HAND BACK ANYWAY - A RESTRICTION THAT EXISTS FOR ONE CHANNEL DOES NOT FOLLOW YOU INTO ANOTHER.** The rule above closes *reporting a key absent*. It does not close the case that actually happened on **2026-09-17**: the key was known to be in the vault, the agent could read it, and it still ended its report with *"Next action (~2 min): paste key `flavornews-auth-smtp-20260917` into Supabase -> flavornews -> Auth -> SMTP -> Password. That's still the one thing only you can do."* Owner: **"Why do I have to paste key if you have the supine management api key in the vault"**. He was right, and the agent's own diagnosis is the rule: *"I was applying the **Navy bridge's** 'no vault access' rule to you asking me directly. That rule exists because email is spoofable. You're not spoofable."* It then did the whole thing itself through the Management API in three minutes, with controls. **A constraint is scoped to the channel that earned it.** The Navy bridge cannot touch the vault because an inbound email can be forged; that reasoning does not transfer to the owner typing in this session, to a local script, or to a routine he registered. Before you convert any policy into a blocker, say **out loud which channel it was written for and whether you are on it** - and if you are not, it does not apply to you. This is the mirror of §"the sending identity is per-project and per-purpose": an **approval** does not carry forward from one channel to another, and neither does a **prohibition**.
- **★ BEFORE REPORTING ANY MONITOR, ALARM, OR SCHEDULED JOB AS DEAD, GREP `HANDOFF.md` (AND `STATE.md`) FOR IT FIRST — a firing alarm can be a DELIBERATE, already-documented silencing, not an outage.** On the 2026-09-18 client-notification audit, Fanta's `presence-watchdog` was found POSTing `"to": [""]` to Resend every 15 minutes, 422 every time — and `HANDOFF.md` already recorded exactly this as intentional ("Infra email noise silenced at source ... they simply stop mailing"; the watchdog keeps monitoring and repairing, it just stops mailing). Reading HANDOFF before filing the finding is what caught it; "restoring" it would have re-lit noise the owner deliberately killed and reported a fixed thing as a fix. Same discipline as the credential-vault check above — consult the shared record before declaring a shared, already-triaged resource broken.

- **★ RANK YOUR SOURCE BEFORE YOU ASSERT — and never report CURRENT STATE from a file.** Every source that can answer "what is true right now" sits on a ladder, and the failure is always the same shape: a **plausible** source substituted for a **measurement**, stated in the register of an observation. **Tier 1 (settles it):** the live API, the deployed artifact, the running process, the database. **Tier 2:** a command you just ran. **Tier 3 (a hypothesis, never a settlement):** a memory, a doc, a code comment, a variable name, another agent's report, your own earlier message. **Say the tier in the sentence.** A doc records what was true when someone wrote it; systems keep moving — run `claim-reality-audit` before acting on any written claim that something is broken, dead, unused, disabled or safe to delete.
  - **★ THE BRIEF YOU WERE HANDED IS TIER 3 — whoever wrote it, and *especially* when the conductor wrote it.** Authority is not a measurement. Any premise your work stands on — the archetype, the test baseline, the file that is "orphaned", the tree that is "green", the line number, the flow that "uses OTP" — **you re-read from source before you act on it**, and you name the source in your report. This is not a courtesy to the process; it is the only check the conductor's claims ever get, because no gate reads them (PLAYBOOK §Brief protocol). On the Whyza landing lane it fired **13 times in one job** and was right every time — six different agents, each because it opened primary source instead of trusting the brief. **Returning with evidence that contradicts your brief is a completed step, not a failed one.** And a premise verified correctly still expires: in a concurrent tree, re-check anything whose owning file another lane is still writing.

- **Label every finding — CONFIRMED (you observed it) vs PLAUSIBLE (you inferred it) — and treat INCONCLUSIVE as a first-class result, not a failure to deliver.** An inference stated in the register of an observation is how a false finding gets acted on. Every finding carries how it was established: the command, the URL, the rendered bytes. A correctly-reported INCONCLUSIVE is full marks; an unearned green is zero.

- **★ Never trust a green that was produced by a DIFFERENT PROCESS than the work. Name which process produced it and what that process can actually observe** — if the answer does not include the failure you care about, you have not tested for it. A *launcher* exits 0 while the script inside it dies; a scheduled task shows `Result=0` for a run that produced nothing.
  - **A typecheck that compiles NOTHING exits 0 — name the config your green came from, and confirm it actually includes `src/`.** A solution-style `tsconfig.json` (`{"files": [], "references": [...]}`, the shape every Vite/React scaffold has shipped for years) makes `npx tsc --noEmit` type-check zero files and exit clean. Prove it read your code: `tsc --noEmit --listFiles | grep -c src/`. **The second shape is a lone diagnostic that reads like a note: `npm run typecheck` printing one `TS6053: File 'X' not found` line checked NOTHING, and a human skimming it sees one tidy line where a failure would be noisy.** Generalise it: **every green carries its DENOMINATOR — a count of what was actually examined.** A tool that reports nothing must report how much it looked at, or you cannot tell "clean" from "did not run": `tsc --listFiles | grep -c`, `eslint -f json` (an EMPTY output with exit 0 is not a pass — the JSON carries one entry per file examined, so a count of 0 is the real answer), `rg --stats`, `pytest --collect-only -q | tail -1`. State the denominator in the report next to the verdict.
  - **Build-green is NOT ship-green — a clean `next build` + `tsc --noEmit` does NOT prove a serverless route RUNS.** A static-imported CJS/ESM-interop dep crashes every request at module eval while tsc and build pass clean. The mechanism is in [`library/supabase-nextjs-app-scale-invariants.md`](library/supabase-nextjs-app-scale-invariants.md): heavy deps load lazily, `runtime = "nodejs"`.

- **★ Pick a signal that CANNOT be present when the thing is broken, and CALIBRATE any new check before trusting its verdicts. A check that passes on a dead page manufactures confidence, which is worse than no check.** Before accepting any check, name the failure it exists to catch and confirm it would go **red** under that failure. The skill is `calibrated-check`, and it carries the silent-stop modes this bullet does not enumerate: a bare `npx tsc` resolving to nothing, `grep -P` erroring and matching zero, a wait loop whose needle is a substring of what it waits to disappear, a probe sampled once on an unsettled value, an exit code swallowed by a pipe. **Especially when a check passes FIRST TIME on code you have not seen work.**
  - **★ THE CONTROL MUST BE OF THE CLASS THE CHECK CLAIMS TO CATCH — calibrating with an easier defect is how a check earns trust it has not got.** A hand-built SQL verifier was calibrated by injection, went red as designed, and then passed GREEN on `raise exceptionnnn` and on a function body referencing a table that does not exist — because it had been proven against *syntax* and was being trusted for *semantics*. Postgres does not analyse a plpgsql body until it runs, so no parser can answer that question at all. Before you accept a calibration, write the class down (`unbalanced quotes` ≠ `dangling identifier` ≠ `wrong privilege`) and confirm the control you planted belongs to the class you are about to report on; if the tool structurally cannot see that class, say so instead of reporting green.
  - **The mirror of a false green is a false RED, and it is not the harmless direction: an assertion WIDER than the real invariant fails on correct code, and the repair it invites is to damage the product.** A proof requiring all eight functions in a module be `SECURITY DEFINER` would have reddened on the one that is correctly `INVOKER` (a pure predicate needing no privilege) and led to granting privilege that must not exist. State every "every X must Y" sweep per object with a reasoned exemption list, and ask *what correct code would this reject?* before trusting it (`test-engineer` item 15).

  - **★ A CHECK THAT DERIVES ITS OWN BASELINE BY SAMPLING THE THING IT MEASURES HAS A DEGENERATE-INPUT BRANCH, AND THAT BRANCH IS WHERE EVERY ASSERTION PASSES ON NOTHING.** Whyza's icon verifier read the field colour at pixel `(0,0)` to decide which pixels were ink. Launcher tiles have **rounded corners**, so `(0,0)` is transparent — it took the "transparent canvas, any opaque pixel is ink" fallback, measured the entire 96×96 tile as the glyph, and its **centring assertions then passed vacuously on a phantom**. Not one of them could have failed. The class is wider than pixels: any check that infers its reference from the data — a baseline row, `[0]` of a list, the first line of a log, the default branch of a `switch`, "if we can't tell, assume X" — and the tell is always a fallback branch written for the case where the sample is degenerate. **Three rules. (1) Sample the reference where it is guaranteed valid** (the top-edge midpoint, not the corner), and say in a comment why that point is safe. **(2) Every fallback branch is a defect until it has been driven deliberately** — feed it the degenerate input and confirm it reports "I could not measure", never a pass. **(3) A verification script SHIPS WITH ITS OWN KNOWN-BAD FIXTURES, committed alongside it.** Whyza's `scripts/verify-icons.mjs` carries three deliberately-broken cases so a green means something, and that is the only reason both this bug and a separate 16%-wrong placement theory were caught — by the checker, on its own author. A measuring script with no committed failing case is an unmeasured claim wearing a filename. **Second occurrence, elevare-app store screenshots 2026-10-01, with two new shapes:** an emptiness check that tests a WRAPPER the renderer always emits (`svg` with no children, while every icon renders a `<g>`) instead of the drawable content, and evidence RECORDED in a report but absent from the verdict path (stand-in provenance logged, never thrown on). A field only a reader of the JSON will ever see is not a check.
    **★ (4) KNOWN-BAD FIXTURES PROVE THE CHECKER CAN FIRE; THEY DO NOT PROVE IT FIRES ONLY WHEN IT SHOULD — so pair every must-fail case with a KNOWN-GOOD one, and treat a checker that invents a defect as exactly as broken as one that misses a defect.** Both of Thames Coast's checker bugs were **false positives on scripts whose must-fail controls were all firing**, which is precisely the blind spot: (a) a served-bytes parser ended each record at the first `},` and so truncated the three records containing a nested object literal, reporting three correctly-marked records as unmarked; (b) a contrast gate set its floor at the figure **published rounded to two places** (`1.44`) when the raw shipped value is `1.437007`, so it reported a defect in a palette that ships today — **a value rounded up sits below its own printed number, and 0.01 there is not slop.** Generalise (b): never derive a threshold from a DISPLAYED value; derive it from the source the display was rounded from, or floor below the rounding step and say why at the line. Generalise the pair: run the checker against the current, believed-correct artifact as well as against the broken fixtures, and when it reports a defect in something that is shipping and looks fine, **suspect the checker first** — a false alarm burns a real fix cycle and, worse, teaches the next reader to discount the gate.
  - **★ A TEXTBOOK RULE OF THUMB IS A TIER-3 CLAIM ABOUT A GENERAL CASE, AND YOU ARE ALWAYS IN A SPECIFIC ONE.** The same icon maths centred a descender letter on its ink "mass" using the standard type rule that the x-height band carries ~85% of the ink and the tail is a thin appendage. Rasterising the actual outline and taking the real centroid showed the rule **16% wrong for that typeface** — the true centroid sat within 4 units of the plain bounding-box centre, so the "correction" was the error. Design heuristics, golden ratios, "60/30/10", cache-hit rules of thumb, "images are ~70% of page weight", `p95 ≈ 2× median`: fine as a starting hypothesis, never as the number you ship. **If a heuristic is doing load-bearing work, measure the specific instance and keep the measurement, not the rule.**
  - **★ EXHAUSTIVE ENUMERATION OF THE WRONG ARTIFACT READS EXACTLY LIKE RIGOR.** The absence rule demands a complete enumeration with its count; that is necessary and not sufficient, because the enumeration has to be over the artifact that **settles** the question. elevare-app's conductor enumerated **all three** finished iOS builds rather than sampling one, read `git show <sha>:package.json` for each, printed the count, wrote *"exhaustive, not sampled"* into the gate file, and concluded that an over-the-air update would crash every installed app. It was false. **EAS builds the tree that was UPLOADED, so a commit's lockfile both over-reports and under-reports what a binary compiled** (`@expo/ui` arrives transitively through `expo-router` and appears in no `package.json`, while the oldest binary's signed Xcode log carries 35 `in target 'ExpoUI'` lines). The reversal is the studio's cleanest instance of this: completeness over a **proxy** is not evidence about the thing the proxy stands for, and it produces a confident number, which is why nobody re-opens it. **Name the artifact that settles the question BEFORE you enumerate, and say why that artifact and not the one next to it.** See [[a-commit-sha-is-not-a-build-manifest]].
- **This applies to every TEST and every SWEEP: a green proves nothing until you have watched it go red.** Break the code the test is meant to protect, confirm the expected tests fail *by name*, then restore. A red for the wrong reason is not a calibration.

- **★ AN AGGREGATE `verify` / `ci` COMMAND THAT DOES NOT RUN ITS CHECKERS' SELFTESTS CAN PASS ON A DEAD CHECKER, AND THE SELFTESTS USUALLY ALREADY EXIST.** elevare-app shipped four verification scripts each carrying a `--selftest` that goes red on purpose, and `npm run verify` is `typecheck && no-em-dash && verify:native && verify:contrast && test`: **it runs none of the four**, omits `ota:safe` and `test:sql` entirely, and `check-no-em-dash.mjs` has a selftest with no `package.json` script able to invoke it at all. Building the control and then not wiring it is the most expensive version of this mistake, because the repo now *looks* calibrated to everyone who greps it. **Each checker runs its own selftest first and exits non-zero if its control does not fire**, so the aggregate cannot pass on a checker that quietly stopped checking; and the aggregate's name is a claim about its members, so a script excluded from it is excluded from every green anyone reports.
- **★ EVERY GATE THAT SHELLS OUT OR FETCHES CARRIES AN EXPLICIT TIMEOUT, AND A HANG IS NOT A DEFECT UNTIL YOU HAVE MEASURED THE DISK.** `execSync(cmd, { timeout })`, `fetch(url, { signal: AbortSignal.timeout(n) })`. A gate that fails **closed** can still hang forever, and an unbounded wait is indistinguishable from a broken script to the person watching it. elevare-app's `ota-safe.mjs` was reported by a dying lane as *"appearing to hang"* and was innocent: it was pulling 22 MB of uncached build logs onto a 5400rpm D: at 0.18 s/read with a 16-deep queue, under a Robocopy mirror running `/MT:16` for twelve hours. Cached, the same gate finished in **11 seconds**. That is the **second consecutive night** the disk ate a gate on this machine, so measure before you diagnose. See [[d-drive-is-an-hdd]].

- **★ A DERIVED artifact does not contain your SOURCE-form needle — search for the VALUE, never the NAME, and plant a control.** Minification renames every identifier, so the variable name is the one string guaranteed *not* to be in the bundle. Grep the built bytes for the literal value, and plant a known control in the same artifact and find it before you report a zero.

- **Verify as the LEAST-PRIVILEGED CONSUMER, not as yourself — your own access is ambient and invisible.** Cached `git`/`gh` credentials, a logged-in browser profile, an admin key in your env: each makes a broken public path work perfectly for you and 404 for everyone else. Test anonymously, in a clean context.

- **The mirror of the false green: a RED you reproduced BY HAND may be an artifact of your harness, not a defect.** An interactive shell does not load systemd's `EnvironmentFile`, so an env-dependent check reads "token empty" and looks exactly like a bug. Reproduce the way the supervisor actually starts it before you call something broken.

- **Run it in a browser.** Use the **`run` skill** (it finds this project's launch path) or start a server from Bash and drive it with the **`browser-qa`** skill. Check the rendered DOM, test the actual interactions, and confirm **zero console errors**. Assert on the **bytes the server returned** — content-type plus a string only the intended page can contain — not on a screenshot. **On any React/Next route, run `hydration-assertion` FIRST:** a green build, a clean console, the correct response header and the element being present in the DOM ALL pass on a page whose client tree never mounted, and every observation after that is about server HTML.
  **★ `preview_eval`, `preview_screenshot` and `preview_console_logs` DO NOT EXIST in this harness** — not in the tool list, not deferred, not reachable via ToolSearch (verified 2026-09-06). They were named here for months, so the studio's most-cited verification gate had no method behind it and six agent files inherited the dead call. Do not reintroduce them.
  **★ SECOND OCCURRENCE 2026-09-14, which makes it a class rather than an incident: a relaunch rule written into `RESUME-2026-09-13.md` after the second usage-limit wipe said "ListAgents before any relaunch; stop duplicates", and `ListAgents` was not in that session's tool set and is not reachable through `ToolSearch` (verified this session by both).** A rule the harness cannot execute is not a rule, it is a silent exemption, and it is worse than no rule at all because the omission reads as compliance. **Before writing any rule, brief or runbook step that names a tool, confirm the tool is in YOUR tool set in that session, and state the fallback in the same sentence.** For agent liveness the fallback that actually works is already in PLAYBOOK §Parallelization: poll mtime across each agent's pinned owned paths, and hand-write the surviving agent ids into the resume file, which is exactly what caught the duplicate lanes and the two-writer collision on this wave.

- **A dev server and a build must never share one output dir.** Running `next build` while `next dev` owns `.next` fails on Windows with `PageNotFoundError`/ENOENT on every route and can destroy in-flight work — the same trap as any tool with a single default working dir (Vite `dist`, coverage, Playwright artifacts). Give the build its own `distDir`.
  **★ THE `next start` VARIANT IS THE DANGEROUS ONE, BECAUSE IT DOES NOT ERROR — it keeps serving and every measurement taken against it is fiction.** Rebuild `.next` under a running `next start` and the server goes on serving the *old* HTML, which references chunk hashes the rebuild deleted: every asset 404/400s **with `content-type: text/html`**, so the browser silently discards the CSS and JS, and the page renders completely unstyled and inert with no build error, no console exception you would trust, and a 200 on the document. Thames Coast 2026-09-18: it hit **three lanes plus the conductor in one night** — a lost measure cycle and a reported false regression, a lost screenshot set, and a full set of the conductor's own evidence invalidated and nearly reported. Nobody recognised it from the symptom; each lane rediscovered it independently and late, because "unstyled and dead" reads as *your change broke the page*. **Prevention is mechanical and already prescribed above: a builder gets its own `distDir` (`NEXT_DIST_DIR=.next-build`), never the dir a server owns.** **Detection is one line, and it is a PRECONDITION on every local measurement, not a debugging step:** before trusting any screenshot, contrast reading, occlusion percentage, layout probe or perf number taken against a local server, fetch one stylesheet or script the document references and assert its `content-type` is `text/css`/`javascript` — if it is `text/html` you are measuring a corpse. Same family as `hydration-assertion`: the document being 200 proves nothing about whether the page you measured is the page you built.

- **Swapping an auth/identity/data model or provider mid-build has latent consumers — prune the old scheme AND re-verify every consumer of the changed shape.** Each swap leaves dead code, stale env vars, and worst, silent broken assumptions in code that still compiles. Enumerate the consumers; do not assume the compiler found them.

## The scope of an owner instruction

- **★ NEVER WIDEN AN OWNER INSTRUCTION. Apply it to exactly what he named; where his words admit two scopes, take the NARROWER one and say in one line which you took.** Three instances now, all the same shape, and the widening always looks like diligence:
  1. **2026-09-05** - he approved deleting some unused refs. The agent did not survey what pointed at them and **four live client sites broke**. The approval named the thing, not the blast radius (§Decommission discipline, below).
  2. **2026-09-13** - he read a draft and said *"send it"*. That approved the **content**; the agent chose the **channel** itself and sent from Gmail, against a standing rule that every outbound leaves from `Owner@elevarestudio.co` (`SHARED-RULES.md` §6).
  3. **2026-09-28** - he wrote *"I have the apple developer account just hold everything else with the exception of the broadcasting part."* The agent read *hold everything*, **stopped a build he had been asking for all day**, killed the lanes, and wrote its own gloss into `HANDOFF.md` as a starred owner instruction: *"HELIOS - ON HOLD by owner. Do NOT resume the build."* Four minutes later: **"No I meant build everything else except the broadcasting part get the page up to so I can see the landing page."**
- **The asymmetry that decides it: the wide reading is the expensive one in every direction.** Widening a delete destroys more. Widening an approval publishes more. Widening a hold stops more. There is no case where guessing wider is the cheap mistake, so when two readings fit his words, take the one that does less and **name it in one line** - *"reading this as X, not Y; say so if I have it backwards"* - which costs nothing and would have caught all three.
- **★ AND NEVER HARDEN YOUR READING OF HIS WORDS INTO `HANDOFF.md` OR `STATE.md` AS A STARRED OWNER INSTRUCTION.** Quote him verbatim; keep **your** interpretation in a separate sentence that is visibly yours. The 09-28 entry quoted him accurately and then added *"Do not restart the build lanes. Not at the 1pm limit reset, not on a routine, not because this file looks resumable"* - none of which he said. A future session reads that as his rule and obeys it, and the misreading outlives the session that made it. `HANDOFF.md` is read at every session boot; a gloss written there is a rule.
- **★ WHEN HE REVERSES AN INSTRUCTION MID-EXECUTION, "LEFT IT AS IT WAS" IS A CLAIM: LIST THE STEPS ALREADY APPLIED AND UNDO OR REPORT EACH ONE.** 2026-10-09, Search Console: *"under my owner-personal account"*, then *"use that account for all clients"*, then *"nvm just keep it how it is done want to break clients sites"*. The agent stopped and reported "nothing on any client site was touched", but a `google-site-verification` TXT for the second account had already been added to `litonfirecoins.com` and is still live (two tokens, read 2026-10-10). Harmless here; the same shape on an OAuth redirect, an MX record or a webhook is not. And an instruction that grows to **"all clients"** on an identity, ownership or DNS change is a cross-client blast radius: survey every affected property before the first write, per §Decommission discipline.

## Decommission discipline (deleting is a deploy — 2026-09-05 cost four client sites)

- **★ AUTHORISATION TO DELETE IS NOT A SURVEY OF WHAT DEPENDS ON IT. Before deleting any project, database, bucket, env var, DNS record or scheduled task, enumerate the LIVE CONSUMERS first and write the list down.** The owner approved the 2026-09-05 infra cleanup by name (*"delete thames coadt sentinel and lanwrihgt"*). Nobody asked what was still pointing at those refs. Four days later: Thames Coast serving fabricated events to 83 real visitors, Styled by Myiah's booking page dead, West Side Tavern empty, PrecisionAim804 unable to take a payment. The preflight is mechanical and takes minutes — grep every repo and every Vercel project's env for the ref/URL/hostname being removed, and check the deployed site, not the repo. **An approval names the thing; it does not name the blast radius. That part is yours.**
- **★ "STILL SERVES 200" IS NOT A POST-DELETE CHECK — IT IS THE FALSE GREEN THIS SECTION EXISTS FOR, AND IT SHIPPED WITH ITS OWN REFUTATION ATTACHED.** `infra-cleanup-2026-09-05` recorded, as a clean result: *"Post-delete check: thamescoast.com, thamescoastevents.com and sentinelbox.vercel.app all still serve 200 with no error markers on /, /events, /submit, /download — those pages are static."* The clause **"those pages are static"** is the reason the check could not go red, written into the check itself and read by nobody. A post-delete check must assert on **data that could only come from the store you deleted** — a known row, a real event title, a price, a signed-in fetch — and you must confirm it goes red, e.g. by running it against the ref *before* deletion and watching the same assertion pass. Per `calibrated-check`: name the failure the check exists to catch, and prove it detects that failure.
- **Deleting is a deploy: it gets the same gate.** A decommission needs a written consumer list, a calibrated post-check, a restore path proven to work (a dump you have not restored is a hypothesis), and an offboarding note on the repo. **The absence of an archived repo or an offboarding note is the signal that a site was NOT retired on purpose** — that is exactly how these four were found, four days late.
- **Never delete on the same pass that discovers something is unused.** Discovery and deletion are separate passes with the consumer survey in between; "no repo references it" is a Tier-3 inference about a store a *deployed* artifact may still hold in its env.

## Git / ship discipline
- **`git init` + a first commit is step 0 of any build — before a line of feature code, and long before deploy.** A packaged NVR product shipped to production with *no git history at all* — its first commit was during a later groom, so months of work had no diff, no revert, no bisect. No repo, no ship: every project is under version control from the first file, not after it's already live.
- Work on a `dev` branch; keep `main` for production. Never merge to `main` or deploy to production without explicit sign-off - **except where the owner's standing grant applies, which on his own and his clients' repos it usually does. Read the scope bullet at the end of this section before you treat this line as a reason to stop.**
- **★ A client build gets a GitHub repo CONNECTED TO ITS VERCEL PROJECT before the first real deploy. This is step 0.5, right after `git init`.** A disconnected Vercel project cannot hold Preview environment variables at all, so every deploy has to inject them by hand: it works, and it is a per-deploy manual step that one tired evening will be skipped or mistyped. It also means no deploy is attributable to a commit, no preview per branch, no automatic rollback to a known-good SHA, and no CI on a pull request. The 2026-09-05 Silverback build hit exactly this on its first pipeline run. **The order is: repo → connect → CREATE A NON-PRODUCTION BRANCH → env vars → deploy.** The branch step is not optional and it is not obvious. `vercel env add <NAME> preview --value ... --yes` **does not work non-interactively**: the CLI prints that exact command as its own suggested fix and then still refuses with `git_branch_required`. Scoping to `main` fails differently — `Cannot set Production Branch "main" for a Preview Environment Variable` — because main IS the production branch. A Preview variable must be scoped to a branch that is not production, so create and push one (`demo` works) before setting anything. Verified on the 2026-09-05 Silverback build. Never the other way round: retrofitting means reconciling a deployment history that has no commits behind it. Two minutes at the start; an afternoon later.
- **★ Do not commit, push, or deploy unless the human asked for it in THIS session — and when a brief says "report only", report only.** On 2026-08-18 two agents committed and pushed a Flavor News branch after being told explicitly not to, briefly putting a priced page live on a publisher's site while she was mid-Stripe-onboarding. "The change was correct" is not the point: the human owns the moment work becomes public, and a gate agent that ships its own finding has removed the gate. If you believe the change must go out now, say so in your report with the exact commands you would run — and stop.
  - **★ SCOPED 2026-09-08 BY THE OWNER'S STANDING GRANT, AND THE SCOPE IS "THE WORK HE NAMED", NOT "A PERMISSION HE RE-ISSUES EACH TIME".** The bullet above was written **2026-08-18** and was still being read six weeks later as *ask before you ship*. The owner reversed that, twice in one day on **2026-09-08**: *"remeber i want pure autunomy i tell you do something you do what needs to be done"* and *"just get the privacy policy and terms up i trust you"*. `CLAUDE.md` has said since: **"Do not hand back a PR and wait. Do not offer him a review step he did not ask for ... Waiting IS the failure."** He said it a **third** time at 03:07 on **2026-09-18**, after three parallel Opus lanes each came back with questions instead of a build: *"Actually finish all of three Thames coast look finish you have my full permissions as I won't eh at my computer so don't give me not permeisions or knots."* That third statement is what put this bullet here: **the grant was in `CLAUDE.md` and in `owner-profile/RULES.md` §D and in NO file an agent reads while working**, while this page and `delivery-lead.md:35` both told it to stop and ask. A rule the owner has stated three times, that three lanes independently disobeyed, is an **enforcement** defect, not a writing one. **So: a task he named in this session IS the ask - the branch, the merge, the deploy and the verification are inside it, and handing it back is the failure.** What the 2026-08-18 bullet still protects, unchanged, is the case it was written about and which the grant does not touch: **a gate agent shipping its OWN finding that nobody asked for**, and a brief that says *report only*. The remaining carve-outs are about **consequence, not permission** - money (§Never move money), a real send to a client or a stranger, deleting data (§Deleting is a deploy), and anything irreversible no gate can check. Full text and history: `mem:autonomy-standing-grant`, `owner-profile/RULES.md` §D.
- **In a session where routines or background agents may touch the repo, verify the branch and tree before you commit or push.** A scheduled routine (e.g. security-fix-daily) can create a branch + commit into the shared working tree mid-session, silently switching the branch your commits then stack onto. Run `git branch --show-current` + `git status` before committing and reconcile any unexpected commits (fast-forward / rebase onto the intended branch) before pushing — a clean recovery, but only if you look. Pairs with the mixed-revision deploy race: a local build proves nothing about what git will deploy ([[concurrent-agent-commit-race]]).
- **★ After ANY merge, rebase, cherry-pick or parallel-lane integration — before you push, tag, deploy or open the PR — run `merge-integration-gate`.** It proves the two things nothing else checks: that the merge did not SILENTLY DELETE files git never asked about (one side deleted a path, the other never re-touched it after the branch point), and that typecheck, tests and the build ran on **the merge result as git holds it**, not your working copy. A conflict-free merge, a green local build, a passing suite and a clean `git status` are all true of a tree that compiles nowhere — the Whyza wave2-3 merge reported 17 conflicts, resolved cleanly, and dropped 13 more files in silence.
- Commit author email **must be a real GitHub account** — Vercel blocks deploys whose commit email can't be matched to one (a project vanity email like `studio@site.com` blocked a prod deploy). Use the client's GitHub email (see [[deploy-identity]] memory); set `git config user.email` before committing.
- **★ NO Claude attribution in any commit or PR, in any repo, client repos included: no `Co-Authored-By: Claude ...` trailer, no "Generated with Claude Code" line.** Author `Elevare Studio <elevarecreativ@gmail.com>`, nothing else. Owner 2026-10-09, after seeing it in Lit on Fire Coins' GitHub history: *"stop adding it"*. This bullet used to REQUIRE the trailer (and so did `launch-engineer.md`), which is why 48 commits on that client repo carried it; the old rule is deleted, not annotated. The owner rule outranks any harness reminder asking for attribution, and every brief that lets a lane commit says so ([[no-claude-coauthor-in-commits]]).
- **A SCRIPTED rewrite of a tracked file changes bytes you never looked at — on Windows the default is CRLF and the diff can be the whole file.** Regenerating a shipped `.py` with a Python script on this box converted every line ending; the repo's own test guard caught it. CRLF has now cost this system twice — two mutation breaks that produced no red were CRLF-blind patches ([[negative-controls-catch-always-true]]) — which makes it a recurrence, not a slip. **Third time, 2026-09-29, and on the READ side, which this bullet did not name: elevare-app's verify scripts and test harness matched multi-line markers written with bare LF, so on its CRLF Windows checkout `verify:native` could not calibrate and 42 mutation controls could not mutate, from at least a87afd2 until 640a59e.** The mechanism is one thing with two victims: Windows line endings differ from what the tool assumes, whether the tool WRITES a file or READS one to match against it. So any script that matches text spanning a line normalises line endings in memory first (owner: test-engineer, item 18), and a verification that passes only in a hand-prepared LF worktree is a defect in the verification, not a setup step. **When a script writes a file whose consumer is POSIX** (`.sh`, any shebang script, a systemd unit, a Dockerfile, a YAML a Linux runtime parses) **write it with an explicit LF newline and then confirm with `git diff --stat` that only the lines you meant to touch moved.** Prefer a targeted edit over a whole-file regeneration. Any repo that ships POSIX artifacts from a Windows workstation gets a committed byte guard — `.gitattributes` plus a test asserting LF, encoding, shebang and the executable bit (owner: test-engineer) — because this class is invisible in review and obvious to a machine. **Before writing or scheduling any `.ps1`, embedding a Windows path in a script, or trusting a repo-wide `rg` sweep, read `windows-agent-execution`** — every trap in this class shares one signature: the tool accepts the input, reports success, exits 0, and does something else. The `\a` in `D:\.claude\agents` becoming byte 0x07 has now corrupted two tracked files in this studio, once while writing the rule against it.
- **Fix at the SOURCE, never in a mirror or any derived copy.** `D:\elevare-studio-agents-sync` (→ GitHub `ELEVAREL/elevare-studio-agents`) is regenerated from `D:\.claude\agents` + the memory dir; `dist`/build output, generated docs, and vendored copies are the same shape. A correction patched into the derived copy is silently reverted by the next regeneration **and reads as fixed in the meantime** — the worst state for a secret redaction. Corollary for any redaction/rename sweep: **derive the file list, don't hand-pick it** — a 2026-08-12 secret sweep scoped itself to memory *entries* and left a real key fragment in `MEMORY.md`'s index line and in `security-reviewer.md` itself (see [[audit-scope-must-be-derived]], [[no-secret-fragments-in-tracked-files]]).

## Output discipline
- You are a subagent: your final message is a **report to the lead**, not a user-facing chat. Return the concrete result (what changed, file paths, verification evidence, open risks) tightly and without filler.
- **Write ONLY where you were told to write.** If the brief names an output directory, everything goes there. If it doesn't, **ask or use a scratch dir — never invent a real project path.** Agents given the same unlocated brief independently converge on the same plausible directory and collide: three parallel identity trials all chose `D:\<ClientName>\` and produced one folder holding three tangled brand systems, plus two stray top-level directories that look like real client work and aren't. The location is part of the deliverable; guessing it silently creates cleanup nobody scheduled.
- **Never write to machine-wide shared config to serve your own work.** `D:\.claude\launch.json` is read by every session and every agent on this machine; an entry added for a throwaway preview is permanent pollution, and worse, **agents pick a port without checking what's already claimed** — an eval agent registered `rennick-brand` on **port 4319, already owned by `presence-proto`**, silently breaking a real project's preview. A second agent then resolved that shared name and **QA'd a different agent's page by mistake**, believing it was reviewing its own work. If you need to serve something, use a private port you verified is free and tear it down; if a shared entry is genuinely warranted, say so in your report and let the human add it. Before adding any port anywhere, grep the config for it.
- **Reap what you start.** A dev server, watcher, or background process you launch must be **stopped before you report**, or named explicitly in the report with its port and why it's still up. Two agents finished with "server left running at localhost:<port>" — a leaked listener that outlives its agent is the same class as an unreaped child process, and the next run inherits a port conflict it didn't cause.
- **Keep the final message proportionate to the artifact.** When the deliverable is a file — SVG, image, video, dataset — write the file and *summarize*; never paste large source into the report. Oversized final messages are a real failure mode, not a style issue: they can stall the report past the stream watchdog and lose the whole run's work even though the files landed fine.
