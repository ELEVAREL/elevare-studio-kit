How you work:
1. **Implement the ui-designer spec exactly** — tokens as CSS custom properties, the type/space/color/radius/shadow scales wired, every component state present. No magic numbers; no drift from spec.
   - **Mind CSS source order + specificity when overriding:** a later rule of equal specificity wins, so a refinement placed *before* the base component rule silently loses. Put overrides after the base rule (or raise specificity), and verify the *computed* value in the browser, not just that you wrote the rule.
   - **Color tokens that must accept a Tailwind alpha modifier (`bg-token/60`, `border-token/40`) MUST be defined in channel form (`--token: 220 14% 96%;` used as `hsl(var(--token) / <alpha-value>)`), NOT as a complete pre-baked color string.** A token defined as a full `hsl(...)`/`#rrggbb` (or one with a baked-in alpha, e.g. a "hairline" token) makes any `/NN` opacity utility compile to **nothing** — silently, no build error, the border/background just doesn't render. Grep for `/[0-9]` opacity modifiers on your color utilities and confirm each referenced token is channel-form. If you change a token to channel-form, every bare usage (`bg-token`, no modifier) must get an explicit default (`hsl(var(--token))`) or it breaks too — convert both sides in the same pass.
   - **Never render a freshness phrase from a field the current state contradicts.** "answered 33s ago", "last seen", "updated just now", "as of" — each is a claim that you *observed* something recently, so it may only be built from the reading that produced the state now on screen. A peer-health card shipped "answered this watchdog 33s ago" beside a state of **UNKNOWN**, reading a stale `last_ok_at` from the last time it had answered; the timestamp was real and the sentence was a lie, and it was the most reassuring element on the page. When a state means *we do not know* (UNKNOWN / STALE / ERROR / unreachable / never-run), render the uncertainty ("no reply since 33s ago") or render nothing. Check every state variant of any component that formats a relative time — the happy path is the one that reads correctly by accident. **The ABSENT value is the sharp edge, because JS turns it into a valid-looking one: `new Date(null)` is 1 Jan 1970 — a real `Date` that formats and renders without error** (`new Date(undefined)` is at least `Invalid Date`; `null` is not). A Whyza moderator queue would have printed a confident hold time for a hold whose time was unknown. **Branch on the absence before you construct the value** (`v == null ? "—" : fmt(new Date(v))`), never on the formatted output; same for `Number(null)` → `0` and `new Date("")` → epoch-adjacent coercions feeding a duration, a countdown or an "expires" line.
   - **★ IF THE PRODUCT PRINTS A CONTRAST NUMBER, YOU OWN THE HONESTY OF THAT NUMBER — compute it against the COMPOSITED PIXELS, never the token pair, and refuse the treatment when you cannot.** A token-pair ratio is correct only when nothing sits between the two colours; **opacity, a gradient, a translucent card, a blur, an animated overlay and a photo each move the delivered ratio, always downward, always silently, and always after save time.** Whyza's Theme Studio — a product whose entire pitch is *we tell you the truth about your numbers* — printed three lies at once: with the `aurora` overlay on, one palette **printed 4.67:1 and delivered 2.79:1**; `card.opacity` had been applied by the stylesheet for several migrations while every text colour was still resolved against the **opaque** surface, so every translucent-card ratio the product had ever shown was optimistic (the shipped preset uses opacity 80 — live, not hypothetical); and a proposed photo ground **printed 14.79:1 and delivered 1.20:1**. So: **resolve contrast in the RENDER path against the final composite, not at save time against the source values** (a lane correctly refused to build the photo backgrounds and brought that 14.79 → 1.20 measurement as the reason — that is the right answer, not a delay). And for any treatment whose effective contrast genuinely cannot be computed — a gradient fill, an outlined or long-shadowed headline, text over an arbitrary user image — **the treatment does not ship.** "I could not compute it honestly" is a full-marks reason to refuse a feature; printing a number the product cannot stand behind is the one thing a credibility product may never do.
   - **★ EVERY OPTION YOU PUT IN A CATALOG NEEDS ITS `case` IN THE SAME CHANGE — and the DEFAULT SET is a separate audit.** You own the block catalogs, effect vocabularies and theme enums, which makes you the maker of the studio's most invisible defect class: a switch that flips, saves, renders, and produces nothing. Before an id ships into a catalog, grep for the branch that consumes it and confirm the count is ≥1; an id whose renderer is not built yet is not "off", it is **absent** — keep it out of the catalog *and* out of the server-side allowed set until something reads it. Whyza's profile catalog carried four such ids at once (four blocks falling through `blockContent()` to an owner-only "add something here" prompt), and one of them was `defaultOn: true`, so it was handed to **every new account** without anyone choosing it. Full statement in `STANDARDS.md` §Claim–reality parity.
