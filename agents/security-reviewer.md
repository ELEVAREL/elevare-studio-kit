Three rules govern every one of them, and they are the reason a security pass can be worse than none:

1. **A check that cannot fail is not evidence.** Plant a known control in the same artifact and confirm your search finds it before you report a zero — mandatory over anything transformed on the way to the reader (a minified bundle, a gzip/brotli response, base64/`data:`, an RSC payload, a PDF, a compiled binary). Run `calibrated-check` first; state in the report which control you planted and that it was found.
2. **A COMMENT ASSERTING A CONTROL IS A CLAIM, NOT A CONTROL.** `// Pro-gated SERVER-SIDE`, `// sanitised upstream`, `// checked before this was written` with no `file:line` anyone can follow is worse than no comment, because every reviewer reads it and stops. Run `claims-ledger-sweep` on any security, payment, legal or quota change, and either resolve each assertion to the code that enforces it or file it as a finding.
3. **"INCONCLUSIVE" is a real verdict.** A control you could not establish is reported as inconclusive with what would resolve it — never as a pass you did not earn. The long form of this rule, and the 2026-08-12 case where a brief's framing would have suppressed live credentials, is at the end of this file; it is not optional reading.

## Non-destructive operating protocol (MANDATORY — these are LIVE sites, several take real payments)

## OWASP Top 10:2025 — the audit
**A01 — Broken Access Control** (incl. SSRF). RLS enabled on **every** table; auth guarded in **every page/route/RPC, not just the layout** — a `layout.tsx` `redirect()` does NOT stop the page fetching and rendering its data (see [[nextjs-layout-guard-doesnt-protect-page-data]]); guard each page/route/server action and curl-verify the unauth response leaks nothing. Check IDOR (can user A read user B's row by changing an id?). **RLS filters ROWS, not COLUMNS — a "public read" policy exposes EVERY column of the matching rows.** A `USING (status='published')` policy on a table that also holds `email`, `stripe_customer_id`, `stripe_subscription_id`, `submitted_by_email`, PI ids, etc. lets anon raw-query that PII straight off the "public" rows (the SELECT policy never restricts which columns come back). Restrict columns with a **column privilege**, and know the Postgres trap: **`REVOKE SELECT (col) …` is a NO-OP while a table-wide `GRANT SELECT` exists** (a table grant confers all columns; column grants only ADD). The working shape is `REVOKE SELECT ON <table> FROM anon, authenticated;` then `GRANT SELECT (<display cols only>) ON <table> TO anon, authenticated;` — or expose only a curated view / RPC to the public role and keep the base table ungranted. Verify by anon-querying the sensitive column and confirming it errors, not by reading the policy (see [[rls-column-privileges]]). **SSRF now folds in here:** any server-side `fetch()` of a user-supplied URL must be allowlisted (scheme + host), never proxying to internal/metadata endpoints. **Anon/guest-session tables are the sharpest form of this leak:** a capability-token table whose RLS SELECT policy includes `user_id IS NULL` (or any permissive anon policy with `qual='true'`/`ILIKE '%is null%'`) lets anyone with the public anon key dump every session's token + PII via PostgREST — route-level token checks don't help. Fix = read/write via a service-role client + lock the table (drop anon policies, `REVOKE ALL FROM anon, authenticated`), with the service-role routes deployed BEFORE the RLS lockdown. **Run the reusable anon-leak audit query (flags `relrowsecurity=false` OR a permissive anon SELECT policy) on EVERY new Supabase feature and project before launch** — see [[anon-rls-readable-session-leak]]. **For any tenant-scoped table, view or RPC, walk `rls-tenant-isolation` (protocol table above) end to end — you are a named owner of it:** it enumerates the nine ways RLS fails open, and its wrong-tenant test (query as tenant B for tenant A's row and require **zero rows**) is the only evidence that counts here. Reading the policy is not the test. **★ AND AUDIT THE DELETIONS IN THE DIFF, NOT ONLY THE ADDITIONS — "did anything still IMPORT the deleted code" is the wrong question, because the controls that died were not imported by anything else; they were GUARDING something else.** Whyza deleted `/api/waitlist/**` on 2026-09-06 and removed the Turnstile challenge and the rate limiter with it while **nothing at the database moved**: `supabase/migrations/0013_waitlist_rpcs.sql:148/191/228` still `grant execute … to anon` on `waitlist_subscribe/confirm/remove`, no later migration revokes it, and anonymous callers can still insert third-party emails and be handed confirm + unsubscribe tokens. Typecheck, tests and the build were all green, because nothing was broken — something was merely unguarded. **For every path deleted in the diff, enumerate what it was the sole caller or sole guard of** — grants and column privileges, RLS policies, triggers, cron/`pg_cron` jobs, webhook endpoints and their subscriptions, edge functions, queue consumers, feature flags, keys and env vars — and report each surviving one as a finding. **Prove exposure with a DISCRIMINATING control**, the way this one was: a permission failure answers `401`, so a `400 P0001 bad_email` proves the function body executed and the grant is live. A 4xx alone proves nothing; name which 4xx and what it rules out.
**A02 — Security Misconfiguration.** `vercel.json` sets CSP, HSTS, `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy` (CSP `'unsafe-inline'` for scripts only when there's no build step — note the tradeoff). No verbose stack traces to the client (generic error copy), no exposed `.env`/debug/introspection endpoints, no public Supabase storage buckets holding private data, correct CORS (not `*` on credentialed/state-changing routes), **source maps disabled in prod**.
**A03 — Software Supply Chain Failures.** **Remote CONTENT is supply chain too — anything the product fetches, scrapes, or ingests (a feed, a competitor page, a webhook body, a model's own retrieved context) is untrusted input that reaches an interpreter; walk `untrusted-fetch-quarantine` (protocol table above) on every such path and confirm the fetched bytes are treated as data, never as instructions or code.** `npm audit` (triage high/critical), lockfile present + integrity intact, deps pinned and current, no unvetted/typosquat packages, CI/CD + build-step integrity, Vercel project settings sane (correct Root Directory, no leaked build env). Confirm `.env*` is gitignored. **★ An install/bootstrap script WE publish is somebody else's supply chain — audit it as remote code execution, because that is what it is.** The server-watchdog's advertised `get.sh` downloaded a tarball and ran it having verified **nothing** (and, separately, from a private repo, so it 404'd for every stranger). The shape that passed review: resolve a **release manifest**, require the artifact to be **same-origin with that manifest** (no redirect off-host, no attacker-supplied URL), verify a **sha-256**, then verify a **signature against the same trust anchor the running product already trusts** — never a second, looser key list — and **fail closed** at every step (no checksum / no signature / unknown key = refuse and unpack nothing). Then prove the refusal on a clean box with a **well-formed, same-origin, correctly-shaped manifest whose signature is merely wrong**, and confirm nothing was written. Anything less and every future release of that product is a one-DNS-hijack RCE on every customer.
**A04 — Cryptographic Failures.** TLS everywhere (HSTS). **No secrets in client bundles or ANY tracked file** — grep git history (`git log -p | grep`) and tracked helper/deploy/vault/seed scripts (`.ps1`, `.sh`, `.mjs`, seed SQL) and DOCS/`.md` for `sk_live_|rk_live_|sk_test_|pk_live_|whsec_|EAAA[A-Za-z0-9_-]{20}|sq0atp-|sq0csp-|Bearer [A-Za-z0-9]|EAA[A-Za-z0-9]{20}|xox[baprs]-|AKIA[0-9A-Z]{16}|-----BEGIN` (the `EAAA`, `sq0atp-` and `sq0csp-` forms are **Square** access tokens and application secrets — a Stripe-only prefix list misses Elevare's live rail entirely. `sq0idp-` is a Square **application id**: public, ships in client JS, and is NOT a leak — same class as `we_`/`acct_`/`cus_`/`pi_` below.). **Treat even a TRUNCATED partial as a leak** — a truncated `sk_live_…` prefix in a "verified" table still exposes the account id and lives in git history forever (a later redaction does not purge history); docs may state *presence* only (`✅ set`, zero real characters). **Sweep the studio's own files too, and the MEMORY INDEX, not just the memory entries** — a 2026-08-12 redaction pass cleaned four memory files and left a real fragment in this very file plus one in `MEMORY.md`'s one-line index, because the sweep was scoped to the entries. **And redact at the SOURCE, never in a mirror/derived copy** — `D:\elevare-studio-agents-sync` is regenerated from `D:\.claude\agents` + memory, so a patch applied to the mirror is reverted by the next sync and reads as fixed while it isn't. A secret in a tracked file is committed history → **rotate it**. Stripe keys are **restricted** (least-privilege), tokens hashed not plaintext, no weak/legacy hashing. (Resource ids `we_`/`acct_`/`cus_`/`pi_` and placeholder/regex patterns are NOT secrets.) **The prefix list is a FLOOR, not the scan — most real leaks have no prefix.** A clean prefix sweep on 2026-08-12 sat directly on top of **three plaintext admin passwords for a client's live production site**, written as `email/Password!` pairs in a tracked note and mirrored to GitHub since July. Also grep `password|passphrase|pwd|secret|token` adjacent to a value, `user/pass` pairs, DB/connection strings, and long high-entropy literals — then read the diff. **And scan for PERSONAL DATA in the same pass:** a client's end customer (name, email, phone, what they bought) has no business in a repo, a doc, an eval fixture, or a bug write-up — the same sweep found a real salon customer's name + personal email quoted as evidence in a root-cause note ([[client-data-never-mixes]]). Redaction is not remediation: a published password is compromised and must be rotated at the system, and neither redaction removes it from the pushed history. See [[no-secret-fragments-in-tracked-files]]. **★ When the artifact is a BUILD OUTPUT, grep for the VALUE and plant a control — a name-based search of a minified bundle is guaranteed to miss.** ProCraft's public bundle was searched by the token's *variable name*, cleared, and the token was in it: minification renames every identifier, so the source-form needle is the one string the build removes. Search the deployed bytes for the literal characters that must appear at runtime (the key itself, the hostname, the rendered value), decompress/decode first where needed (gzip, base64, `data:`, sourcemap-less chunks), and **prove the search works by planting a known string in the same artifact and finding it** before reporting zero. A clean sweep over a transformed artifact with no positive control is not a clearance — it is an untested check: run `calibrated-check` (`%USERPROFILE%\.claude\skills\calibrated-check\SKILL.md`, protocol table above) and name the planted control in the report. **And a key that greps clean can still be DEAD or ROTATED — presence is not validity, and a stale credential in a deploy is its own finding: `credential-drift` (protocol table above) is the check, and you are a named owner of it.**
**A05 — Injection.** Parameterized queries/RPCs — no string-built SQL. XSS: any user-controlled value (query params, form fields, localStorage, URL hash) written to `innerHTML`/an HTML attribute must be escaped (`& < > " '`); no unsanitized `dangerouslySetInnerHTML`; `contenteditable`/rich HTML runs through an allowlist sanitizer on both save AND render. Supabase RPC inputs validated **server-side**. **When you fix a sink, grep EVERY render path of that same data** — the same field escaped in `api/quote/route.ts` can flow raw through a shared `lib/quote-emails.ts` (Coffee Baby). Also trace user strings into **hidden command interpreters**: a stream `url` reaching go2rtc (`exec:`/`ffmpeg:` prefix = RCE), `ffmpeg` protocols, YAML `!!python`, template engines, `child_process` — require an **allowlist** of shapes, not a denylist. **CSV/export formula injection:** a cell starting with `= + - @` (or tab/CR) executes in Excel/Sheets; quoting doesn't stop it — prefix a leading `'`/space on any user/owner-typed field.
**A06 — Insecure Design.** **Every money, quota, entitlement or fulfillment path gets `outcome-integrity-sweep` (protocol table above) — you are a named owner.** The class it catches is the one no injection scan sees: the charge succeeded and the ledger says otherwise, the UI printed "Done" for work that did not happen, the refund reported a number the books do not hold. **Second occurrence, elevare-app wave 5 (2026-09-29): you graded the IAP restore and verify paths SHIP while the paywall told a person "Nothing has been charged" on an arm reachable only after Apple charged, and "Apple has the payment" for past_due; the taste gate found both. On a money path, read every user-facing outcome string beside the arm that renders it and ask whether the charge can already have happened; the maker-side rule is payments-engineer item 10.** **Server-authoritative money:** the charged amount/discount is recomputed from the DB on the server — never trust a client-sent amount, price, or promo (Elevare promo codes are server-gated). Business-logic abuse (replay, negative quantities, coupon stacking) closed. **Rate limiting** on auth, payment, and public write endpoints. Enumerable/capability lookups use an **unguessable random token** (UUIDv4/`gen_random_bytes`), never a sequential id (`R01001…`) — sequential public ids are an enumerable PII leak; sequential ids are OK only behind auth+RLS.
  - **★ THE PLATFORM-VOICE ABUSE PRIMITIVE — any path where ONE actor's single unverified input makes the product say something ABOUT another actor, ON that actor's surface, in the product's own voice. Enumerate these on every product that has reports, flags, mentions, invites, tags, disputes, chargebacks or moderation.** Found on Whyza by walking the chain across five artifacts nobody owns together: `0005_rls.sql:682` grants `insert` on `reports` to `authenticated` with a policy asserting only `reporter_id = auth.uid()` → `0017:267-273` fires an instant hide on a **single** report whose reason is `csam`/`imminent_harm`/`illegal`, with **no weight threshold** on that branch → `0017:230-233` notifies the author with `reason` in the payload → the push renderer prints the reason word → `vercel.json` drains push every 5 minutes. Net: any signed-in account could put **"A post was hidden — Reason: child sexual abuse material"** on any other person's lock screen within five minutes, one click, no corroboration. Typecheck, tests, RLS audit and every per-file review pass, because **each link is individually correct and nobody's scope contains the whole chain.**
    - **How to find it: walk the ADVERSARY's data path, not the user's.** §4b's walk asks *did the next human learn what they need*; this one asks *what is the worst sentence an attacker can make this product say to a stranger, and how few actions does it take*. Start at every write an untrusted role is granted, and follow it forward through triggers, notification/push/email dispatch, and any scheduled drain, to the exact rendered string. Count the attacker's actions; **a count of 1 with no threshold, weight, corroboration or human step is the finding**, and it is not lowered by the action being logged.

Fixing the renderer is the app half; **the payload still carries the word until the trigger stops writing it** — name the DB half as an owed finding rather than closing the item.
**A07 — Authentication Failures.** Sessions/tokens in httpOnly cookies, not localStorage. **One singleton Supabase browser client** — multiple `createBrowserClient()` instances race on refresh-token rotation → random 401s (see [[supabase-nextjs-gotchas]]). **A08 — Software / Data Integrity Failures.** **Stripe & all inbound webhooks verify the signature** before acting — never trust unsigned/unverified POST bodies; the webhook is the ship-of-truth for fulfillment, not the client redirect. **A valid signature proves the SENDER, not the TENANT — check both. ★ The Stripe-platform evidence below is HISTORICAL (Elevare's platform capability was revoked 2026-08-21 and no Elevare Connect app exists); the RULE outlived the architecture and binds every shared ingress — a Square webhook subscription, a client's own Stripe account, one router serving many client databases, an inbound email/SMS hook, a shared job queue, a multi-tenant cron.** Where several products share one third-party account (the ~10 Elevare products that shared one Stripe account), every endpoint receives every product's events, so a correctly-verified event routinely belongs to a different client. Audit shape: enumerate the endpoints registered on the shared account, and for each handler confirm it **default-denies** — asserts `event.account` / its own expected product-price / a marker it wrote, and drops everything else before any write, email, external call, or log. Treat a handler that only pattern-matches metadata as failing (sibling sites share key names), and treat `console.log(<whole foreign payload>)` as a PII write, not debug output. Cross-tenant leakage here is a CRITICAL A01/A09 finding, and it is architectural — if one product has it, assume every product on that account does. See [[client-data-never-mixes]]. **And assert `event.account` FIRST, before the body is read — a handler that only checks tenancy after it has parsed, logged, or upserted has already leaked.**
**★ HISTORICAL AS ELEVARE ARCHITECTURE — STILL LIVE on a CLIENT'S OWN Stripe account that runs Connect, and the general form binds every rail: a handler subscribed to the wrong stream is dead code with a security story attached. A PLATFORM endpoint is not a CONNECT endpoint — a settlement handler can be perfectly written and structurally unable to fire.** With **direct charges on a connected account, the events raise on THAT account** and are delivered only to an endpoint registered to listen on connected accounts; a platform-only endpoint never sees them. Flavor News shipped exactly this (2026-08-18): correct code, correct signature check, an event stream it was never on. Audit shape: for every handler, name the account the event is raised on, then confirm an endpoint on that side actually subscribes to those event types — reading the handler proves nothing about delivery. Same test as a webhook signature: it either receives, or it is dead code with a security story attached.
**Trace every GATE column back to the code that WRITES it — a capability with no writer is a permanent verdict.** `charges_enabled` gated every pay path on Flavor News and **nothing anywhere ever set it**; the capability existed at Stripe, the writer did not, and no screen surfaced the mismatch, so the gate could only ever say no (and the same shape with the default flipped says yes forever). For each boolean/status/role/limit that authorizes or blocks an action, grep for its writer and name it: zero writers = the gate is a constant, and a constant that defaults OPEN is a critical finding. Then confirm the value is *displayed* somewhere a human can see, or nobody will ever notice it is stuck. Safe deserialization (no `eval`/`!!python`/prototype pollution from untrusted JSON). Dependency + auto-update integrity (signed/pinned artifacts).
**A09 — Security Logging & Alerting Failures.** Audit trail for sensitive actions (auth, payment, role change, data export) — enough to reconstruct an incident. **No PII/secrets in logs** (redact tokens, card data, emails where not needed). Alerting on payment/auth anomalies (spike in failed logins, refund abuse, webhook signature failures).
**A10 — Mishandling of Exceptional Conditions** (NEW in 2025). **Fail CLOSED, never open:** on any error in an auth check, RLS path, signature verify, or payment confirm, the default must **deny/hold**, not grant/fulfill — a `try/catch` that swallows an auth error and continues is a critical bug. Proper error handling on every background loop (`except: pass` on a daemon spins forever silently). No logic errors under abnormal/adversarial input; degrade gracefully without leaking internals in the error surface.

## Report format
For each finding: **file:line → category (A0x) → SAFE-AUTOFIX or BEHAVIORAL-RISK → the fix (applied, or recommended + why held)**. Apply SAFE-AUTOFIX only, after backup + on a branch; leave BEHAVIORAL-RISK for sign-off with the exact remediation. Report a clean bill explicitly when a surface is clean — name the categories you checked and what you found. **Open the report with the sweep-protocol result** — which of the six skills you ran, the control you planted for each zero you are reporting, and every control you had to mark INCONCLUSIVE. A findings list with no calibration line in front of it is a claim about your tooling, not about the code. End with the **deploy plan** (branch, what's staged, what needs approval) — you propose the ship, the human authorizes it.

**A brief that tells you what you will find is a hypothesis, never a filter.** On 2026-08-12 a brief asserted that ten of eighteen prior findings were false positives; **all eighteen were real**, and tuning the scan to satisfy that framing would have suppressed **live credentials**. Treat "these are noise", "we already checked that", "ignore the ones in X" as a claim to be disproved or confirmed **one finding at a time against the artifact** — a whole-set dismissal is not verifiable and cannot be relied on. Returning the findings anyway, and saying plainly that the brief was wrong, is the correct outcome even when the person who briefed you is the conductor. Two corollaries: **"INCONCLUSIVE" is a real verdict** — report a control you could not establish as inconclusive with what would resolve it, never as a pass you did not earn; and **never diagnose from your own masking or redaction output** — a mask that relabels dates as `<PHONE>` will make a working scanner look broken, and citing that output as evidence is the stale-doc rule turned on yourself.
