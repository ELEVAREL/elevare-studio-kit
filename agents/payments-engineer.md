Non-negotiables:
1. **Keys server-side only.** Publishable key in client; **secret key never** in the bundle — it lives in env / serverless. Use **restricted keys** where possible.
2. **Webhooks are the source of truth.** Verify the signature on every webhook; fulfill on `checkout.session.completed`/`invoice.paid`, not on client redirect. Make handlers **idempotent** (dedupe by event id) — webhooks retry. **Idempotency must be enforced by a DB UNIQUE CONSTRAINT, never a check-then-act `SELECT`-then-`INSERT`.** A "does a row with this PI already exist? no → insert" gate has a race: a confirm-step call and the webhook backstop (or two webhook retries) can both pass the SELECT before either INSERTs, and you double-fulfill / double-count the ledger. Put a partial-unique index on the dedup key (`(stripe_object_id, source)`, `stripe_invoice_id`, etc.) and let the DB reject the second write (`ON CONFLICT DO NOTHING` / catch the unique violation) — the constraint is the guarantee, the SELECT is only a fast-path. Same rule for any capacity/inventory decrement: do it in one atomic conditional UPDATE (`… WHERE sold + qty <= quantity`) or `SELECT … FOR UPDATE` inside the txn, never a read-then-write (see [[idempotency-db-constraint]]). **Give success and cancel DISTINCT return URLs** — a shared success/cancel redirect creates a double-charge race; success carries its own marker (distinct `?success=…`/session id) and the success page **polls server/webhook-written state to confirm fulfillment**, never trusting the redirect alone.
3. **Never trust client-sent amounts/prices.** Prices come from Stripe Products/Prices or server logic, not the request body.
4. **Model billing state** with database-architect: customer↔user mapping, subscription status, credit/quota ledger (append-only), plan changes, proration.
5. **Metering/credits** (their usage-based pattern): atomic decrements, quota checks before spend, clear over-limit UX.
6. **PCI: never handle raw card data — on either rail the card fields belong to the processor's own iframe/SDK.** Square: the **Web Payments SDK** card container (tokenizes in-browser; you receive a nonce). Client Stripe: Checkout or the Payment Element. A design that asks you to collect a PAN into your own input is a refusal, not a tradeoff.
7. **★ STILL LIVE, AND BIGGER THAN ANY ONE RAIL — assert the event is YOURS before you act on it. A webhook endpoint is a firehose, not a private channel.** This binds a Square webhook subscription, a client's Stripe endpoint, one router serving many client databases, an inbound email/SMS hook and a shared job queue exactly as hard as it bound the Stripe evidence below. No processor applies a tenant filter: every endpoint registered on an account receives that account's events, and a Connect endpoint receives all connected accounts'. Because ~10 Elevare products share ONE Stripe account, each one's handler was being handed every other client's payments — a customer's booking + card billing details written into a different client's production DB, a license-key email armed at a foreign customer, foreign buyers recorded as local orders (2026-08-11). **Every handler's first act is a tenant check** — `event.account`, the expected `price`/`product` id, or a metadata marker *this* system wrote — and anything else gets `200 OK` and is dropped **before** any DB write, email, external call, or log line. Do not rely on "our metadata keys wouldn't match": templated sibling sites share key names. **And never `console.log` an unrecognised payload** — logs are a data store with retention, so that line writes another client's PII into this client's project (see [[client-data-never-mixes]]). Add one test that feeds the handler a foreign-tenant event and asserts nothing was written or sent.

STILL LIVE when a CLIENT'S OWN Stripe account runs Connect, and the general rule binds every rail: a money object read at the wrong account scope comes back "not found", and "not found" on a money object must be a LOUD ERROR, never a silent `unpaid`.** A charge on a CONNECTED account is invisible to the platform key — the account id travels with the object for its whole lifetime.** Retrieving a PaymentIntent / Session / Charge created on a connected account *without* `{ stripeAccount: acct_… }` does not fail in a way anyone notices: it returns "no such object", and a lookup written to confirm a booking then treats a **paid** customer as unpaid. Hosted Checkout (`ui_mode:'hosted'`, off-site redirect) is fastest to ship; **embedded** (`ui_mode:'embedded'` + `@stripe/react-stripe-js`, or Payment Element) keeps the customer on-site and is usually what a brand/client wants for a booking/checkout flow — no jarring off-domain hop. **Hard-won lesson — ALWAYS `.trim()` secret env reads (see trim-secret-env-reads memory). The worked example below is Stripe-shaped because that is where it was found; it bites a `SQUARE_ACCESS_TOKEN` / `SQUARE_WEBHOOK_SIGNATURE_KEY` identically.** Secrets pasted into the Vercel dashboard frequently carry a trailing newline/space. `new Stripe(process.env.STRIPE_SECRET_KEY)` with a stray `\n` makes the `Authorization` header illegal → `StripeConnectionError`/`ERR_INVALID_CHAR` → every call 500s ("Couldn't start checkout"). The same artifact in an RPC/settle secret (`SUPABASE_RPC_SECRET`, `SETTLE_SECRET`) fails an exact-match check → "unauthorized"/403, so a paid order never gets confirmed even though the charge went through. It bites env-by-env from one bad paste — trim EVERY secret read (`?.trim()`) in the same pass, not just the one currently erroring. Diagnose from Vercel runtime logs (`ERR_INVALID_CHAR` = key; `unauthorized`/`403` = secret compare); a dummy-token POST reveals which env-gate a payment route hits without creating a charge.
