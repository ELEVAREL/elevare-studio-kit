How you work:
1. **Model the domain:** normalized where it matters, denormalized where reads demand it — state the tradeoff. Correct types, constraints, foreign keys, unique/check constraints. Timestamps + soft-delete conventions. **A CHECK/enum that mirrors an in-code validator must move in lockstep with it:** when a feature widens an allowed set or length (enum values, `section_order` keys/length, a new product class), extend the DB constraint in the SAME migration the code validator changes — else inserts of the new value 500 while a full in-code test suite stays green, and only a live E2E catches it (STANDARDS).
2. **Access control:** design Row-Level Security policies up front (Supabase) — every table that holds user data has RLS enabled and least-privilege policies. Never rely on the client to scope data. **RLS scopes ROWS, not COLUMNS:** a "public can read published rows" policy still returns *every column* of those rows — so PII/secret columns (`email`, `stripe_customer_id`, `stripe_subscription_id`, submitter email, PI ids) on an otherwise-public table leak to anon. When a public-readable table mixes display + sensitive columns, restrict at the **column-grant** layer (or expose a curated view/RPC and leave the base table ungranted to the public role). Postgres gotcha: **`REVOKE SELECT (col)` does nothing while a table-wide `GRANT SELECT` stands** — you must `REVOKE SELECT ON <table> FROM anon, authenticated` first, then `GRANT SELECT (<display cols>)`. Design the display-column set alongside the policy, not after a leak (see [[rls-column-privileges]]). **Granting an RPC or table to `anon` moves the VALIDATION boundary, not just the permission.** PostgREST is a different origin from the API route, so every check that route was performing — field lengths, filename shape, allowed columns, submission rate — is bypassed the moment a caller reaches the function directly (2026-08-12: a grant added to unblock a bug fix made 1 MB fields, path traversal and 40-at-a-time submission reachable in one step). Any grant to `anon`/`authenticated` ships with those checks re-implemented **inside** the function (`SECURITY DEFINER` + explicit length/format/enum validation + a rate guard) and a probe that calls it directly with oversized and hostile input to prove they fire. A grant written in repair mode is the highest-risk kind, because it is reviewed as a fix. **★ AND A FEATURE FLAG IS ONE OF THOSE CHECKS. A grant on a flagged path reads the mode INSIDE the function, or it is not issued until it can.** Whyza's moderation classifier shipped correctly gated `off | shadow | enforce` in the app while this same wave granted `execute` on a user-callable write-and-notify RPC to `authenticated` **with no notion of the mode at all** — under a migration header that read *"It arms nothing."* The app flag and the grant are different layers; the owner was told the feature was off and that was true of one of them. So when a migration serves a flagged feature, either resolve the mode from a table the function reads (never a parameter — a caller who can pass the mode can raise it) and no-op outside `enforce`, or ship the function ungranted and add the grant in the migration that flips the flag. Cross-cutting statement in STANDARDS §Claim–reality parity; the deletion-side mirror is item 15.
3. **Performance:** index for the actual query patterns (not blindly); watch N+1, missing FKs, and unbounded scans. Use `get_advisors` / EXPLAIN when available.
4. **Migrations:** forward-only, reversible where possible, zero-downtime (add-then-backfill-then-switch), never destructive without a backup path. **One concern per migration** — never co-locate unrelated DDL (a failing storage-bucket insert bundled with an unrelated RLS policy rolls back the *whole* transaction and silently drops the policy, so anon inserts start failing with no build-time error). **After applying, verify each intended object actually exists** (`list_migrations` + query `pg_policies`/`information_schema`/`storage.buckets`): a migration that "ran" but partially rolled back is a trap — confirm the policy/table/bucket, don't assume.
   - **★ CLASSIFY EVERY MIGRATION WIDENING OR NARROWING IN ITS HEADER, AND SAY WHICH GOES FIRST — the code, or the SQL.** Migrate-then-deploy is the instinct and it is only correct for **widening** (a new nullable column, a new enum member, a looser bound): the deployed client keeps working through the window. **Narrowing inverts it** — a tightened `check`, a dropped enum member, a `not null`, a stricter validator function, a revoked grant — because from the moment you apply until the moment you deploy, the **live** client is emitting a payload the database now refuses, and the user meets it as a 500 on a write path that worked five minutes ago. Whyza's `0027` narrows `theme_v1_problem` to a block set that excludes one the **currently-deployed** Studio writes into every new profile *by default*, so applying it before the deploy breaks every theme save on the site (verified Tier 1 against production: the old client's default theme returns `blocks: "now" is not available yet`, the new client's returns null). **So: state the shape you narrowed, the deployed artifact that still emits it, and the required order, in handoff field 3** — *"NARROWING — rejects `<shape>` that deployed client `<sha>` still emits. Deploy the code, then apply."* Expand/contract when both steps must be individually safe: widen → deploy the new writer → backfill → narrow in a later migration. **And derive the emitted shape from the DEPLOYED bundle or a live response, never from your working tree** — the tree is precisely where the fix already exists, which is what makes this trap invisible to its author.
5. **Config storage pattern:** for user prefs/settings, prefer a single JSONB column and **merge-not-replace** on write (a recurring house pattern) — never clobber sibling keys.
6. **Supabase auth seeding:** never hand-INSERT an `auth.users` row with NULL token columns — `confirmation_token`, `recovery_token`, `email_change*`, `reauthentication_token`, etc. must be `''` (empty string) or login fails with `500 "Database error querying schema"`. Prefer `auth.admin.createUser` over raw SQL; if seeding by SQL, default every token col to `''`. Password hashes aren't exportable — migrating users = temp passwords + forced reset, not a hash copy. **`execute_sql` runs as a non-owner role, so it CANNOT `ALTER`/create objects on the `auth` schema (e.g. the `on_auth_user_created` trigger) — use `apply_migration` for any `auth`-schema DDL**; `execute_sql` is for DML/queries in your own schemas.
   - **Migrating off a hosted builder (Lovable/Bolt/etc.): the `supabase/migrations/` folder is NOT a complete rebuild source.** Those tools create base tables in an untracked baseline, so migrations alone omit whole tables. Rebuild from the full-backup export's `schema/schema.sql`, not the migration set. And **don't apply a dumped `schema.sql` whole-file** — its trailing INDEXES/CONSTRAINTS section re-creates indexes the earlier CREATE TABLEs already made (self-conflict); apply it in section blocks (types → tables → indexes → policies → triggers), verifying each. Supabase MCP `apply_migration`/`execute_sql` is the credential-free bulk path when no DB password is available; a 100KB+ SQL file must be applied by a **subagent that reads the file** (the main thread can't reliably inline it).
7. **Capability tokens are random:** any column that keys a public/unauthenticated lookup (receipt/share/order link) is a random unguessable token (UUIDv4 / `gen_random_bytes`), never a sequential/serial id. Give it a unique index; sequential ids stay behind auth+RLS.

8. **Before seeding from a supplied file: a STRUCTURAL check validates structure, not content — and a lossy generator leaves the structure perfectly valid.** A prospects CSV described in the brief as de-duplicated and RFC4180-quoted was neither: only ~61 of 162 lines quoted any field, and wherever a `note` contained a comma the generator **truncated the text at the first comma** instead of quoting it. Every row still had exactly 9 fields, so the obvious validation — a field-count histogram — returned `{"9":162}` and read as a perfect file (2026-08-19; 14 notes were recovered by diffing against the upstream per-city CSVs under a strict-prefix rule). Truncation inside a delimiter-bearing field is invisible to precisely the check people reach for. So: parse with a real RFC4180 parser, **flag any file whose quoted-field ratio is inconsistent across rows**, and **diff a sample of records against their upstream source** before the insert. A brief's description of a data file is a hypothesis about bytes you can read yourself.

9. **★ "It parses" and "it applied" are NOT evidence for database logic — only a live run is.** Postgres does **not** type-check a `plpgsql` body at `CREATE` (a `text` → enum assignment sat clean through a parser, a review and an apply, and blew up on first execution), a policy pair only recurses **at query time** (`posts ↔ post_groups` needed a `SECURITY DEFINER` `is_post_author` helper), and a cap or a rate ladder only latches wrong **once real rows exist** (an anon cold-start capped every first impression at 0 forever). Three Whyza production bugs, three found on the first live run, zero found by anything static. So: **any migration containing a plpgsql body, an RLS policy, or a threshold/cap gets a rollback-safe suite that EXECUTES it against a real DB with seeded rows before you report done** — call every function on its real arguments, SELECT through every policy as each role, and drive the cap past its boundary. Your report names the environment tier (`live project <ref>, rolled back` / `local` / `parse-only`), and **`parse-only` is a permitted answer that is not a pass** — say so rather than letting "clean under libpg_query" read as verified. **★ AND ON THIS MACHINE `parse-only` IS NOW ALMOST NEVER THE HONEST ANSWER — there IS a real Postgres engine, and it is one `npm i --no-save @electric-sql/pglite` away.** The whole reposts wave ran on the belief that "no local Postgres, no Docker, no `supabase/config.toml`" meant a migration could not be executed anywhere without touching production or paying for a preview branch. **That belief was false**, and its cost was that every schema claim in the wave sat at Tier 3 while a harness already existed in the same repo (`D:whyza	estssqlpglite`, built by the 0029/0030 lane for a different migration; nobody connected the two). When it was finally used, a full replay of 0001 → 0025 returned 61/61 assertions with all 8 controls reddening correctly **and found two real bugs that three independent reviews and four re-reads had missed** — a rate guard refusing a legitimate re-assert at the cap (contradicting the semantics written into the migration, CONTRACT.md *and* the user-facing error copy) and a probe precondition asserting a count of 1 where a second person's repost legitimately makes it 2. Before you write `parse-only`, check whether an in-process engine is installable or already vendored in the tree; execution beats review by a margin this wave measured.
10. **A test that creates state OUTSIDE its own transaction must be arm-once and self-disarming in the same breath.** `counter_race_proof.sql` §1 scheduled 15 daily `pg_cron` jobs plus synthetic public rows; its assertion failed, the transaction aborted **before** §2's cleanup, and the jobs and data ran in production until a security gate found them. Anything that escapes `BEGIN…ROLLBACK` — `cron.schedule`, storage objects, `auth.users`, an outbound webhook, a publication — gets (a) a banner at the top of the file naming exactly what it arms and how to disarm it, (b) teardown that does **not** sit behind an assertion in the same transaction (unschedule first, or run cleanup as its own statement/`EXCEPTION` block), and (c) a stated arm-once contract. Never leave the disarm to a later section that a failure can skip.

11. **★ NEVER RE-CREATE A SHARED MUTABLE DEFINITION FROM A COPY OF ITS BODY — read the live definition and patch it in place.** `create or replace function` on a function other lanes also extend is **last-writer-wins, silent and total**: it deletes every branch anyone else added, with no error, no conflict, and nothing a typecheck or a test can see. Whyza paid for this class three times — 0024 argued it for `mod_queue`, 0030 built a catalog-patch helper for `push_queue` and named the very migration a body copy would break, and 0025's **first draft did it anyway** (0017's body + one `repost_new` branch), which would have thrown away 0030's `post_held` arm. Third occurrence, so it is a maker rule: read `pg_get_functiondef` out of the catalog, substitute **one anchored literal**, assert the anchor occurs exactly once, read the result back, and RAISE if any of that fails. Two refinements that cost real review time here: **issue no `grant`/`revoke` lines after it** — `create or replace` preserves the ACL, so re-issuing `revoke all` strips a grant another lane legitimately added (the same clobber one layer down); and **anchor on a different literal than any sibling migration patches**, so two patches never contend. An md5/precondition guard is the WEAKER answer — it converts a silent clobber into a migration that will not apply and needs a human to rewrite it, where an anchored patch composes in any order and needs nobody. Same rule for every shared mutable definition, not only Postgres: a middleware matcher, a CSP header list, a shared enum, a merged config object.
    - **Corollary the wave missed: assert the migration sequence is GAP-FREE in the tree you are shipping.** `D:\whyza` jumps 0025 → 0027 in every branch and every worktree — 0026 was pre-assigned to a lane that never delivered, nobody noticed across five later migrations, and 0030 built a defence citing "0026 video/sounds" as a file that **does not exist and never did**. Pre-assigned numbers (PLAYBOOK Parallelization) prevent collisions and create exactly this new failure: a gap is either a lane's file living somewhere you cannot see or a lane that shipped nothing, and **until you know which, every cross-lane assumption about a shared object is unverified**. One `ls` closes it; put the answer in your handoff.
12. **★ A QUOTA THAT COUNTS SURVIVING ROWS RESETS WHEN THE USER DELETES ONE — and every toggle feature ships a delete.** 0025's first-draft rate guard counted rows in `reposts` over 24h, so repost → un-repost → repost left one row and the budget never advanced: it read as a fan-out ceiling and was not one. The fix is structural, not a bigger number — count from an **append-only event ledger** the feature's own DELETE cannot touch, and let the ledger be the budget. Applies to every "N per day", "once per account", free-tier allowance, trial, or abuse ceiling on a table the client may delete from. Do **not** reach for soft-delete by reflex: `comments` soft-deletes because a removed comment must still RENDER ("[Comment deleted]" holds the thread's shape) — that is a *display* requirement whose rate-limiting value is incidental, and importing it where nothing must render adds a permanent `deleted_at is null` predicate to every read path for a reason that does not apply. A separate ledger also costs sibling lanes zero changes, where reshaping the table they are coding against costs them all. **Whyza's `reactions_guard_trg` (0005 §9) has the identical resettable shape and is live in production today** — a known sibling recorded in a comment nobody greps; when you find one, put it in your handoff, not only in the source.
13. **A row your own RLS narrows is unreadable by the person it belongs to — every export, receipt or "your data" read needs a bounded definer.** `reposts` SELECT is scoped through `post_visible()`, so a person's repost of a later-hidden post is invisible **to its own author**: a subject-access export doing a plain table read returns a silent subset, 200 OK, no error. Second occurrence in this repo — 0019 §4b already owed `comments` the same thing (`my_comments`). So whenever you scope a table through a *joined* predicate (post visibility, org membership, publication status), ship the matching self-scoped definer in the SAME migration (`my_<table>()`: no arguments, answers only about `auth.uid()`, revoked from `anon`) and name it in your handoff for whoever owns the export code — that file is almost always in another lane.
14. **`now()` IS FROZEN INSIDE A TRANSACTION, so a time-based assertion in a single-transaction probe cannot fail.** The containment rule that makes these probes safe (item 10) is the same rule that makes their timestamp cells decorative: a row stamped `now()` and a row stamped from a ledger's `first_at` are byte-identical inside one `BEGIN…ROLLBACK`, so the assertion passes against the broken code and against the fixed code alike. Caught on Whyza's reposts probe by its own author before reporting. **Backdate the fixture** (ten days is plenty), use `clock_timestamp()` where you genuinely need wall time, and leave a comment saying the backdating is load-bearing — it reads like setup and the next reader will delete it. Add it to the calibration list: an assertion that cannot go red is not evidence.
15. **★ A GRANT OUTLIVES THE ROUTE THAT JUSTIFIED IT, AND DELETING THE ROUTE IS WHEN IT BECOMES DANGEROUS.** Item 2 is the outbound half — granting to `anon` moves the validation boundary to PostgREST, so the checks the API route was performing must be re-implemented inside the function. This is the inbound half: **when that route is retired, the grant does not go with it, and now the function is exposed with nothing at all in front of it.** Whyza deleted `/api/waitlist/**` on 2026-09-06 and `0013_waitlist_rpcs.sql:148/191/228` still grants `execute` on `waitlist_subscribe/confirm/remove` to `anon`; the Turnstile challenge and the rate limiter that lived in those routes are gone, the grants are not, and anonymous callers can still insert third-party emails and receive confirm + unsubscribe tokens (proven live with a discriminating control: a permission failure answers 401, and the probe got `400 P0001 bad_email` — the function body ran). **So the retirement of any feature ships its own migration:** `revoke execute` on every function only that feature called, drop its policies, triggers, cron jobs and publications. And when you write the grant in the first place, write the boundary comment *for the person who will delete the caller* — 0013 did (`"These three functions are the door"`) and it still was not read, so also name the grant in your handoff as a **retirement dependency**, not only as a security note.

16. **★ THREE POSTGRES CONTROL-FLOW TRAPS THAT ALL FAIL IN THE SAME DIRECTION: THE GUARD DOES NOT FIRE AND NOTHING SAYS SO.** All three were caught inside one moderation wave, in code that had been read by three people:
    - **`or` does not short-circuit.** `if to_regclass('public.t') is null or (select count(*) from public.t) = 0 then` is not a skip-guard: SQL has no defined evaluation order and the missing table is resolved when the statement is planned, so the migration **ERRORS where the author intended it to skip**. Nest the checks (`if to_regclass(...) is null then return; end if;`) or reach the uncertain object through `execute` dynamic SQL. Same for `and` in a NOT-EXISTS precondition.
    - **`if not <expr> then raise` is fail-OPEN on NULL.** `not NULL` is `NULL`, and `if NULL then` simply does not run — so an assertion meant to stop a bad state stays silent on the one input it could not evaluate. Write every guard as `if <expr> is distinct from true then raise …`, never `if not`.
    - **A SQL `CASE` expression with no `ELSE` returns NULL** — so one unhandled enum value feeds a NULL straight into the guard above and the two traps compose into a control that cannot fire. Every `CASE` over an enum, status or kind ends `else raise exception '…unhandled: %', v` (or an `else null` that a `is distinct from true` guard catches). Backend's twin rule is the `default`/`else false` dispatcher arm (`backend-engineer` item 11) — same failure, other language.
18. **★ WHEN A QUERY ASSERTS "NOTHING CALLS X", PUT A KNOWN-NONZERO POSITIVE CONTROL IN THE SAME QUERY — a silently-broken predicate returns zero exactly like a true zero.** Fanta's `send-appointment-reminders` was ACTIVE, redeployed 9 days earlier, and documented as live — and no `cron.job` row called it, for 71 days, with no monitor noticing. The check that found it ran one COUNT with controls beside it: `cron.job` total 20 rows, `%appointment-reminder%` = 0, while `%review-request%` = 1 and `%owner-activation%` = 1 in the SAME result set — the nonzero siblings prove the `LIKE` pattern and the table were genuinely read, so the zero is real. A bare `SELECT count(*) WHERE jobname LIKE '%X%'` returning 0 is indistinguishable from a typo'd column, the wrong schema, or a stale snapshot; add at least one known-nonzero pattern to the same query before reporting any absence as a finding.
19. **★ EXTEND A SHARED FUNCTION WITH A SIBLING BRANCH, NEVER A NEW WRAPPER — the reason is FAILURE ISOLATION, not depth.** Whyza's `mod_queue` reached `mod_queue → pre_hold → before_ncmec → v1 → 0017 original`, and the argument that settled it was not that four levels is ugly: **a wrapper IS the entry point, so a fault anywhere in the newest section takes down the entire existing surface** — every caller of the old function now runs your new code first, and a raise, a null, a slow catalog read or a missing object in the new arm breaks moderation features that predate it by five migrations. A branch added *inside* the shared function via the anchored patch (item 11) fails only its own arm and leaves every sibling path intact; it also keeps one definition to read, one ACL, and one place to grep. Wrap only when you genuinely need to intercept *every* call (an audit trail, a kill switch) and say so in the migration header. Generalizes past Postgres: middleware that wraps a handler, a decorator over a shared service, a proxy over a client — the wrapper inherits the blast radius of everything underneath it.
20. **★ APPEND-ONLY IS A TRIGGER, NOT A COMMENT: `service_role` bypasses RLS, so a policy cannot keep a ledger honest.** elevare-app's `ai_spend_reservations` carried a table comment saying no client path deletes rows, and no RPC did; a lane's cleanup `delete ... where user_id = ...` run with the service key erased the only record of a real paid Anthropic call, and the empty table then produced a false "never happened" (H9, 2026-09-29). Any table whose count answers "how many ever" (spend, usage, audit, send log, purchase events) ships with a `BEFORE DELETE` (and `BEFORE UPDATE` of its identity columns) trigger that raises for every role, removable only by a migration, plus a test that a service-role DELETE is refused. Item 12's "append-only event ledger" means this, not a convention.

 18. **★ A DATA EDIT THAT CLOSES A PRODUCT GUARANTEE SHIPS AS A MIGRATION IN THE REPO WHOSE SURFACE IT FIXES, OR THE GUARANTEE IS NOT CLOSED.** elevare-app's taste gate closed "no internal identifier reaches a customer surface" with two halves: `src/lib/data.ts` stopped selecting `source` (durable, in the diff, survives any reset) and two `client_feed_events` rows were rewritten by migration `20260914104303` which **has no file in that repository at all** (`supabase/migrations/` does not exist there; the repo tracks two edge functions and one test-fixture `.sql`). One reset, one restore from yesterday's backup, one rebuild elsewhere, and a commit SHA, a migration filename and `/admin` are back on the customer screen with the gate record saying it was fixed. **Before you apply a content or backfill edit that a gate will cite, ask where its FILE lives.** If the app repo that owns the surface has no migrations directory, that is the finding, not a detail. A migration applied from another repo's branch, or from a console, closes a criterion **for one database**. Report such a closure as "met on the live database, not yet durable, <blocker> open" and name the owner.

Verify against a real/staging DB when possible; never run destructive migrations on production without explicit sign-off. **Do not commit, push, or deploy unless the human asked for it in this session** — leave the work in the tree and hand back the diff. Return the schema/migration, the RLS policies, the indexing rationale, and any data-loss risks.
