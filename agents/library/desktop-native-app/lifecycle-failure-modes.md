# Long-running processes & failure modes

> **Extracted from `STANDARDS.md`.** Moved out of `STANDARDS.md` on 2026-09-06. Measured across all 80 agent definitions, 18 of
> them do work involving a daemon, installer, packaged app, child process or media pipeline;
> the other 62 were carrying 4.5 KB they never use.
> These rules are unchanged and still binding on the work they cover.

Learned from a "gates-passed" NVR engine that still shipped 6 blockers — all process-lifecycle bugs the happy-path QA never touched (leaked ffmpeg children on quit, a retention pruner that deleted *all* footage, a dead recorder thread that still reported "running", an auto-updater that could never succeed). Happy-path green is not shippable-green for anything with a lifecycle.
- **Every shippable engine/daemon ships a log file from day one — not "add logging later".** No-logging turned a frozen-app crash (an eager `matplotlib` import) into a multi-hour blind hunt and would have hidden every lifecycle bug too. Wire a rotating file logger to `%APPDATA%`/data-dir at first boot; log start/stop, every spawned child PID, every thread's health, and every caught exception (never `except: pass` on a background loop — a silently-swallowed error makes an AI/recorder loop spin forever doing nothing).
- **Child processes are owned, supervised, and reaped.** Anything that spawns `ffmpeg`/`go2rtc`/a helper must: track the PID, kill it on parent quit (register an `atexit`/signal handler — don't leak it), kill strays from a crashed prior parent on start, and restart-or-surface it if it dies. A spawned child with no owner is a leak and a "still running" lie.
- **Liveness must be measured, not assumed.** A "running/OK/All clear" status must reflect a real health probe (thread alive? last-frame timestamp recent? child PID responding?), never a flag set once at startup. A dead recorder reporting "running", or "All clear" while the AI thread is dead, is worse than an error — it hides the failure.
- **An action the product offers must be able to succeed.** Before shipping a self-update/export/download/backup path, run it once end-to-end on the real artifact — an auto-updater that downloads and self-replaces must actually complete against a real release, or it's a dead button that erodes trust. Never ship an affordance you haven't watched succeed.
- **Exit codes are a contract with the supervisor: a benign no-op exits 0.** Any CLI a timer/cron/systemd unit re-runs must treat "already done today / nothing to do" as success — a daily-report command that exits 1 on already-sent makes every legitimate manual run turn the scheduled unit red, and a monitoring surface that cries wolf trains its owner to ignore real failures. Reserve nonzero for outcomes a supervisor should alert on.
- **Test the destructive/adversarial lifecycle, not just the flow:** kill it mid-run (does it corrupt/leak/orphan?), fill the disk (does retention delete the right thing or everything?), unplug the camera / pull the network (does it degrade or spin?), restart it (does state survive?). This FAILURE-MODE pass is a required gate for any long-running product — see qa-verifier and the PLAYBOOK gate list.
- **Verify the artifact you SHIP, not a proxy — and a GUI must be proven to RENDER a window in its frozen form.** A `--selfcheck`/headless smoke (which boots the engine and hits an API) is NOT acceptance for a GUI app: SentinelBox v1.1.0 shipped "verified" because every gate ran `SentinelBox.exe --selfcheck` and NO ONE ever ran the shippable installer — the frozen app and installer both launched but never rendered a window (silent hang), because PyInstaller dropped pywebview's WebView2 backend DLLs (`webview/lib/*.dll`). The exact binary a user downloads must be run **end-to-end at least once** before ship: for a desktop installer that means **launch Setup.exe → confirm a window renders → complete the install → launch the installed app → confirm ITS window renders → uninstall.** Frozen GUI backends (pywebview/WebView2, Qt, Electron) commonly lose runtime assets that dev mode has on PATH — a process that starts is not a window that shows; require a post-build window-render smoke check, not just "the exe launched."
- **Frozen-build asset completeness:** when packaging, GUI backend native libs/plugins (WebView2 DLLs, Qt platform plugins, Electron resources) must be **explicitly verified present in the bundle** — `collect_all`/collectors silently drop non-linked DLLs, so "collect_all(webview) is in the spec" ≠ "the DLLs are in dist." After every build, assert the expected backend files exist in the output tree (e.g. a `verify_build.py` that checks `webview/lib/*.dll` are present AND launches the frozen exe to confirm a visible window appears), and fail the build if not.
