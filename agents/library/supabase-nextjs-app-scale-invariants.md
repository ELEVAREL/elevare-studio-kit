# Supabase + Next.js (app-scale) — non-negotiables

> **Extracted from `STANDARDS.md`.** Moved out of `STANDARDS.md` on 2026-09-06 because STANDARDS is injected into all 80 agents
> and this section is needed by roughly 17 of them — every music, Temptation, marketing and
> exec agent was carrying 16 KB of Supabase invariants it can never use.
> These rules are unchanged and still binding on the work they cover.

Learned from a build where each of these shipped as a defect and was caught only by a late sweep. Check them *while building*, not at the gate.
- **One browser client, singleton.** `createBrowserClient()` must be created **once** and reused (module-level singleton). Multiple instances race on refresh-token rotation and produce random `401 "permission denied"` on authenticated writes. Never `createBrowserClient()` inside a component/hook body.
- **Seed `auth.users` with `''`, not NULL, for token columns.** A hand-inserted `auth.users` row must set `confirmation_token`, `recovery_token`, `email_change`, `email_change_token_new/current`, `reauthentication_token`, etc. to **empty string**, not NULL — GoTrue scans these and NULL throws `500 "Database error querying schema"` at login. Prefer the Admin API (`auth.admin.createUser`) over raw INSERT; if seeding by SQL, set every token col to `''`.
- **Capability tokens are RANDOM, never sequential.** Any public/unauthenticated lookup URL (receipt, order, share link) must be keyed by an **unguessable random token** (UUIDv4 / `gen_random_bytes`), never a sequential id (`R01001…`) — a sequential id is an enumerable PII leak. Sequential ids are fine only behind auth+RLS.
- **An anon/guest-session table's RLS is the ONLY gate — and `user_id IS NULL` in a SELECT policy is a public dump.** Supabase grants `anon` table privileges by default, so a capability-token/guest-session table with `USING (user_id = auth.uid() OR user_id IS NULL)` lets anyone holding the public anon key hit PostgREST directly (`?user_id=is.null&select=session_token,...`) and read EVERY guest's token + PII — an in-route `session_token`/owner check can't help because the attacker bypasses the app. Read/write anon-session tables through a **service-role client** (the in-code check becomes the real gate), then lock the base table: drop the anon policies, owner-only `USING (user_id IS NOT NULL AND user_id = auth.uid())`, `REVOKE ALL … FROM anon, authenticated`. Deploy the service-role routes BEFORE the RLS lockdown (reversing it 404s in-flight guest sessions). This was a CRITICAL LIVE leak on launch_kit/site_builder — see [[anon-rls-readable-session-leak]] (reusable audit query; run it on every new Supabase project before launch).
- **A PostgREST embed needs an explicit FK hint the moment two tables have more than one relationship — and the failure is an HTTP 300, not a 400.** `profiles?select=id,posts!inner(id)` answered **HTTP 300 `PGRST201`** on Whyza because `profiles`↔`posts` has three relationships: the author FK plus two many-to-many paths through `reactions` and `saves`. Only `posts!posts_author_id_fkey!inner(...)` resolves. It compiles, it typechecks, and it is a runtime 300 that most error handling treats as "not an error" — and the count you were reading (`Prefer: count=exact`) silently never arrives. **Name the constraint in every embed on a table that any junction table also references**, and verify the count against a real query, not against the request succeeding. Adding a new junction table *breaks existing embeds elsewhere in the app* — list that in the "Breaks / invalidates" field of your handoff.
- **Money dashboards use shop-local CALENDAR boundaries, not rolling UTC.** "Today / This week / This month" totals must be computed against the shop's configured timezone's calendar day/week boundaries, not a rolling `now - 24h`/UTC window — otherwise the headline numbers are wrong for any non-UTC shop.
- **CSV export guards against formula injection.** Quoting alone does NOT stop spreadsheet formula injection. Prefix any owner/user-typed cell that begins with `= + - @` (also tab/CR) with a leading `'` (or space) before writing CSV. Applies to every exported field, not just obvious ones.
- **Cross-boundary errors carry a machine `code`; UI branches on the code, never on the message copy.** When one agent's API/RPC returns an error and another agent's UI must react to a *specific* case ("slot too soon", "already booked", "sold out"), the API must return a stable machine identifier (`{ code: "SLOT_TOO_SOON" }`) and the UI must switch on that code. A UI that regex-matches the human/translated error *message* ("too soon") is a silent contract seam that a green build hides — it breaks the instant the copy is reworded, translated, or i18n'd, and no compiler catches it. Pin the error-code enum in the cross-agent contract exactly like request/response shapes (see [[parallel-wave-contract-seams]]).
- **★ HISTORICAL RECORD — the Connect registry-row recipe. DO NOT BUILD FROM IT; the four rules beneath it are still live and are why it stays.** Stripe **permanently revoked** Elevare's PLATFORM capability on 2026-08-21 for aggregation (appeal denied, final) and Elevare can never open another, so there is no Connect app, no connected account and no `application_fee_amount`. **Precision matters, because the loose phrasing "the account was closed" has already produced wrong answers.** What died TECHNICALLY is aggregation on behalf of others; the Stripe ACCOUNT itself was still able to take direct charges as of 2026-09-05 (live API, [[fanta-stripe-split-is-manual]]), and Square forbids aggregation just as explicitly. **But as of 2026-09-06 that is history, not an option: by owner decision Stripe is DEAD as Elevare's own payment rail and Square is the live rail.** Their bot offered a fresh account if this one is closed first — do not. The denial was structural, the fee model has since changed to billed-not-skimmed, and Square is ACTIVE. Reapplying trades a working rail for an uncertain one on the same entity. **Do not reapply, do not open a second account, never route Elevare revenue through Stripe.** Clients keep their own Stripe accounts; those are unaffected and stay separate. The fee is now **INVOICED**: 10% on deposits/bookings and 5% on everything else, both rates on the same client per transaction type, **billed monthly in arrears, never deducted** *(model settled 2026-08-30; authority [BUSINESS-PLAN.md](BUSINESS-PLAN.md) §2 and memory [[elevare-operating-model]])*. What the rule *said*, kept only so the sub-rules have their context: onboarding a Connect client was a REGISTRY ROW, never a new integration — insert a row in `app_private.connect_settlement` + `platform_clients` and the **central router** at `elevarestudio.co/api/stripe/connect-webhook` did the rest (`syncPlatformClientStatus` on `account.updated` / `capability.updated` kept `charges_enabled` fresh for every client at once); there was no per-client webhook step, because a platform *cannot* create account-level webhooks on a Standard connected account. **None of that is executable today.** [[stripe-connect-blueprint]] is the history, not a build guide.
  - **★ STILL LIVE, AND BIGGER THAN STRIPE — this rule outlived the architecture that taught it. Treat EVERY endpoint on a shared account, router, or queue as a firehose, not a private channel.** A webhook endpoint has no per-tenant filter: a Connect endpoint delivers every connected account's events to whatever URL it points at, and an *account-level* endpoint on a shared platform account delivers every product's events to every endpoint registered on it. Both were live here: ~10 client products each registered their own account-level endpoint on the ONE Elevare Stripe account, so each client's system received every other client's payment data — a Fanta customer's booking + card billing details landed in Thames Coast's production DB, SentinelBox was armed to email a license key to another client's customer, elevare-studio booked foreign buyers as its own orders (2026-08-11, all remediated). Not one handler checked `event.account`. **The rule is DEFAULT-DENY on tenant identity: every handler asserts the event is its own — `event.account` / the expected product or price id / a tenant marker it wrote itself — and returns 200-and-ignores anything else, BEFORE it reads a body, writes a row, sends mail, or logs.** A handler that acts because the payload merely *looked* familiar is relying on a UUID miss, and templated sibling sites share metadata key names, so the miss is not reliable. This is architectural, not a bug list: one shared ingress plus no tenant assertion means every new client inherits the defect. **The Stripe details above are the evidence; the rule is the general one** — it binds any shared entry point that fans out to many tenants: a Square webhook, one router serving many client databases, an inbound email/SMS hook, a shared job queue, a realtime channel, a multi-tenant cron. Elevare now reads every client's earnings out of per-client databases through studio-held credentials, which is exactly the shape this defect lives in, so the assertion is *more* load-bearing under the invoiced model than it was under Connect. See [[client-data-never-mixes]].
  - **STILL LIVE: never build bespoke per-client infrastructure to do what a shared path already does.** ProCraft VA shipped a bespoke `stripe-connect` edge function doing its own `accounts.retrieve` with its own `STRIPE_SECRET_KEY`; it broke ("Failed to send a request to the Edge Function") and blocked the client from taking any card payment. A config row cannot be un-deployed or lose its secret; a per-client function can do both. **Before standing up infrastructure for one client, diff your plan against what the other clients actually do live** — if you are adding a deployable rather than a row, stop and justify it.
  - **STILL LIVE:** never show a client "connected" without data backing it. A row kept fresh by the shared path is as good as a live retrieve and needs no per-client key. A "connected" state that is not backed by real data is the lie that puts a customer in front of a Pay button that cannot charge. (Same family as claim–reality parity and measured liveness, above.)
  - **STILL LIVE: a client's rate is set once, by hand, at onboarding — no sync path may derive or overwrite it, and no agent may infer one.** Rates are per client and **both apply to the same client per transaction type** (10% deposits/bookings, 5% everything else); grandfathered rates change only with that client's written sign-off. **Never generalise one client's arrangement into a rule for the others**, and never guess a rate — bill the wrong number and a real client is charged the wrong amount. [[elevare-platform-fee-pricing]] holds the per-client table; [BUSINESS-PLAN.md](BUSINESS-PLAN.md) §2 and §3 are the authority, and where the two disagree the owner settles it, not you.
- **Payments: success marker + confirming poller, never identical success/cancel URLs.** A shared success/cancel redirect URL creates a double-charge race. Give success its own marker (distinct `?success=…` param / session id) and confirm fulfillment by polling server state (webhook-written), not by trusting the redirect. (Ship-of-truth is still the webhook — see payments-engineer.)
- **Migrations are atomic — verify each object actually applied.** A migration runs in one transaction: if any statement fails, the **whole thing rolls back** and every other object in it silently vanishes. So never co-locate unrelated DDL — don't bundle a storage-bucket insert (which fails if the storage schema isn't ready) with an unrelated RLS policy; the failed bucket takes the policy with it, and anon inserts start getting blocked with no error at build time. One concern per migration, and after applying, **verify each intended policy/table/bucket actually exists** (`list_migrations` + query `pg_policies`/`information_schema`) — "the migration ran" ≠ "everything in it applied."
- **Seed-referenced asset paths must match on-disk filenames.** Seeded `image_url`/OG paths (e.g. `/placeholders/bags-totes.svg`) must point at files that actually exist on disk (`bags.svg` ≠ `bags-totes.svg`) — a drift ships broken product images and broken OG/share cards. Whoever seeds data verifies every referenced asset resolves (list `public/` and diff against the seed), and keeps slug↔filename naming in sync.
- **A route's render/cache mode is a CROSS-AGENT CONTRACT, not a local perf setting.** `force-dynamic` ↔ `revalidate`/`generateStaticParams`/`unstable_cache` decides whether the route resolves a viewer at all, so flipping it silently changes what every per-viewer prop on that page evaluates to. On Thames Coast a correct ISR restore (380ms → 3.5ms) turned a correctly-built venue-follow control's props into `undefined`, and the control — still imported, still mounted, still compiling — rendered nothing. A paid perk died with no error anywhere. Rules: (1) whoever changes a route's render mode **enumerates every viewer-dependent prop on that route and reports its new value**; (2) a component that legitimately renders nothing for an unresolved viewer says so **in its own header**, so the next reader can tell dormant from dead; (3) **never "fix" it by resolving a viewer inside a cached route** — per-viewer state in a shared cache entry is a correctness bug, not a perf trade. The legitimate fixes are a client island that renders nothing until it resolves (never the signed-out variant, which would flash "not a member" at a paying member) or a home on a surface that is already dynamic.
- **React/Next 16 effect hygiene.** Don't set state synchronously in an effect to derive a value you can compute during render (`set-state-in-effect` lint = a real bug: extra render, stale flash) — derive it in render instead. Reserve effects for genuine external sync.
- **Windows Node exit hygiene.** Don't call `process.exit()` while undici keep-alive sockets are open — it races libuv and crashes with `UV_HANDLE_CLOSING` on Windows. Let the event loop drain (close the fetch client / `undici` agent, or `process.exitCode = n` and return) instead of a hard exit.
- **A serverless route's heavy deps load lazily + `runtime = "nodejs"`.** Never static-import a native/CJS-interop dep (jsdom, isomorphic-dompurify, sharp, canvas) at route module scope for a branch that rarely runs — it crashes EVERY request to that route at module eval (`ERR_REQUIRE_ESM` on Vercel), a 500 on all paths that no build step catches. Dynamic-`import()` it inside the branch and pin `export const runtime = "nodejs"`. Confirm with a LIVE curl of the deployed route's happy + error paths (see "Verify before you claim done").
- **`.env.local` is NOT the source of production truth — and may belong to a DIFFERENT project. Neither is the VAULT ENTRY'S NAME.** A repo's `.env.local` can hold another app's keys: `elevare-studio/.env.local` held Asky's Supabase URL, app URL **and service-role key**, so any local run in the platform repo wrote to Asky's database with Asky's admin key — and all three `ELEVARE_STUDIO_*` vault entries decoded to Asky's project too (corrected 2026-08-12). **A key's label is a claim about its contents, not proof: decode it and match the project ref / account id against the live project before you use it.** A misnamed admin key is a cross-client write, not a config nit — see [[keyvault]], [[client-data-never-mixes]]. Before ANY money/DB action on an existing app (create products/prices, charge, migrate, seed), confirm the LIVE project/account via MCP — `mcp__*supabase*__list_projects` / `get_project_url` and `mcp__*stripe*__get_stripe_account_info` — never trust local `.env.local`. Prod env lives in Vercel; the account is confirmed live, not read from disk. **A migrated site's Stripe price IDs may live in a DIFFERENT Stripe account than the vault's Elevare platform key** — a `price_...` from the old build is meaningless under our platform key. Before wiring payments on an inherited/migrated site, confirm which account owns the existing price IDs (Connect-settle on that account vs. re-create under the platform key) — don't assume the vault key can see them.
- **Vercel stores env values LITERALLY — strip surrounding quotes, and use `--no-sensitive` to verify.** A `.env` line like `KEY="pk_live_..."` pushed to Vercel keeps the quotes as part of the value (breaks the key at runtime); strip wrapping quotes before `vercel env add`. `vercel env pull` masks Prod/Preview values by default (`--sensitive` is on) so pulled values look empty — verify publishable/non-secret keys with `vercel env pull --no-sensitive`. Preview-scoped vars need the git-branch argument or they don't resolve for preview deploys.
- **Widening a set/length that a DB constraint ALSO enforces = update the constraint in lockstep, and prove it with a live E2E.** Any change that grows an allowed enum/set/length also policed by a DB `CHECK`/enum/FK — a new product CLASS (`ads` fulfillment_type + category + `ads-monthly` plan label), section keys 6→11, a `section_order` max length — must extend every gating constraint (`..._category_check`, `..._fulfillment_type_check`, `subscriptions_plan_check`, the length check) in the SAME migration the code validators change, or inserts of the new value silently 500 against the old constraint. **In-code unit tests CANNOT see this drift** — they exercise the code validators you already widened, so a full green suite (e.g. 227/227) passes while the live feature fails; only a live E2E insert of the new value against the real DB catches it. Enumerate the DB constraints a widened value must satisfy, migrate them together, and run one live insert before claiming done.
