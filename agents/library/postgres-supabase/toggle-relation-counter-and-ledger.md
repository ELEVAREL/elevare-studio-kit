# Toggleable relations: the counter trigger, and the append-only ledger that must sit behind it

Two halves of one problem. **Half A** is the boring, correct way to keep a denormalized count on a
parent row. **Half B** is the defect class that Half A quietly invites, and it is the one worth
reading: *anything derived by counting the surviving rows of a relation the user can DELETE from is
resettable by a toggle.*

## When to reach for it
Any **toggle relation** — like/unlike, follow/unfollow, save/unsave, repost/un-repost, RSVP/cancel,
upvote, join/leave — where the row is an `(actor_id, subject_id)` pair the client may insert and
delete at will. Reach for Half A whenever you add a public count. Reach for Half B **the moment
anything other than a display count is derived from those rows** — a rate limit, a notification, a
ranking/engagement event, a "first time" badge, an audit trail, a quota.

---

## Half A — the denormalized counter trigger (the house shape)

A public count lives on the parent so a feed is one query and nobody reads child rows to render a
number. `security definer` + `set search_path = ''` + fully-qualified `public.` names + `greatest(x
- 1, 0)` on the way down + `revoke all` so no client role can call it directly.

```sql
create or replace function child_count_trg() returns trigger
language plpgsql security definer set search_path = '' as $$
begin
  if tg_op = 'INSERT' then
    update public.parents set child_count = child_count + 1 where id = new.parent_id;
  elsif tg_op = 'DELETE' then
    update public.parents set child_count = greatest(child_count - 1, 0) where id = old.parent_id;
  end if;
  return null;
end $$;
revoke all on function child_count_trg() from public, anon, authenticated;
create trigger child_count after insert or delete on children
  for each row execute function child_count_trg();
```

**The three-armed variant, when the child SOFT-deletes.** A soft-deleting table needs INSERT /
UPDATE-of-`deleted_at` / DELETE, and the trigger must be declared `after insert or update of
deleted_at or delete` — a bare `or update` fires on every column write, and omitting `of deleted_at`
means the decrement never runs:

```sql
  if tg_op = 'INSERT' and new.deleted_at is null then
    update public.parents set child_count = child_count + 1 where id = new.parent_id;
  elsif tg_op = 'UPDATE' and old.deleted_at is null and new.deleted_at is not null then
    update public.parents set child_count = greatest(child_count - 1, 0) where id = new.parent_id;
  elsif tg_op = 'DELETE' and old.deleted_at is null then
    update public.parents set child_count = greatest(child_count - 1, 0) where id = old.parent_id;
  end if;
```

**Why `greatest(x - 1, 0)`.** A double-decrement from any path leaves the count stale-LOW, which
nobody sees. A negative count on a public column is the one failure every reader sees. Floor it.

**On parent delete:** the FK cascade removes the child rows and this AFTER trigger then updates zero
rows (the parent is already gone). Harmless — do not add a guard for it.

**Copy the shape, don't invent a second one.** When the codebase already has one of these, the new
one should be diffable against it. A reviewer who can see that two counter triggers are identical
except for table names reviews in ten seconds; two different approaches to the same problem cost an
hour each time.

## Half B — the append-only ledger (the actual lesson)

### The defect class, named
**Counting the surviving rows of a user-deletable relation gives you a number the user can reset.**
Every derived fact built that way is one toggle away from zero, and none of them raise an error.

Three separate defects in one feature — each of which looked like its own bug — had this single root
cause:

| Derived from `count(*)` of live rows | What the toggle actually bought |
|---|---|
| **Rate limit** — "N actions per 24h", counting extant rows | do → undo → do leaves ONE row. The budget never advances past 1. It is an **infinite budget**, not a limit. |
| **Notification** — fired on every INSERT into an upsert that resets `read_at = null`, moves `created_at = now()` and bumps `count` | One actor can drive the subject's inbox row back to UNREAD and to the top of the list on demand, and inflate a `count` the push copy calls "people" without limit. "N people did X" becomes a claim about people generated by ONE actor. |
| **Ranking/engagement event** — an events row re-minted with `created_at = now()` on each re-insert | The endorsement moves into whatever measurement window is open **now**. A weighted engagement can be dropped into any test on demand. |

All three need the same thing, and none of them can get it from the toggle table.

### The fix: a second, append-only table with no client grants

```sql
-- The FIRST time each actor did this to each subject. Never deleted when they undo — that is
-- the entire point. Service-side only: no grants to any client role, ever.
create table action_events (
  subject_id uuid not null references subjects on delete cascade,
  actor_id   uuid not null references profiles on delete cascade,
  first_at   timestamptz not null default now(),
  primary key (subject_id, actor_id)
);
create index action_events_actor_first on action_events (actor_id, first_at desc);

alter table action_events enable row level security;
revoke all on table action_events from public, anon, authenticated;
```

Then every derived fact reads the LEDGER, not the toggle table:

```sql
-- Rate guard: a real 24-hour budget on NEW actions. Toggling one subject costs one, once, ever.
if (select count(*) from public.action_events e
     where e.actor_id = new.actor_id and e.first_at > now() - interval '24 hours') >= 200 then
  raise exception 'action_rate_limit' using errcode = 'P0001';
end if;

-- Notification: the ledger insert's OWN ROW COUNT is the idempotency test.
insert into public.action_events (subject_id, actor_id) values (new.subject_id, new.actor_id)
  on conflict do nothing;
get diagnostics v_first = row_count;
if v_first = 0 then return null; end if;   -- seen before: never re-notify

-- Engagement row: created_at comes from the LEDGER, never from now().
insert into public.engagements (subject_id, actor_id, channel, created_at)
  select new.subject_id, new.actor_id, 'action', e.first_at
    from public.action_events e
   where e.subject_id = new.subject_id and e.actor_id = new.actor_id
  on conflict do nothing;
```

### Three mechanical notes that are easy to get wrong
- **Insert the ledger row idempotently in EVERY trigger that needs it**, not only the first one to
  run. Postgres fires same-timing triggers in **name order**; depending on that silently is how a
  working trigger set breaks on a later rename.
- **Bare `on conflict do nothing`**, no target — a partial unique index (`... where channel =
  'action'`) cannot be named as an `on conflict` target without repeating its predicate.
- **Why a ledger and not `deleted_at` on the toggle table.** Soft-delete is the obvious alternative
  and it is worse here: it imports a permanent `deleted_at is null` predicate onto every read path,
  changes undo from a DELETE to an UPDATE (needing `grant update (deleted_at)` and an UPDATE policy),
  and **changes the shape of a table other parallel lanes are already reading and writing**. The
  ledger costs those lanes nothing — no grants, so no query anywhere changes. Soft-delete is right
  when the deleted row must still RENDER (a comment showing "[deleted]" to hold a thread's shape); it
  is not a rate-limiting device.

### The other half of the guard: an INSERT grant moves the boundary into the DB
If `authenticated` holds `insert` on the toggle table, **PostgREST is a different origin from your
API route** — any per-account limit the route implements is bypassed the moment a caller posts
straight to `/rest/v1/<table>`. Every client-insertable table needs its limit as a `before insert`
trigger, not as route middleware. Set the ceiling generously (far above any human) so it never
constrains the UI lanes; it exists so one account cannot be scripted into a fan-out engine.

The same trap one level up: **a definer RPC whose rate-limit keys are CALLER-SUPPLIED parameters does
not rate-limit anything** for a direct PostgREST caller, however carefully the route derives them.
If a limit's bucket is a function argument, the attacker chooses the bucket. Derive the bucket inside
the function from something the caller cannot pick, or revoke `execute` from `anon` and force the
call through a server route holding the service-role key.

## Assumes / adapt
- Postgres 15+ / Supabase with RLS on and revoke-by-default privileges (a table a later migration
  creates starts unreachable; you grant explicitly).
- Assumes the parent count column is `int not null default 0` and that a stale-low count is
  acceptable. If the count must be exact, do not denormalize — aggregate.
- The ledger cascades with both parents, so account deletion and subject deletion carry it out. Check
  that is what you want before adding any retention job.
- **Audit your existing toggles when you adopt this.** The codebase this came from has a live
  reactions guard with exactly the resettable shape; its consequences are small (nothing notifies on
  a like) but the flaw is identical. Finding one of these usually means finding three.
