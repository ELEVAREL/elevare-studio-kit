# False-green casebook — the incidents behind STANDARDS §Verify

> **Extracted from `STANDARDS.md` on 2026-09-06, verbatim.** The operative RULES stayed in
> STANDARDS, which is injected into all 80 agents; this file holds the worked incidents —
> the exact commands, repos, dates and post-mortems — which are only needed when you are
> diagnosing one of them. Nothing here was reworded. If a rule and this file ever disagree,
> STANDARDS is the rule and this is the history.

Related skills, all of which were forged from these incidents: `calibrated-check`,
`claim-reality-audit`, `hydration-assertion`, `outcome-integrity-sweep`, `claims-ledger-sweep`,
`merge-integration-gate`, `windows-agent-execution`.

- **★ RANK YOUR SOURCE BEFORE YOU ASSERT — and never report CURRENT STATE from a file.** Every source that can answer "what is true right now" sits on a ladder, and the failure is always the same shape: a **plausible** source substituted for a **measurement**, stated in the register of an observation. **Tier 1 (settles it):** the live API/runtime, the deployed artifact, the real charge, the actual served bytes. **Tier 2 (evidence, can be stale):** repo source you just read, a DB row, a live query. **Tier 3 (hypothesis only — never state as fact):** a memory file, a code comment, a doc or config value, a variable or file *name*, another agent's report, your own earlier message, an uncalibrated check's output. **A Tier-3 source may OPEN an investigation; it may never CLOSE one.** A doc states an *intent* and rots silently while the system states the *outcome*, and a stale doc does not read as uncertain — it reads as authority: `docs/CONNECT-MIGRATION.md` said a client was at 0% platform fee, that was relayed as fact and produced three false statements to the owner in a row (his client was at 0%, it had been costing him money, his income dashboard was fiction) before he corrected it from his Stripe dashboard — **the real charges had said 3% the whole time**. A same-day fleet sweep found four more of the same class (code/doc/DB disagreeing three ways, a live card-taking site documented "not live", a version four releases stale). On 2026-09-04 the conductor asserted five things to the owner off Tier 3 and was wrong five times: gift cards "broken" (from a memory), a revenue split "automatic" (from a code comment — an amount sat unseparated), a bundle "clean" of a leaked token (searched by variable *name*), an API "failing" (its own header handling), and a zero-occurrence count from a sweep whose positive control never executed. **The counter-measure is a FORMAT rule, because the honesty rules alone did not fire: when you state system state, the sentence carries its tier inline** — "live Stripe API: no application fee on either account" beats "the split is automatic" even when the second happens to be right, because the reader can see which one is a measurement. Ground truth for money is `application_fee_amount` on a real charge; for a deploy, the deployed artifact; for a flag, the value the runtime reads; when sources disagree, the one that disagrees with reality is the error and it is usually the doc. **Memory and comments are the most dangerous Tier 3** — memory auto-loads with the authority of a rule, and a comment actively suppresses the review that would have caught the gap. Memory is authoritative for *hazards and procedures*, never for *current state*. Two corollaries: **when corrected, withdraw everything you derived from the bad number**, not just the number; and **your own tool's output is a document too, and the newest one is the least trustworthy** — a masking regex written minutes earlier relabelled dates as `<PHONE>`, and that output was then cited as evidence the scanner was mis-flagging dates (the scanner was correct, the mask was wrong). Never diagnose a system from an artifact you generated in order to *look* at it — a summary, a redacted dump, a normalized export, a screenshot of a screenshot; go back to the raw source and calibrate the viewing tool first. Skills that do the work: `[[claim-reality-audit]]` (a written claim is a hypothesis with a timestamp), `[[calibrated-check]]` (prove the check can fail), `[[credential-drift]]` (test the exact copy). See [[assert-from-the-live-system]], [[docs-must-not-assert-stale-state]].
- **Label every finding — CONFIRMED (you observed it) vs PLAUSIBLE (you inferred it) — and treat INCONCLUSIVE as a first-class result, not a failure to deliver.** An inference stated in the register of an observation is how a false finding gets acted on. Every finding carries how it was established (the command, the URL, the rendered artifact) so the next reader can re-run it; anything you reasoned to rather than watched is marked PLAUSIBLE and says what would confirm it — mixing the two in one list makes the whole list untrustworthy. If something is unverified, a placeholder, or simply could not be established, say exactly that and name what would resolve it: on 2026-08-12 one agent reported rate-limiting as *inconclusive* rather than banking a pass it had not earned, and nearly every defect that reached a real paying customer that same day came from the opposite move. **A pass you did not earn is worse than no pass, because it retires the question** — nobody re-checks a green. Never round an unproven check up to green, and never let a brief's expectation of green do the rounding for you.
- **★ Never trust a green that was produced by a DIFFERENT PROCESS than the work. Name which process produced it and what that process can actually observe** — if the answer doesn't include the failure you care about, you have not tested for it. The clearest case: a *launcher* exited 0 while the script inside it died — a scheduled post reported success and never posted, because the 0 was the wrapper's code, not the script's. Same class, one clause each: `tsc` cannot see across a serialization or render boundary (a function returning `null` rendered the literal word "null" to a customer under a clean typecheck); Deno edge-function sources sat **outside the tsc project entirely**, so a syntax error surfaced only at deploy; a *backgrounded* browser pane never fired `requestAnimationFrame` and manufactured a false "SEO is broken sitewide" finding. **Verification scripts are in scope — a tool you wrote to look at the system is not the system:** one reported 14/14 URLs BROKEN because of a bad cast inside its own `try` block, and the tell was its negative control "passing" while everything else failed.
  - **A typecheck that compiles NOTHING exits 0 — name the config your green came from, and confirm it actually includes `src/`.** flavornews-web's root `tsconfig.json` is a *solution-style* stub (`{"files": [], "references": [...]}` — the shape every Vite/React scaffold has shipped for the last two years), so `npx tsc --noEmit` type-checks **zero files** and exits 0 regardless of the state of the code. It was run four times and reported as `TSC_OK`; `npx tsc -p tsconfig.app.json --noEmit` on the same tree showed 11 real errors, and a test-engineer subagent — not the conductor — is what caught it (2026-08-19). **If the tsconfig you point at has `"files": []`, an empty `include`, or only `references`, you have measured nothing** — run `tsc --build` (which follows the references) or `-p` the referenced project, and state the config file in the report. The defect is never in the command, it is in what the project silently excludes; calibration settles it in one minute — break a type in a real source file and confirm the command goes red.
  - **Build-green is NOT ship-green — a clean `next build` + `tsc --noEmit` does NOT prove a serverless route RUNS.** The mechanism is stated once, in §Supabase + Next.js ("heavy deps load lazily + `runtime = \"nodejs\"`"): a static-imported CJS/ESM-interop dep crashes every request at module eval while tsc and build pass clean — on Vercel that 500'd *even the bad-token 404 short-circuit*. The verification half is here: **every new/changed API route gets a post-deploy LIVE smoke against the deployed URL — curl the happy path AND the error path (bad token, missing body)** as part of definition-of-done. Only real HTTP against the deployed function surfaces a module-eval crash.
- **★ Pick a signal that CANNOT be present when the thing is broken, and CALIBRATE any new check before trusting its verdicts. A check that passes on a dead page manufactures confidence, which is worse than no check.** Before accepting any check, name the failure it exists to catch and confirm it would go **red** under that failure. A freshly written pass/fail gate (a visual seam scan, an ink/contrast threshold, a lint rule, a smoke assertion) is itself unverified code — run it against a known-good AND a known-bad/known-empty reference sample first: an uncalibrated ink-threshold seam scan fired 3 false positives on a reel slate (sparse-but-real frames flagged as empty) and burned a re-review cycle, while a threshold anchored to a measured chrome-only reference fired clean. Four HausAI verifications returned confident green against a broken product; the two sharpest mechanisms: an element asserted **present in the DOM** passes on a page that never hydrated, because the server HTML contains it; and an anon-leak sweep whose criterion was `status 200 && rows > 0` scored a wide-open policy on an **empty** table as `ok` — and pre-launch, most tables are empty. (The other two: a CSP fix confirmed by reading the response *header* on a dead page — by grepping only the **first 8** script tags and generalising from the sample — and a test pinned to a seed migration that a **later** migration had superseded.) Concretely: assert the **end state**, never a source something else may have superseded (a guard anchored to a superseded source validates the wrong thing forever *and reads as proof*); assert the **residue** — "does any `<!--` or `[NEEDS` survive the publish?" — rather than one known shape of the defect; and choose a positive signal impossible in the broken state (React **fiber count**, not element presence; a real row, not a 200). **The SPA corollary: an HTTP 200 proves nothing, because every unknown URL returns the shell.** A Vite/CRA/SPA host serves `index.html` with status 200 for `/does-not-exist`, `/typo`, `/an-endpoint-nobody-built`, so a link-checker or smoke test asserting `status === 200` scores a dead route as healthy and a broken deploy as clean. Assert on the **bytes** — content-type, plus a string that can only be present on the intended page (the route's `<h1>`, an id, a server-rendered value) — and include a **known-bad URL as a negative control** in the same run, which must come back failing.
- **This applies to every TEST and every SWEEP: a green proves nothing until you have watched it go red.** Break the code the test is meant to protect, confirm the expected tests fail *by name*, then restore. Used repeatedly on Thames Coast and it caught real holes each time — injecting an `authorId` into a serializer to prove 4 leak tests fire, disabling a tombstone early-return to prove the reply-leak test fails, restoring a query-param auth path to prove the refusal test triggers. Costs a minute; it is the only thing that distinguishes a test that protects behaviour from one that merely runs. Non-negotiable for any test guarding money, auth, privacy, or a destructive path. **When it refuses to go red, the cause is one of three and you must name which:** a stale build artifact ran instead of your edit ([[pyc-cache-masks-red-green]]); a *different* guard fired first, so the test never exercised the one it names; or the suite only asserts refusals against a gate that refuses everything ([[negative-controls-catch-always-true]]). "It stayed green, probably fine" is the failure — and an agent that reports "this test passed for the wrong reason" unprompted has done the job exactly right. **Any ZERO you report from a search obeys the same rule:** plant a known control in the artifact and confirm the search finds it before you report the absence.
- **★ A DERIVED artifact does not contain your SOURCE-form needle — search for the VALUE, never the NAME, and plant a control.** ProCraft's public bundle was searched for a leaked token **by its variable name**, reported clean, and the token was sitting in it: minification renames every identifier, so the one string guaranteed *not* to survive the build is the one that was searched for. The class is far wider than minification — any time the artifact you are grepping was **transformed** on the way to the reader, source-shaped needles miss by construction: a minified bundle (names gone), a gzip/brotli response, a base64 or `data:` URI, an RSC/JSON payload (escaped, and it double-counts visible copy), a PDF or image (no text layer), a compiled binary, a template that interpolates at runtime. **Two mechanical rules: (1) search for the literal value that must appear at runtime** — the token's own characters, the rendered sentence, the actual hostname — never the identifier, the env-var name, or the constant that produced it; **(2) plant a known control in the same artifact and confirm the search finds it** before you report a zero. An absence-of-evidence result over a transformed artifact is worthless without a positive control, and this is the exact shape of a false "no secrets in the bundle" clearance. Owner of the sweep: `security-reviewer`; owner of the calibration: whoever reports the number.
- **Verify as the LEAST-PRIVILEGED CONSUMER, not as yourself — your own access is ambient and invisible.** The server-watchdog's advertised install one-liner fetched a codeload tarball from a **private** repo. It worked every single time the owner ran it (cached git/gh credentials) and returned an anonymous **404 for everyone else** — a command handed out for a while that had never once worked for a stranger. Same class, twice more: `*.vercel.app` is login-walled while the custom domain is public, and a deployed credential can be expired while your local copy is valid ([[deployed-credential-goes-stale]]). **Any URL, command, download, install script, share link, QR code, or invite you publish must be exercised from the consumer's identity and state — no cached credential, no prior clone, no logged-in session, no local file the reader will not have.** Run it in a throwaway container or a clean profile with the auth stripped. "It works for me" is a statement about your credentials, not about the product.
- **The mirror of the false green: a RED you reproduced BY HAND may be an artifact of your harness, not a defect.** Running `watchdog run` from an interactive shell does **not** load systemd's `EnvironmentFile`, so an env-dependent check read "token empty" and looked exactly like a bug — the service, started the way its supervisor starts it, was correct. Cron's minimal PATH, a scheduled task's user profile and working dir, a container's env, a shell's inherited `PATH`/locale: every supervisor hands the process an environment your terminal does not. **Before filing a defect you observed under manual invocation, re-observe it the way the thing actually runs** (`systemctl start` / trigger the timer / run the scheduled task / exec in the container) — and when the two disagree, that difference IS the finding, not the symptom. **The same rule governs blaming a THIRD PARTY, and the tell is identical failures: N calls that fail the SAME way share one factor, and it is your caller, not their service.** Five Inkbox API calls were reported to the owner as API failures on 2026-09-04; all five were the conductor's own PowerShell header handling. A real outage is usually intermittent, or the errors differ, or a status page says so. **Before attributing any failure to a vendor, reproduce it through a SECOND, independent client** — raw `curl` against the documented endpoint, the MCP tool instead of your shell, a different machine — and quote what the provider actually returned. Same family as `[[credential-drift]]`: "it fails" is not evidence about *their* system until you have removed yours from the path.
- **Run it in a browser.** Use the **`run` skill** (it finds this project's launch path) or start a server from Bash and drive it with the **`browser-qa`** skill. Check the rendered DOM, test the actual interactions, and confirm **zero console errors**. Assert on the **bytes the server returned** — content-type plus a string only the intended page can contain — not on a screenshot. **On any React/Next route, run `hydration-assertion` FIRST:** a green build, a clean console, the correct response header and the element being present in the DOM ALL pass on a page whose client tree never mounted, and every observation after that is about server HTML.
  **★ `preview_eval`, `preview_screenshot` and `preview_console_logs` DO NOT EXIST in this harness** — not in the tool list, not deferred, not reachable via ToolSearch (verified 2026-09-06). They were named here for months, so the studio's most-cited verification gate had no method behind it and six agent files inherited the dead call. Do not reintroduce them. `.claude/launch.json` on both drives is orphaned config from that era.
- **A dev server and a build must never share one output dir.** Running `next build` while `next dev` owns `.next` fails on Windows with `PageNotFoundError`/ENOENT on every route and can destroy in-flight work — the same trap as any tool with a single default working dir (Vite `dist`, coverage, Playwright artifacts). Wire the escape hatch once (`distDir: process.env.NEXT_DIST_DIR || ".next"`) and have any agent verifying alongside a running server build with `NEXT_DIST_DIR=.next-build`. A build failure caused by a shared dist dir is an environment collision, never a code defect — do not "fix" the code for it.
- **Swapping an auth/identity/data model or provider mid-build has latent consumers — prune the old scheme AND re-verify every consumer of the changed shape.** Each swap (asky went shared-passphrase → email-OTP → username/password in ONE session) leaves dead code, stale env vars, and — worst — silent broken assumptions: a removed field (an `email` column) still referenced downstream and passed to a third-party API (`customer_email` → Stripe) **502'd every purchase while the build stayed green**. After any such swap, grep the removed field/env/scheme name repo-wide, delete the remnants, and exercise each consumer live — a compiler won't show a now-`undefined` value crossing an API/serialization boundary.

## Added 2026-09-06 — Whyza reposts wave (NOT from the STANDARDS extraction above)

Three incidents from one parallel wave. Each is the same shape: **"found nothing" and "did not
look" produced identical output**, and nobody could tell them apart from the report.

- **A measurement harness needs a NEGATIVE CONTROL before any of its numbers are worth reading.** A
  CSS overflow harness reported **0 overflow** for a row a real browser measured at **8px**. Its
  output was discarded — correctly — but only after it had been believed once. The general mechanism,
  which is worth knowing whatever harness you are handed: a probe of the form
  `document.documentElement.scrollWidth > document.documentElement.clientWidth` is a boolean about the
  **document**, and an 8px overflow inside *any* clipping or scrolling ancestor (`overflow:hidden`,
  `overflow:auto`, a carousel, a `contain:` box) never propagates to the document. The probe is not
  wrong; it is answering a different question than the one asked, and its answer is `false` either
  way. Whyza carries probes of exactly this shape at `scripts/verify/page-probe.mjs:27` and
  `scripts/verify/shoot.mjs:78,86` (CONFIRMED present; that these are the specific harness whose
  output was discarded is PLAUSIBLE, not confirmed). **The rule: before trusting a measurement
  harness, feed it a case you have measured by hand that MUST come back non-zero.** A harness that
  cannot produce a non-zero has not been shown to measure anything. Same family as
  `[[negative-controls-catch-always-true]]`, applied to measurement rather than to pass/fail.

- **A repo-wide sweep walks build output and `node_modules`, and returns a clean-looking zero.**
  `claims-ledger-sweep` was run across a tree holding **24 `.next-*` directories** (`.next`,
  `.next-api`, `.next-audit`, `.next-build`, `.next-captcha`, … one per agent per gate in the wave,
  which is the *correct* answer to the shared-dist-dir rule above) plus `node_modules`. It returned
  zero. A zero from a sweep that spent its budget on dist dirs is indistinguishable from a zero from
  a sweep that read the source. **This is directly reproducible and cost this harvest a run:** a
  bare `grep -rn <pattern> .` at the Whyza repo root **exceeded a 120-second timeout and died**
  (2026-09-06), having read nothing anybody wrote. **The rule: any repo-wide sweep states its
  exclusions and its file count in the same sentence as its result** — "0 hits across 412 tracked
  files, excluding `.next*`/`node_modules`/`dist`" is a finding; "0 hits" is not. Prefer
  `git ls-files` (or `rg` with its default VCS ignores) as the file list, and plant a control the
  sweep must find, per the derived-artifact rule above.

- **Check the gate is REACHABLE before you spend on it.** ~95 minutes were lost to two `npm run
  build` attempts that could never have succeeded: another lane had landed 8 `TS5097` errors and
  `next.config` sets no `ignoreBuildErrors`. Nothing about the failure was surprising once anyone
  looked; nobody looked first. **The rule, for whoever is about to run an expensive gate in a
  parallel wave: spend thirty seconds establishing that the gate CAN pass in the tree's current
  state** — a `tsc --noEmit` before a build, a `git status` for another lane's in-flight files, the
  tree-frozen field from the handoff header — before committing minutes to it. A gate run against a
  tree that cannot compile is not a failed gate; it is a gate that never ran, and it is time spent
  learning something a cheaper command would have said. This is a conductor-level scheduling rule as
  much as a verification one.

## From the $49 audit-report wave, 2026-09-13

- **A comment-stripper is a false-green machine in BOTH directions, and the same wave hit both.**
  Direction one, the stripper eats real hits: a design rejection-list rule for hard-coded `clamp()`
  was reporting its own documentation as a violation, so CSS comments were stripped before it ran.
  A stripper wide enough to fix that is wide enough to hide a real `clamp()` inside a commented-out
  block. The containment: strip for the two rules that need it and NOTHING else (the emoji and serif
  rules still read the whole file), and print the byte count removed in the same output as the
  result. Direction two, an extractor reads garbage FROM a comment: the audited site's own `<head>`
  contained an HTML comment holding the literal text `<title>`, and a naive title regex matched
  inside it and returned garbage as the page title. The crawler now strips comments before
  extraction and retains them separately. **The rule covering both: state what your stripper removed
  in the same sentence as your result, and scope it to the rules that need it.**

- **"Newest first" was a comment, not a behaviour, and it silently shipped the OLDEST candidate.**
  A renderer resolved its input as "any `report*.json`, newest first". `readdirSync` is
  alphabetical, not chronological. With three model-variant outputs present it selected the oldest
  every time, with no error and a perfectly clean-looking build. Which variant a paying reader
  receives is not a decision a renderer gets to make by sort order. **The rule: resolve the exact
  contracted filename; if it is absent and exactly one candidate exists, use it and print WHY; if
  two or more exist, refuse with a distinct exit code.** Generalises to any glob-then-pick-one input
  resolution, including `dist/*.js`, `migrations/*.sql` and `out/*.png`.

- **An anchored regex silently undercounted a budget by exactly one.** An accent-colour budget rule
  counted `var(--accent)` declarations with a line-anchored regex. A single-line rule such as
  `.x { border-left: 2px solid var(--accent); }` puts its declaration mid-line, so one of the three
  allocations was never counted and the budget reported clean while it was at its limit. **Any rule
  that counts occurrences in source must be run against a synthetic positive written in every
  formatting style the source actually uses**, minified and single-line included.

- **`grep -P` errors on this machine and its error reads as a clean pass.** Restated here because it
  is the direct cause of [`control-first-check.md`](control-first-check.md) and of
  [`_gates/emdash-check.mjs`](_gates/emdash-check.mjs). Never use `grep -P` for a studio ban; run
  the detector that carries its own control.
