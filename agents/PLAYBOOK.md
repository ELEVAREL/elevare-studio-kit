# Elevare Studio — Operating Playbook

How the studio turns an idea into a shipped result, every time. This is the process the conductors (**delivery-lead**, **marketing-strategist**) run, and the map anyone can follow. Pair with [OPERATIONS.md](OPERATIONS.md) (how the COMPANY runs — client lifecycle, incidents, cadence; this file is how a JOB runs), [STANDARDS.md](STANDARDS.md) (the bar), [CRAFT.md](CRAFT.md) (visual bar), [SYSTEMS.md](SYSTEMS.md) (the system-design bar for multi-actor/hardware/money/offline builds), [SKILLS-MAP.md](SKILLS-MAP.md) (which skill to pull), and [README.md](README.md) (the roster).

## The loop (every job runs this)
```
INTAKE → TRIAGE → PLAN → EXECUTE → GATE → SHIP → MEASURE → LEARN → ITERATE
```
Scale it to the job: a one-line fix skips most of it; a new product runs the whole thing. The conductor decides how much.

### 1. INTAKE — capture the real request
- **Ask first, always: is this a CLIENT project or a PERSONAL / Elevare Studio idea?** Never assume — it changes ownership, branding, deploy target, monetization, and whether the "Powered by Elevare Studio LLC" credit applies.
- Restate the goal in one sentence and name the outcome/definition of done.
- Capture constraints: scope, deadline, budget, what the client supplies (keys, photos, copy, accounts), and whether a brand already exists.
- Ask only the 1–3 questions that actually change the plan. Don't invent requirements; don't stall on things with a sensible default.
- **★ CHALLENGE THE BRIEF BEFORE YOU BUILD IT — SHARED-RULES §11, added 2026-09-29.** Every other step in this playbook checks WORK. None of them checks the PREMISE, so a job can clear all of them and still build the wrong product, and a good process only makes the wrong thing arrive faster. **Rank where the requirement came from:** the owner in his own words outranks a document he wrote, which outranks a document he FORWARDED — and a forwarded document is not his voice, it is somebody else's idea he found interesting. Helios was built from four such emails, reconciled against each other like scripture, and produced 70 commits, 579 files, 46 migrations and **2,025 passing tests** before he said *"this is nothing on how I want it to look or operate"* and all of it was deleted. Nothing failed; every gate passed; the premise was never checked. So: restate the job in one sentence, name and rank its source, **challenge at least one thing** (a weak decision, a scaling risk, a cheaper route, scope that does not earn itself), prefer the smallest TRUE thing over the smallest thing that demos, and ask the ONE question whose answer changes what you build. **Verification cannot rescue a wrong premise.** The ten senior-engineer role prompts and which agent owns each: [ROLE-PROMPTS.md](ROLE-PROMPTS.md).

### 2. TRIAGE — pick the conductor + playbook
- **Product / build / technical / research** → **delivery-lead**.
- **Marketing / content / campaign / creative assets** → **marketing-strategist**.
- **Tiny, single-specialist task** → route straight to that specialist (skip the conductor).
- **Unfamiliar existing codebase** → **codebase-navigator** runs first, always, before any change.
- **A brand with a dedicated pod** → route brand-specific work to that pod's specialists (they bake in the brand DNA), still under the studio conductor. **TEMPTATION** has a 7-agent pod (`temptation-*`, see [temptation-TEAM.md](temptation-TEAM.md)): build/storefront work runs under delivery-lead with **temptation-graphic-designer** → **temptation-merchandiser** feeding the build and **temptation-brand-guardian** gating alongside art-director; drop/marketing work runs under marketing-strategist with **temptation-drop-strategist** → **temptation-conversion-copywriter** → **temptation-growth-marketer** + **temptation-social-content**. The pod operates inside this same flow — it does not fork the process.
- Choose the matching playbook (section below).
- **★ SCOPE ESCALATION IS A RE-TRIAGE, AND THE PLAN'S OWN EXEMPTIONS ARE WHAT EXPIRE.** A plan written for a smaller scope earns exemptions honestly — "no payments, no accounts, no PII, so `compliance-counsel` is NOT a dependency" — and then writes the trigger that cancels them and nobody watches it. PhyscoClosett's `PLAN.md:295-296` said exactly that for the demo and, three lines down, *"REAL BUILD: `compliance-counsel` IS a hard pre-launch dependency"* with four named blockers; the client approved the demo, the same session took it to production with a database, accounts and buyer names/addresses, and the site collected real PII behind `/privacy` and `/terms` returning **404**. Nothing failed — a conditional dependency simply never fired, because the condition was written in the plan and the plan was never re-read after the scope changed. So whenever a job crosses a scope line — demo → production, prototype → real users, internal → public, free → paid, fake data → real data — **stop and re-read the plan's own conditional, deferred and "not for this phase" items, and discharge or restate each BY NAME** before the next wave starts. The tell to grep your own plan for: `not a dependency`, `not a blocker`, `phase 2`, `once we`, `if this becomes`, `for the real build`. An exemption is scoped to the scope that bought it.
- **Declare the DESIGN ARCHETYPE and the INDUSTRY VERTICAL in the brief — for any job with a visual surface, this is mandatory and it happens here, at triage, not at design time.** Archetype from [ARCHETYPES.md](ARCHETYPES.md) (product-tool · editorial commerce · immersive · local trust · content/media · conversational · internal operator console); vertical from [INDUSTRIES.md](INDUSTRIES.md) (paste that section's eight fields — money moment, above the fold, required, trust proof, schema, booking/payment, compliance, #1 failure — straight into the plan). Undeclared, every job silently defaults to *product-tool + no vertical*, which is exactly how a bar, a salon, and a fashion drop all ship as the same SaaS dashboard with a different accent hue. `art-director` owns the archetype call and also names the **one signature moment** the project will be remembered for; `product-strategist` owns the vertical fields. Both carry through to the gate.

### 3. PLAN — decompose + route
The conductor produces a step list: each step has an owner agent, a self-contained brief (so the agent can act cold), its dependencies, and whether it runs in parallel. Flag every human decision point up front.

### 4. EXECUTE — specialists work, in parallel where independent
- Independent work runs concurrently (e.g. copy + visuals + video; or the six quality gates).
- Dependent work is sequenced (data model before backend; direction before UI; UI before motion).
- Every agent finishes with the **handoff report** (below). The conductor reads it and decides the next step.
- **Memory is a PRE-FLIGHT check, not a post-mortem.** Before the first irreversible action against any shared/global store (the key vault, Vercel env, a scheduled task, a live DB, a third-party resource you can delete), read the memory entry for that tool FIRST. Two vault/env hazards were destroyed on Thames Coast *hours after* the memory files warning about each were written — a documented hazard that is consulted only while repairing the damage is not a control. Consult, then act.
- **Same pre-flight for the LIBRARY/BLUEPRINT: if the step adds INFRASTRUCTURE rather than a row of configuration, stop and diff against what the existing instances actually do live.** ProCraft VA shipped a bespoke `stripe-connect` edge function with its own secret when the studio's documented Connect blueprint needed only an onboarding link plus a registry row; it broke and blocked the client from taking any card payment. The blueprint existed and was never opened. The tell is structural, not a judgement call — **you are building a second copy of something that already runs for other clients**, which also means a second thing to secure, rotate and keep alive. Read `D:\.claude\agents\library` + the relevant memory blueprint FIRST and name it in the plan, or say why the existing one does not fit.

### 4b. SEAM PASS — a mandatory barrier at the end of every parallel wave, BEFORE gates
On a 12-agent / 6-wave run, **every serious defect lived BETWEEN agents, not inside one.** No agent's self-verification can see across its own fence, and tsc + tests + build are all green on both sides of a broken seam. So the conductor closes every parallel wave with an explicit barrier, run by an agent that **built nothing in that wave**:
- **★ FIRST ITEM, NOT LAST — WALK THE WHOLE PATH AS ONE PERSON.** Confirmed a *third* time on 2026-08-12, which means the seam note below was being read and not acted on: three separate products shipped correct pieces and a dead product, each with tests, types and build green on both sides of the break. (1) **Fanta** — a booking lookup used the platform key against a charge on a *connected* account; three real customers paid $180, saw a green "Payment successful!", and no appointment was ever created. Found only by probing production. (2) **Favis Customs** — the customer's tracking token was minted when the shop owner *priced* the job and the submit endpoint returned nothing, so a customer could submit, be priced, and never learn the price — putting the owner back in the DMs the site existed to escape. Schema right, API right, security right, product useless. Found only by walking the hops as a person. (3) **Favis again** — the tracking link that fix produced pointed at `/quote/[token]`, **a page nobody had built**, because two agents each assumed the other owned the destination. So the barrier's first act is literal and non-negotiable: **name every actor and every hop** (customer submits → owner is notified → owner prices → customer is notified → customer opens the link → customer pays), then **perform each hop and OPEN each destination**, including the hops that leave the app (an email, an SMS, a link a human pastes). **Any hop where an actor would not learn what they need is a blocker, weighted identically to a failing test.** A green suite cannot see a hop nobody wired, and neither can a claims ledger of copy — the ledger asks *which file implements this*, the walk asks *did the next human ever find out*.
- **★ NEVER WRITE COPY, DOCS, OR A COMMENT ASSERTING A DESTINATION YOU HAVE NOT OPENED.** A URL, a route, a "check your link", a "see the dashboard", a file path in a guide, a `// handled in X` comment: opening it is one action and it is the entire check. The unbuilt `/quote/[token]` above survived every gate and was caught only because a third agent **refused to write copy claiming the link worked** without first confirming it resolved — that refusal is the behaviour to reinforce, not a delay to route around. This is the actionable half of the claim–reality rule and it belongs to whoever writes the sentence, not to the gate that reads it.
- **Diff the "Breaks / invalidates" declarations (handoff field 3) against every other agent's "Done" list.** Any intersection is a seam — resolve it before the wave closes. Requiring each agent to state what it BREAKS for others is the cheapest seam detector there is; "what I built" alone never surfaces one.
- **A render/caching-mode change is a CONTRACT change, not a local perf detail.** Adding or removing `force-dynamic` / `revalidate` / `generateStaticParams` / a cache wrapper changes what every per-viewer prop on that route resolves to. Whoever changes it must enumerate the viewer-dependent props on that route and report each one's new value — a prop that silently becomes `undefined` is a shipped-dead feature. This exact pair killed a paid perk on Thames Coast: a perks agent built a venue-follow control on `/events/[slug]`; a perf agent then correctly restored that page to ISR (380ms → 3.5ms), so the page stopped resolving a viewer and the control received `undefined` and rendered nowhere. **Both changes were right.** The defect was that neither declared what it broke for the other.
- **Claims ledger.** Every user-visible sentence the wave added that promises a capability, or names *where* a capability appears ("on every event card and every event page", "replies live on the event page", "follow venues"), gets a row: claim → the `file:line` that implements it → verified reachable. A row with no implementing file is a **blocker**, not copy polish. Six surfaces drifted this way in one run; no automated gate can see any of them. **The mechanical tell to grep for: a route calls an RPC, table, column or edge function that NO migration or source file in this tree defines.** Whyza's whole early-access funnel called three RPCs that existed neither on disk nor in the live DB — typechecked, linted, reviewed and screenshotted while completely inert, because a `supabase.rpc("<name>")` string is invisible to every compiler. Extract every such external symbol the wave's diff names and resolve each one against the artifact that defines it; the same sweep catches a legal remedy, a retention period, or a "you can do this in Settings" with no implementing object behind it.
- **★ THE LEDGER HAS A MECHANICAL, CHEAP FORM NOBODY WAS RUNNING: adjudicate every FALSIFIABLE cross-file assertion in the wave's diff, and report the denominator and the selection rule alongside the count.** elevare-app wave 4's seam pass built its corpus in four commands (comment lines across the diff's 52 code files: **7746**; of those, ones naming a file, path, package, env var, table or migration outside their own file: **412**; of those, the ones carrying a `file:line`, a count or a negative, which are the falsifiable ones: **33**), opened all 33, and found **18 defective**. It then wrote that 33 of 412 is *"a floor, not a total"*, which is the sentence that makes the number usable instead of reassuring. **The skill for this is `claims-ledger-sweep`, it existed, and it was not invoked on this wave** (see §6 `skills:`). **★ SECOND OCCURRENCE, Thames Coast 2026-09-18 — so this is an ENFORCEMENT defect, not a writing one (§8), and the remedy is the receipt, not a louder sentence.** `src/lib/map-types.ts` carried *"Every surface that renders a business MUST render its sample marking. A gate checks this by name."* **No gate checked it**: the field was set on all nine records and read by nothing — twelve references in `src/`, zero in `scripts/` and `tests/`. That is the textbook nomination this skill returns, on a wave that ran a taste gate, a security gate and four verification gates and invoked the skill **zero** times; it was caught by a human-style read in the security review, i.e. by luck. The right ending happened (the fix was to *write the gate*, never to delete the sentence), but the sweep costs one command and would have found it first. **Nothing here needs rewriting — type the `skills:` line, and `NONE` is only a valid value if you can defend it.** Two shapes to reject on sight: an assertion whose target lives in a **different repository** (no reader of this one can follow it and nothing here can tell when it rots; cite the other repo's SHA beside the path or do not write it), and a comment that quotes its own needle and then reports the grep count.
- **Reconcile every build-order STUB when its unblocking condition lands — a `// wired once X ships` TODO is not self-clearing, and a green build actively hides it.** HausAI closed a wave with **five dead affordances** (revert was a no-op, materials inert for paying users, and a fifth nobody ever reported), each stubbed against a dependency that arrived *later in the same run*. A stub whose unblocking condition is now met is invisible to every gate — tsc, tests, lint and the console are all clean, and the control renders. At the barrier, grep the wave's diff for `TODO` / `once … lands` / `not wired` / `stub` / `placeholder`, and for each hit either wire it or state in the report that it is still blocked **and on what**. Same class: a required-placement list (disclosures, disclaimers, consent lines) with no named owning check — HausAI's checkout disclosure existed as a constant with zero render sites and was found *by accident* during a dead-export sweep.
- **★ WALK THE DATA PATH, not only the user path — a produced artifact is DEAD until a CONSUMER is proven to read it.** Four cross-agent seams shipped green on Carina's Workout App (87 tests passing, every file compiling) and were caught by code-quality, never by tests: a data file (`exercises.js`) built by one agent but never SEEDED at boot → the program generated empty; a `pending_readiness` UI-state handshake written by one screen and never read by another; a day-rotation index computed in one screen and ignored by its consumer; and TWO agents (player + finish) each running the progression engine → progression applied twice. The barrier check is mechanical: for every value the wave produces — seed data, a handshake/state flag, a computed index, a stored key — grep for the code that CONSUMES it and confirm the consumer count is exactly right (a write with no reader is a dead feature; a shared single-apply engine with two runners is a double-apply). This is the data-path twin of the user-path walk at the top of this list and of the dead-code rule — a WRITE is only live if something reads it.
- **Round-trip the seam for real.** A green build/tsc/suite is exactly what a seam defect hides behind — two agents shipped session handling with different cookie names (`tc-session` vs `tc_session`) and **both test suites passed, because each mocked its own**. A shared contract must be asserted against ONE exported constant, not re-stated on each side.
- **★ A FOUND DEFECT TRIGGERS A CLASS SWEEP BY ITS MAKER, NEVER A POINT FIX — and the report names the sweep and its count.** This is the single highest-yield behaviour observed on the Whyza reposts wave, and it produced **seven** catches that no gate could have reached. The mechanism is one question, asked by the agent that just found a bug, about its own prior output: *"where else did I make this same assumption?"* — not "re-audit yourself" in general. The API lane, asked whether anything else of its own read through a narrowed table, found a fabricated-fallback defect in its own code with a confident comment above it explaining the wrong thing, then found that one of its own existing tests had been asserting a bare stub that could only have round-tripped through an unserialised route — the stale test was itself the evidence for a second defect. The art-director caught a defect inside its own fix mid-task. The feed lane ran a negative control on its own CSS measurement harness, found the harness reported 0 overflow where the real browser measured 8px, and **discarded its own green**. The security gate audited its own coverage claim, found its repo sweep had walked build output instead of source, declared its own result worthless and re-ran it. The database lane found two bugs in its own probe before reporting, one of which would have passed against the broken code. **Each of those is an agent contradicting its OWN shipped output, which is a different and rarer act than contradicting the brief** — the invitation-to-contradict line covers the brief; this covers the work. So: the barrier asks every lane that fixed anything for its sweep line — `class swept: <the assumption> · <n> sites checked · <n> more found` — and "0 more found" is a real answer that costs one grep.

### 5. GATE — nothing ships un-checked
**Every gate's report states that its check was CALIBRATED.** Run `calibrated-check` before reporting anything as green, verified, passed, or "zero occurrences" — a check that cannot fail is not evidence, and a gate that could not reach the thing it grades has NOT run. Name the observation that would have made it a FAIL.

**After the wave's lanes are MERGED — before any push, tag, deploy or PR — run `merge-integration-gate`.** It catches the two things the seam pass cannot: files silently deleted by a *conflict-free* merge (git never asks about a path one side deleted and the other never re-touched), and typecheck/tests/build never having run on the merge result as git holds it. This is not hypothetical — the Whyza wave2-3 merge reported 17 conflicts, resolved cleanly, and silently dropped 13 more files.

Run the relevant gates (parallel):
- **Build gates:** code-quality-engineer, test-engineer, design-auditor, security-reviewer, qa-verifier, performance-engineer, + **art-director** taste gate. The taste gate is not optional polish and finds a DIFFERENT defect class than the technical audits (it looks at the product, not a checklist): its first pass on a portal caught a functional blocker (an unstyled view-toggle state) plus systemic button-hierarchy/theme-layer issues that four prior technical audits never flagged. Run art-director at least once per product, early enough that its findings can still be acted on — never only as final signoff.
  - **STRUCTURAL, not advisory: the taste gate is a WAVE barrier, not a release gate.** The first wave that produces any user-visible surface DOES NOT CLOSE until art-director has reviewed it, and no later wave starts until it has. Technical gates green is not permission to advance. On Thames Coast this rule existed and was ignored, so art-director returned **DO NOT SHIP with five blockers after every technical gate had already passed** — a count contradicting its own empty state 40px below it, a draft banner announcing a saved draft over a blank form, "100 of 100 founding memberships left" over an empty bar while billing was off, and a paid archive perk that was literally empty. Not one was reachable by tsc, tests, or a security audit, and each was cheapest to fix in the wave that created it.
    - **★ A BARRIER IS AN ARTIFACT ON DISK, NOT AN AGENT COMPLETION — because an agent that DIES is indistinguishable from a barrier that was never scheduled, and the wave closes either way.** Whyza's profile wave scheduled the taste gate correctly as a barrier; it died when the agent pool saturated and was re-run only after the work was committed, returning **DO NOT SHIP with five blockers** at commit-time cost instead of build-time cost — two of which (a signature moment offered on profiles that have no look to lift, and that same moment rendered as a 19px inline link under a 44px pill) are pure taste finds that no typecheck, test or security audit could ever surface. **So the barrier's output is a file — `docs/gates/<wave>/taste-gate.md` — and the conductor's own commit step checks that the file EXISTS before staging anything from that wave.** A dead agent leaves no file, so the wave stays open instead of silently advancing. Recovery when the pool is saturated: re-spawn it, or run it **inline** (the conductor may read the surface directly — the same escape hatch Parallelization already permits for image-heavy gates), and `SKIPPED — pool saturated, re-run at <wave>` is a permitted receipt value. Silence is not. Same reasoning as the missing-header field: an absent file is visible to someone other than the actor.
  - **A gate that could not reach the thing it grades has NOT run — record it BLOCKED and re-run it; never bank it as a pass.** HausAI's first taste pass reported honestly that it had never seen a generated massing board, because the app could not hydrate; the conductor advanced anyway. The re-gate, once the product actually ran, returned **DO-NOT-SHIP on the artifact itself** — plus a false-positive fair-housing refusal fired at a user asking to make a bedroom bigger — after **six technical gates had passed**. The taste gate grades the *product*, not the repo, so it is the gate most often pointed at something unreachable: a dead build, a login wall, fixtures, an empty state. Its brief must name the artifact it has to see, and its report must state that it saw it — at real data volumes, in both themes, at more than one width.
    - **When the blocker is a PERMANENT boundary rather than a broken build — an auth wall, a credential an agent is prohibited from entering, a physical device — the move is to REFACTOR A TESTABLE SEAM, never to fake the gate or drop the check.** On the Good News USA prospects panel the required logged-in walkthrough (change a Stage, toggle Landed, confirm Paid unlocks, reload, confirm persistence) was unreachable because entering a password is a prohibited action. What shipped instead: the stage/paid vocabulary proved exhaustively against the **live** CHECK constraints in SQL, the Landed/Paid unlock rule lifted out of the React component into **pure functions in the lib specifically so it was testable without a DOM**, and the human-only walkthrough handed back as an explicit owner to-do. That is the pattern — move the logic to where the boundary isn't, test it there, and name the irreducible remainder as an owner action. Banking the unearned pass retires the question forever; silently dropping the check is the same thing with less paperwork.
    - **★ THE AGGRAVATED FORM IS WORSE THAN AN UNREACHABLE ARTIFACT: the gate reaches something that LOOKS like the product and is the product with one layer silently removed.** elevare-app shot five App Store frames from a **web export** of a React Native app. `expo-symbols` has no web implementation, so every `Glyph` resolves to an empty box **of the correct size**; `expo-router/unstable-native-tabs` does not render at all; `headerLargeTitle` degrades to a web compact header. **All three failures are silent and all three preserve layout**, so no text gate, blankness gate, duplicate gate or screenshot diff can see any of them, and the frames passed every automated check while missing every icon, the entire tab bar and the native title. All five were correctly HELD by `art-director` looking at pixels, which is the only instrument that could. The general rule: **an export, preview, fallback or emulated render is the artifact minus a layer, and the missing layer is precisely the part no automated gate is watching.** So name the render target in the gate header (`device build` / `simulator` / `web export` / `deployed` / `dev`), and never grade an appearance claim against a target that substitutes for the shipping one. Store screenshots come from a device or simulator build, never from a web export. **One permitted exception, used for elevare-app 1.0 (2026-10-01), and it carries a debt:** when no Mac, simulator or device capture is reachable before a deadline, a web render may ship ONLY through `library/expo-ios-app/store-screenshot-render-pipeline.md`, where every SF Symbol is drawn by a mapped stand-in and an unmapped or blank glyph fails the frame loudly, the tab bar and status bar are drawn, the frames show what that build actually does (hidden tabs held, no unbuilt feature), `art-director` or `social-post-critic` passes the pixels, and the release record says `render target: web export + stand-ins`. **That exception opens an owner row: device recaptures replace the set with the next build or within a week of approval, whichever is first.** The owner's words that started it (*"this looks terrible as it doesn't have icons"*, relayed) asked for icons, not for the web route; the route was the conductor's choice, so the debt is the conductor's too.
  - **The archetype gate runs inside the taste gate** (art-director + design-auditor, from [ARCHETYPES.md](ARCHETYPES.md)): does the built surface actually read as the archetype declared at triage, or did it drift back toward product-tool? Point at the **one signature moment** — is it the highest-craft thing in the project, with enough quiet around it to land? Is anything on the archetype's "must not borrow" list present? And do the numeric budgets pass on that archetype's real target device (STANDARDS: LCP ≤2.5s / INP ≤200ms / CLS ≤0.1 at p75; local-service under 2s on a mid-range phone; immersive held on a mid-range Android, not the builder's laptop)? A drifted archetype is a blocker, not a note — it is the difference between work that looks like a template and work that looks like a studio.
  - **The vertical gate** ([INDUSTRIES.md](INDUSTRIES.md), owned by design-auditor + qa-verifier): walk the declared vertical's **money moment** end to end on a phone, confirm every "required" item shipped, confirm the schema type is present and valid, and explicitly check the vertical's **#1 failure** — they are listed because they are the mistakes that actually recur (the PDF menu, the call-only booking, the hidden price, the form with no phone number, the thin PDP, the buried recurring donation). Any compliance landmine named for that vertical (PHI, licensed-professional advertising rules, minors' data, Fair Housing, charitable solicitation, consent for beneficiary/client photos) goes to `compliance-counsel` **before** launch, never after.
- **★ A GATE CRITERION IS ONLY CLOSED BY AN ARTIFACT IN THE REPOSITORY THE CRITERION IS ABOUT. Anything closed by live data, by a console change, or by a commit in a DIFFERENT repo is "met, not durable" and stays open with a named owner.** elevare-app wave 4 closed criterion 17 (no internal identifier on a customer surface) in two halves: one durable (`src/lib/data.ts` stopped selecting `source`, visible in the diff, survives any reset) and one not (two `client_feed_events` rows were rewritten by migration `20260914104303`, which has **no file in that repository at all** since `supabase/migrations/` does not exist there; the repo tracks two edge functions and exactly one `.sql`, a test fixture). A database reset, a restore from yesterday's backup, or a rebuild in another environment puts a commit SHA, a migration filename and `/admin` straight back onto the customer screen, and the gate record will say it was fixed. The same wave closed another blocker with the qualifier *"durable at `77e9bc0` on Stream B's branch, not yet on master"*, which makes one product's customer-surface guarantee depend on an unmerged commit in a **different product's repo**. **The `art-director` move is the one to copy, and it is a refusal, not a note:** it scored the criterion MET on pixels and then wrote *"I will not sign the sentence that B11 is closed, full stop, without B14 attached to it ... report it as: met on the live database, not yet durable, B14 open."* Report it that way. A criterion carrying a durability qualifier is not a criterion that is closed.
- **GATE-ENVIRONMENT PARITY — every gate declares its environment + tree revision in its report header, and at least ONE gate per wave runs against the DEPLOYED artifact.** On HausAI only **1 of 8 gates tested the deployed build**; the rest ran a dev server, a localhost production build, or an out-of-repo copy — **four environments across two tree states, merged into one ledger as if they were simultaneous.** That is how a hydration failure was "found", "fixed" and "still broken" at the same time, and how two gate reports contradicted each other about a checkout disclosure: **both were true, of different tree states.** Undeclared environment turns a gate ledger from evidence into noise, and no amount of gate *quality* fixes it. The conductor assigns the environment, doesn't leave it to the agent.
  - **Weight the wave toward LIVE exercise — it is 1.76× more blocker-dense.** Measured across HausAI's 109 findings: 42% came from live-app exercise vs 48% from static review, but of the **25 blockers, 56% were live and 36% static** → blocker density **30.4% live vs 17.3% static**. And **every** "the product does not work" defect came from a live gate. Static review is not cheaper per blocker; it is cheaper per *finding*, which is not the same thing. A wave of gates that all read source is a wave that cannot discover the product is dead.
- **Failure-mode / lifecycle pass — required for any long-running product (daemon, engine, installer, packaged/desktop app), owned by qa-verifier:** don't stop at happy-path QA. Kill it mid-run, fill the disk, unplug the camera/pull the network, restart it — and confirm no leaked child processes, no destructive prune deleting everything, no dead thread reporting "running", and that every offered action (self-update, export, download) actually completes once against the real artifact. A product that "passed gates" once still shipped 6 lifecycle blockers because this pass was skipped (the full pass is in [`library/desktop-native-app/lifecycle-failure-modes.md`](library/desktop-native-app/lifecycle-failure-modes.md), moved out of STANDARDS 2026-09-06).
- **Marketing gates:** art-director (craft) + marketing-strategist (on-message, complete, honest) + a fact/claims check + **social-post-critic on the FINALS** — the full-resolution / 300-DPI files, not previews — with the client's audience described, returning SHIP / FIX / REWORK. It covers print pieces and exported decks, not just social posts ([[social-post-critic-gates-all-graphics]]). A REWORK verdict goes back to the producing agent, never into the calendar.
A gate that fails sends the item back with a precise repro/fix — it does not get waved through. **When independent gates converge on the same finding, call it out and rank that fix #1** — cross-auditor convergence is the strongest priority signal. **A finding RELAYED from one agent to another carries its evidence or the label "CLAIMED, UNVERIFIED"** — a conductor that forwards a gate's finding as fact launders an unchecked claim into a work order (a security finding relayed to a Thames Coast agent named two functions; one was already fixed and had never been a WARN). **An agent that comes back with evidence contradicting its brief has done its job — that is the behaviour to reinforce, never to override.** Two more on 2026-08-12, both correct, both changed the coordinator's mind: an agent **refused to build the per-client webhook endpoint it was instructed to build** (it would have been a cross-tenant leak — see [[client-data-never-mixes]]), and an agent **refused a brief asserting that ten of its eighteen findings were false positives** (all eighteen were real; tuning to satisfy the brief would have suppressed live credentials). **A brief's claim that findings are noise is a hypothesis to test per finding, never a filter to apply.** **And so is a brief's claim that a check ALREADY PASSED — the conductor's own verification claim is the most-trusted and least-re-checked input any agent receives.** Two agents overrode one on 2026-08-19 and both were right: a test-engineer re-ran a typecheck the conductor had reported green four separate times (`TSC_OK`) and proved the command was compiling **zero files**; a database-architect, handed a CSV the brief called properly RFC4180-quoted, went to the raw bytes, proved it was not, and recovered 14 fields the generator had truncated. Both changed what shipped. Reinforce the override; never re-issue the claim with more confidence. **★ AND A REFUSAL IS A HYPOTHESIS TOO — resolve it by reading the file, never by whose authority is larger.** On the Whyza moderation lane an admin lane was told to print *"This account has an open instant-lane review"* and **refused it as unsupportable**; the conductor checked the file and the clause was **TRUE** — the lane had conflated *"nothing files to NCMEC yet"* with *"nothing happens at all"*. The refusal instinct was right and the conclusion was wrong, and only opening the source settled it. So neither party wins on standing: a refusal that survives is one that names the file it read, and a conductor that overrides one must name the file it read. Both moves are the same move — go to Tier 1 — and "I could not establish this" remains a full-marks answer for either side. Same family: **"INCONCLUSIVE" is a first-class result** — an agent reporting "I could not establish this, here is what would settle it" has told the truth, while the same agent banking an unearned pass manufactures exactly the confidence that let three defects reach paying customers that day. Never treat an inconclusive as a non-delivery; ask what it would take to resolve it, and score it as honesty (see eval-master's maker rubric). **A static gate's "harmless / dead / safe to ignore" verdict is NOT a clearance for anything still wired into a live boundary** (a value passed to a third-party API, serialized into a request, written to a template): code-quality called asky's `customer_email: user.email` a harmless leftover and it 502'd every purchase — only real-flow qa-verifier caught it. When a static audit rationalizes away a still-wired reference, that exact path goes to qa-verifier to exercise live before ship. **For a constrained/existing codebase, give every gate the constraints brief up front** (how it's built + what not to recommend) so no gate spends itself on out-of-scope advice. **Always close a gate phase by having `eval-master` score the run and append it to `evals/scores.js`** so the improvement dashboard updates — every run, no exceptions.
**★ A FINDING CARRIES A SYMPTOM AND A CAUSE, AND ONLY THE SYMPTOM IS EVIDENCE — REPRODUCE THE CAUSE BEFORE YOU FIX IT.** This is the gap the "contradict the brief" line does not cover: the lane agrees the defect is real, accepts the stated mechanism with it, fixes that, and ships nothing. Three of Thames Coast's five taste-gate fixes had a **right conclusion and a wrong cause**, all three written by the conductor: an arrival overprint blamed on a `label.id === target` clause when measurement showed *all three* labels on, which that clause cannot produce (real cause: a flight's last `move` fires before it ends, so the final evaluation ran mid-flight and nothing re-ran after); a sibling-fade defect pinned to a line that was already correct (the writer was an unguarded `styledata` handler, and `styledata` fires during a flight because tile loads change source data); and a "signature moment buried at 390px" that measured **0.0% occluded before the fix as well as after** — what was buried was the resting and card states, which is a different fix. **The test is cheap and it is the whole discipline: remove the named cause alone and watch the symptom persist.** A cause you did not reproduce is a hypothesis wearing a finding's clothes, and it is the most-trusted unmeasured claim in any wave, because it arrives attached to a defect that is genuinely there.

### 6. SHIP — only on human sign-off
Production/outward actions are **stop-and-ask** (see the gate list). The agent stages everything and presents it; the human approves the go-live.

**★ THE GO-LIVE REQUEST IS A RECEIPT, AND THE OWNER IS THE READER — this is where the process rules get enforced, because it is the one message the conductor cannot skip and a human always reads.** §8's self-written WAVE RECEIPT was added on 2026-09-04 after the second skip and was itself skipped on 2026-09-06 (eight user-visible surfaces shipped before `art-director` saw any of them; the LEARN loop ran only because the owner asked "did you run the full playbook"). §Brief protocol ("The remedy is not more self-audit") already says the third occurrence moves the check from the actor to a **reader** — so it moves here. Every go-live request ends with these six lines, and **`SKIPPED — <reason>` is a permitted value while an omitted line is not**:
```
seam pass:   <agent who built nothing this wave> — walked <n> hops, <n> blockers
taste gate:  art-director — archetype <X> confirmed vs <direction-doc:line> · reviewed <surface> at <wave>, BEFORE commit <sha> · report at <path> · verdict <SHIP/FIX>
plan deps:   <conditional/deferred items from the plan> — discharged | deferred with owner
premises:    <n> asserted · <n> Tier-3 flagged UNVERIFIED · <n> overturned by a lane
harness:     <diagnostic routes/pages/endpoints added this run> — removed | none added
skills:      <skill> (<who read it, for what>) · … | NONE — and why the job needed none
reuse:       <library assets opened BEFORE the build> | NONE — and why nothing applied
LEARN:       eval-master <scored, incl. ≥1 maker> · retrospective <ran, receipt at <path>> · pattern-librarian <ran>
```
A go-live request missing a line is **malformed** — the owner refuses it and asks for the line, rather than reading five gate reports to discover what wasn't run. The `premises:` line was added 2026-09-07 after the Whyza moderation lane, where **ten conductor premise errors were overturned by lanes reading primary source** — a wrong table name a sibling migration had renamed, a retention question a sibling migration had already answered, an absence generalised from a truncated `tail -20`, a flat contradiction between two briefs, a "ships behind a flag that is off" that was false of the database, and a stale blocker one message from escalation. Zero of them shipped, and none was caught by a gate. **A nonzero overturn count is the system working; a zero across a whole wave means nobody re-read your facts.** A conductor cannot audit its own omission; a reader can see a blank. **Second measurement, Whyza profile wave 2026-09-06, and it is the strongest number this studio has:** the brief's own §0 carried the line *"if the evidence contradicts this brief, STOP and bring the evidence — that is a successful outcome"*, and its ERRATA records **six conductor errors, six caught, every one by a lane arriving with a measurement** (a BEFORE-INSERT trigger mistaken for any-self-write, an overstated dead end, a byte budget wrong by 25%, a "slightly optimistic" contrast note that was a live floor breach, a dead reference platform, and the archetype). On top of that: a lane **refused a "delete this row" instruction** because the precedent the conductor cited *kept* the row; a lane **refused to build photo backgrounds** and proved why (14.79:1 printed, 1.20:1 delivered); a lane **disproved a taste-gate finding** with a calibrated grep and diagnosed the false positive's mechanism; and two lanes **discarded their own greens** (a "production" hydration run exposed as dev by `unsafe-eval` in the CSP; a known-dead control that would not go dead until bundles were blocked over raw CDP *and counted*). Zero shipped, and no gate found any of them. **That single line in the brief is the highest-yield sentence in this playbook — put it in every brief you fan out, and read an overturn as the process succeeding, never as a lane being difficult.**
**★ THIRD MEASUREMENT, Thames Coast 3D map 2026-09-18 — and it finally isolates WHY the line works, which matters because "paste this sentence" is not a mechanism.** Six conductor errors overturned in one wave, plus a gate corrected by the conductor and two of the conductor's own probes discarded by the conductor; every single correction arrived as a **number that contradicted a named value** — three labels on where one clause could explain one, `0.0%` occluded where the gate premised "buried", a raw `1.437007` under a floor set from the published `1.44`, six district misresolves produced by a probe that was clicking the site header. **The invitation converts into corrections in proportion to how FALSIFIABLE the brief is.** A brief that names a cause at a specific file, line, clause or number hands the lane something it can try to remove and watch fail; a brief that says "fix the label overlap" or "make this feel better" cannot be contradicted, so the line sits in it decoratively and the wave looks obedient. So the conductor's obligation is not just to paste the sentence — it is to **write every premise in a form that can be measured false**, and a premise you cannot phrase that way is one you have not thought through. Corollary the same wave proves: the protocol is **not** a property of strong lanes. The conductor overturned a gate (the art-director asked for a control to be promoted to a gated check "because a control cannot catch drift"; measurement showed that script's control catches drift *harder*, and both checks stayed), and the conductor twice discarded its own output. It runs in every direction or it is deference with extra steps.

**★ FOURTH MEASUREMENT, the 2026-09-18 client-notification audit — three premises overturned, all three correct.** A brief naming Petal as "on custom SMTP" was contradicted by Petal's own migration quoting a live 401 refusing `RATE_LIMIT_EMAIL_SENT`; a brief naming PhyscoClosett auth as "on Inkbox" was contradicted by a live probe that delivered through Resend SMTP in 4 seconds; and the instinct to restore `send-booking-digest` was overturned by the migration that retired it on purpose plus its source queue having no writers left. Zero of the three shipped wrong, and the near-miss the same wave caught by a different means (`presence-watchdog`, reading HANDOFF before filing) belongs to the same family: **a nonzero overturn count is the tell that the process is working, never that a lane is being difficult.**

**★ AND THE RECEIPT IS ALSO A FILE, `docs/gates/<wave>/ship-receipt.md`, BECAUSE IT IS THE ONLY BARRIER IN THIS PLAYBOOK WHOSE OUTPUT LIVES IN A CHAT MESSAGE.** Every other barrier here was converted into an artifact for one reason: an actor that dies is indistinguishable from one that never ran. The go-live receipt was left as a message, and elevare-app wave 4 is the proof of what that costs: **three usage-limit wipes in about fifteen hours**, every lane dead each time, and the only state that survived any of them was on disk (`RESUME-2026-09-13.md`, the gate files, the commits). That wave shipped an OTA and two internal preview builds, and `docs/gates/wave-4/` holds a taste gate and a seam pass and **no receipt of any kind**, so no reader can establish whether the six lines were ever produced. Write the same six lines to the file at the moment you send them. Same reasoning, same cost, one extra write. **★ SECOND MISS, wave 5 of the same repo (2026-09-29), and it names the mechanism: under the owner's PURE AUTONOMY grant there is no go-live request, so the rule's trigger ("at the moment you send them") never fires.** Wave 5 deployed three edge functions and a migration and fast-forwarded `main` (3796da4 to ef19800); the conductor emitted the receipt lines in 115 separate chat messages, correctly, and still wrote no `ship-receipt.md`, and its final block arrived after the merge. **Under autonomy the file IS the go-live request: write `docs/gates/<wave>/ship-receipt.md` before the first production deploy or the merge to `main`, commit it with (or before) that change, and append each later deploy to it.** A merge or deploy with no receipt file on disk is malformed, whoever is watching. And every line carries a number: `premises: dozens asserted` is a mood, not a count.

**★ A GATE THAT CLEARS A SHIP *WITH CONDITIONS* OWES EACH CONDITION AS A NAMED OPEN ITEM WITH AN OWNER, NOT AS PROSE INSIDE ITS OWN VERDICT.** Wave 4's taste gate cleared the build on four explicit conditions and handled three of them exactly right, recording B9, B13 and B14 under "deferrals, recorded as decisions with a named owner", with the instinct stated out loud: *"a deferral that is written down is a decision, and an omitted one is a leak."* The fourth condition is the one the entire clearance was bought with (*"when the build is in the owner's hand, criteria 11, 12 and 13 get measured on it and reported back to this gate ... if it does not happen the clearance bought nothing"*), and it exists only as a sentence in the verdict with no owner and no row. **A clearance is conditional or it is not; if it is, every condition is a row in the receipt and the job stays open until each one is discharged or restated.**

**★ THE `reuse:` LINE WAS ADDED 2026-09-18, AND IT IS THE SAME DEFECT ONE STEP EARLIER.** The
`skills:` line catches a conductor who did not run an installed check. This one catches a conductor
who rebuilt an asset the library already held. Thames Coast's map wave wrote
`scripts/verify/contrast.mjs` — 936 lines — from scratch, and independently re-derived the `var()`
chain resolver, alpha compositing, the exit-2-means-did-not-check convention, and the headline
gotcha that `color-mix()` serialises to `color(srgb 0-1)` rather than `rgb(0-255)`. All of it was
already on disk in `library/ui-craft/token-resolved-contrast-gate.md` plus **two runnable gates**,
committed **2026-09-13, five days before the wave started**. Verified by git, not recalled, and the
wave referenced `library/` **zero** times across both verify scripts and its 59KB direction doc.

The cause is a sequencing defect, not ignorance: `pattern-librarian`'s own definition says to invoke
it *"when starting one (to reuse what exists first)"*, and the conductor dispatched it **only at the
end, as a LEARN closer**. Harvesting is the closing half of that agent's job; supplying is the
opening half, and the opening half is the one with no receipt.

Two honest caveats, because they change what the fix should be. The rebuilt gate came out
**materially better** than the library's (four control stages against four rows), so the miss cost
time rather than quality — which is exactly why it is invisible without a receipt, and why the
remedy is a line rather than a prohibition. And the control-first shape did propagate correctly
*within* the repo from its own `scripts/verify-map-geo.mjs`, so the instinct was right and only the
supply lookup was missing. **`NONE` is permitted and will often be honest — most jobs reuse
nothing. What is not permitted is silence, because a conductor cannot see its own omission and a

**★ THE `skills:` LINE WAS ADDED 2026-09-10, AND IT IS THE SAME ENFORCEMENT DEFECT §8 ALREADY NAMES.** "Use the skills" was written in this file, in STANDARDS, and in 68 agent definitions, and the studio still ran a full day of Whyza work — an app icon replaced, a schema-fallback test repaired, a production deploy — with **the Skill tool invoked exactly once, for `workflow-authoring`, and never again**. Measured from the session transcript, not recalled. The work was verified, but every check was re-derived by hand: `calibrated-check`'s discipline was reinvented as bespoke calibration cases, and the wrong contrast constant that had propagated through six files was found by accident during a taste gate rather than by `claims-ledger-sweep`, which exists for exactly that. So the rule stops being prose and becomes a line the owner reads. **NONE is a permitted value** — a two-line copy fix genuinely needs no skill — but it must be typed, because an omission is invisible and a typed NONE is a claim someone can challenge.

**And the line binds the SESSION, not only the sub-agents.** The failure above was not an agent skipping its own definition; the agents name their skills correctly. It was the main loop doing the work **solo** and never routing through a lane that would have loaded them. Working directly instead of delegating is often right and is not the exemption — a conductor that writes code itself is a maker for that stretch and owes the same receipt as any lane it would have spawned.

**Before staging: run `outcome-integrity-sweep`** on every path that writes, sends, charges, notifies or archives, and on any success toast, chime, `sent: true` or `200` the ship introduces. A library that RESOLVES with `{ error }` instead of throwing means the try/catch caught nothing and the success path ran unconditionally — that is how a kiosk chimed "Cash logged — $140 recorded" on a refused row.

**A specialist agent NEVER runs `git commit`.** It writes its owned paths and reports them; the conductor is the only committer, stages explicit per-lane paths, then reads `git diff --cached --stat` against the ownership table and drops every file it does not own at that moment. A commit is a shared-tree write, so the single-owner fence covers it.

### 8. LEARN — close the loop (the self-improvement layer)
This is why the studio compounds. Cadence:
- **Every gate run / substantive job — ALWAYS:** run **eval-master** to **score the run** (rubric composites per agent) and **append it to `D:\.claude\agents\evals\scores.js`** so the improvement dashboard updates — this is mandatory, not optional; it's how "the team is getting better" stays a measured fact instead of an assumption. Also run **retrospective** (encodes blind spots into agents/standards/memory) and **pattern-librarian** (harvests reusable assets).
- **Score at least one MAKER every run, not only the gates.** For the studio's first 15 scored runs every agent ever measured was a gate or a conductor, and the file sizes showed it. **The rule worked and the numbers moved, so MEASURE, never cite** — `wc -c *.md | sort -n` in `D:\.claude\agents`, makers against gates, and quote only what you just ran. Re-measured 2026-09-07: makers span 4.9 KB (`ui-designer`) to 11 KB (`art-director`); gates span 5.8 KB (`performance-engineer`) to 28.5 KB (`security-reviewer`). The gap has narrowed and inverted in places — `ui-designer` and `performance-engineer` are now the two thinnest definitions in the studio, which makes them the next scored runs, not the next assumed-fine ones. Whatever isn't measured doesn't improve. `scores.js` now carries a **maker rubric** (Craft · Brief fidelity · Distinctiveness · Honesty · Handoff); a run that scores only gates is an incomplete measurement and the dashboard now says so.
- **Route every gate finding back to its MAKER, not just the catcher.** Every defect has two owners: the agent that produced it and the gate that caught it. Encoding the lesson only into the gate hardens the net and leaves the hole — and a defect class caught a **second** time is a maker failure, not a gate success. `retrospective` owns this loop-back.
- **★ A RULE SKIPPED A SECOND TIME IS AN ENFORCEMENT DEFECT, NOT A WRITING DEFECT — convert it from an instruction into a REQUIRED DECLARATION LINE.** Restating a rule that was already written and already ignored adds bytes and changes nothing; on 2026-09-04 the §4b seam pass and this very LEARN loop were skipped on **every wave** while both were already mandatory in three places. Look at which rules this studio actually obeys: gate-environment parity and the "Breaks / invalidates" handoff field, both of which work for one reason — **their absence is visible in a report header, so a second person can see the omission.** A rule enforced only by the actor's memory is enforced by nobody, and the actor least able to catch itself is the conductor, whose output no gate reads. So `retrospective`'s move on any second occurrence is mechanical: name the report the rule belongs in, add a one-line receipt to it (`seam pass: <agent> · LEARN: <scored/ran>`), and make **SKIPPED plus a reason** an explicitly permitted answer — a stated skip is a decision, an omitted one is a leak. Prefer this to a third, louder copy of the rule.
- **★ RETROSPECTIVE LEAVES A FILE, OR IT DID NOT RUN — `docs/gates/<wave>/retrospective.md`, and the receipt names the path.** Same reasoning as the taste-gate barrier above, and it failed the same way: an agent that is never spawned is indistinguishable from one that ran and found nothing, and the job closes either way. Measured 2026-09-10 — the owner's own read of it was *"the continuous improvement agent wasn't being recognised and making the agents better"*, and he was right: across a full day of Whyza work `retrospective` was never invoked once, so not one lesson from that day reached an agent definition until he asked. The self-improvement layer is the step with **no downstream symptom** — skipping a gate breaks a product and somebody notices; skipping LEARN costs nothing today and compounds silently, which is precisely why it needs an artifact rather than good intentions. A missing file keeps the job open. `SKIPPED — <reason>` in the file is a permitted receipt; an absent file is not.
- **When a lesson recurs or a gap appears:** **skill-forge** turns the pattern into a real installed skill; **agent-architect** creates/refines an agent to own it.
- **★ EVERY AGENT NOW CARRIES ITS OWN SKILL BLOCK — regenerate it, never hand-edit it.** As of 2026-09-10 all **68** agent definitions end in a generated `SKILLS:BEGIN/END` block naming the skills that agent owns, so the wiring no longer depends on anyone reading SKILLS-MAP.md and choosing to follow it. Between them the 68 cover **all 207** installed skills, with zero unowned and zero dangling references — verified by parsing the blocks, not by trusting the map. The assignment is seeded from SKILLS-MAP's routing lines plus whatever each agent already named, so hand-written sweep protocols (security-reviewer's, qa-verifier's) survive untouched outside the block. When a skill is installed or an owner changes, edit **SKILLS-MAP.md** and re-run `python D:\.claude\agents\wire-agent-skills.py` (`--check` reports coverage and writes nothing), then copy the `.md` files to `C:` — **`C:` is the copy that loads, and a block that exists only on `D:` has never been installed** ([[c-drive-is-what-claude-actually-loads]]).
- **Periodically (studio upkeep):** **memory-curator** consolidates/prunes so the ruleset stays sharp instead of bloating.
Then ITERATE — a measurably sharper team runs the next job.

## Brief protocol (every conductor SENDS this) — the mirror of the handoff protocol, and the hole it closes

An agent's RETURN has had a required format for months. A conductor's SEND has never had one, and that asymmetry is where the studio's defects are actually made. Measured on the Whyza landing lane (2026-09-06): the conductor made **13 wrong statements in one job** — a wrong archetype, a stale test baseline, wrong route arithmetic, a file called orphaned that a test imported, a stale line number, a tree reported green that a sibling had already broken — and **every one was caught by a specialist reading primary source it was never told to read.** Zero shipped. That is a catch rate wearing the costume of a process.

**The remedy is not more self-audit.** Self-audit has been prescribed to the conductor three times and converted into a self-written receipt after the second; the third occurrence is this one. You cannot repair a verification defect by assigning more verification to the actor whose verification is failing — a receipt nobody reads is the same failure class as a comment asserting a control. What worked all 13 times was **a different actor reading the source**, so the check moves to the reader and becomes a field:

1. **PREMISES — every fact the brief asserts, each as `source · tier · measured when · which lane owns the file that can change it`.** A premise is anything the receiver would otherwise take as given: the archetype, the test baseline, the route count, "X is orphaned", "the tree is green", "that call is at line N", "the auth flow uses OTP". Tier per STANDARDS §Verify (1 = the live system, 2 = a command you just ran, 3 = a doc, a memory, a comment, another agent's report, your own earlier message). **A premise you did not measure yourself this session is Tier 3 and must say so.**
   - **★ ON ANY VISUAL SURFACE THE ARCHETYPE IS A NAMED, MANDATORY PREMISE ROW, and it is the one the conductor must not answer alone:** `archetype: <X> · read from <path:line> "<the quoted binding line>"` — or, when the repo genuinely has no direction doc, `archetype: PROPOSED, no direction doc found — art-director confirms before any design brief fans out`. **A brief with no archetype row is malformed and the receiving lane refuses it**, exactly as a go-live request with a missing receipt line is refused. This is now the fourth place the "read it, don't coin it" rule is written (here, `ARCHETYPES.md` rule 1, `art-director.md`, `delivery-lead.md`) and a fifth copy would change nothing — **and the same conductor drifted the same way on two different surfaces of the same repo on the same day** (the landing lane's early-access page, bound `"E with one A component"`, and then the profile, bound `"E, hosting user-authored maximalism"`), which is what makes it an enforcement defect rather than a wording one. What failed on Whyza's profile wave 2026-09-06 was the ownership: `ARCHETYPES.md` rule 1 and `art-director.md` **both already said `art-director` owns the archetype call**, and the conductor wrote the call into §4 of its own brief under the header *"art-director owns the final call; build to this"*, so the owner first saw it at the gate — after eight lanes had built to it. The gate then found the project's own `docs/design/DIRECTION.md:23` bound that surface as **"E, hosting user-authored maximalism"** and `:27` pre-committed to blocking *"toward product-tool everywhere"* — the brief had written down as a directive the precise drift the document promised to block. A row a reader can see blank is the only version of this rule that has ever fired.
2. **Mark every Tier-3 premise the work stands on `UNVERIFIED — CHECK THIS FIRST`,** and the receiving agent re-reads it from source before acting. That is the gate, not a courtesy. Pair it with the line that already belongs in every brief — *"if the evidence contradicts this brief, stop and bring the evidence; that is a successful outcome"* — which is precisely what produced all 13 catches, six times over on this one job.
3. **A MEASUREMENT HAS A SHELF LIFE, and in a concurrent tree it is minutes.** Three of the 13 were facts verified *correctly* that went stale before the agent acted: an auth flow another lane rewrote the same day, line numbers that moved twice in one session, a tree that went red under a sibling. So a premise carries its timestamp **and the lane that owns the file it lives in**; the receiver re-checks any premise whose owning lane is still writing. Same fence as the readers-too rule under Parallelization — a brief is a reader of a moving tree, and its stale reading outlives the wave.
3b. **ONE RULE, ONE OWNER: when two lanes' work touches the same rule (a predicate, a constant, a route builder, an enum), the brief names the ONE lane that defines it, the ONE file it lives in, and that every other lane imports it.** Third occurrence of the class (money-slice RPC 2026-09-02, Whyza funnel 2026-09-05, memory `cross-wave-seam-needs-an-owner`): elevare-app's "on a web plan" rule for seam-pass F1 was written three times in the build-24 working tree (paywall inline, the Assistant's `topUpHref`, Home's door) before a lane collapsed it into `onWebPlan` in `plan.ts` with a count guard (`tests/design/web-plan-rule.test.mjs`). That collapse is the behaviour to reinforce; the brief is where it should have started. A count guard over a line-bounded regex misses the same rule wrapped across lines, so say so in its header.
4. **FINDING and SUGGESTED FIX stay visibly separate.** A finding arrives with evidence; the fix stapled to it arrives with your authority and nothing else, and a lane that trusts it stops looking.
4b. **SHARED RESOURCES AND IDENTITY, ONE LINE EACH, IN EVERY BRIEF THAT CAN TOUCH THEM:** `commit: Elevare Studio <elevarecreativ@gmail.com>, no Co-Authored-By` · `browser: own tab only; claimed tabs <ids>` · `live writes: sentinel ids only (<the project's QA id>)`. All three were missed on the 2026-10-09/10 Lit on Fire run (48 trailered commits, a staged EasyPost form navigated away, a QA order that held a real coin), and a lane cannot honour a constraint the brief never named.
5. **Rank premise errors above instruction errors — they are not the same defect.** A wrong *instruction* ("use this grep") costs one lane a re-run and that lane usually catches it. A wrong *premise* is copied into every downstream brief and is caught only if somebody reads a document they were never pointed at. Whyza's archetype error put the product-tool reference set (Linear/Stripe/Vercel) into every design brief on a job whose own `docs/design/DIRECTION.md` had pre-committed to *blocking drift toward product-tool at the gate* — it survived until `art-director` read the direction doc instead of the brief. Spend the verification budget on the premises.

## Handoff protocol (every agent returns this)
A subagent's final message is a **report to the conductor**, not chat. Keep it tight:
1. **Done:** what was produced/changed (file paths). **Plus a `claims:` line — one row per user-visible sentence you added that promises a DESTINATION, a CAPABILITY, a NOTIFICATION or a CONSTRAINT, each with the `file:line` that implements it, or the literal `claims: none`.** This is the §4b claims ledger moved from the barrier to the author, because at the barrier it is a different agent reconstructing your intent, and by then the sentence has shipped. Fourth occurrence of this class, 2026-09-06: PhyscoClosett told buyers on **four surfaces** that they would get an order email — only one mail is ever sent, and it goes to the seller. `conversion-copywriter` and `brand-copywriter` have carried this rule since the first occurrence and it kept failing, which is the tell that it was never enforced by anything but the author's memory; and copy is frequently written *inline by a builder* who never read those files at all, so the field binds **every agent that ships a sentence**, not the copy specialists. A row you cannot fill is not a copy note — it is a `DEAD:` entry for field 1 or a feature request for the conductor.
2. **Evidence:** how it was verified (what was rendered/tested/measured; console clean?) — and **open with the ENVIRONMENT and TREE REVISION you verified against**: `deployed <url> @ <sha>` / `localhost prod build @ <sha>` / `dev server @ <sha>` / `out-of-repo copy at <path>`. One line, before the findings. Without it a ledger silently merges gates that looked at different products (see §5). **A GATE's header carries one more field on the same line — `tree frozen: yes` or `no — still writing: <agents>`** — because the readers-too fence (Parallelization rules) has now been skipped twice: a design gate watched its target grow 739→809 lines mid-audit, and Whyza's code-quality gate saw three different typecheck results in fifteen minutes while other agents were still building. A third louder copy of the rule would change nothing; a missing field in a header is visible to someone other than the actor, which is the only enforcement that has ever worked here. The conductor assigns the freeze; a gate that finds itself reading a moving tree says so, pins its findings to quoted anchors rather than line numbers, and requests a re-run — that is a correct result, not a slow one. **★ AND `tree frozen: yes` IN YOUR BRIEF IS THE CONDUCTOR'S CLAIM, NOT A FACT — you measure it, because the conductor is the one actor who cannot see its own lanes finish.** On PhyscoClosett two concurrent gates were both told the tree was frozen and it was not; the security gate **detected a design gate writing seven files mid-audit and reported that instead of reporting against a moving target** — that is the behaviour to copy, and it is why its findings survived and the other's would not have. The measurement is cheap and it is the whole check: `md5sum` (or `git rev-parse HEAD` + `git status --porcelain`) over your target set when you start and again before you write a single finding. If it moved, say so in the header (`tree frozen: no — <n> files changed under me`), re-derive anything you had concluded, and ask for the re-run. A stale finding is not a small error: it costs a real fix cycle, and in `retrospective`'s hands it becomes a permanent rule about a hole that no longer exists.
**★ AND THE FREEZE LINE MUST NAME THE PATHS DELIBERATELY HELD UNSTAGED, because two correct behaviours collide there and manufacture a false blocker.** The conductor is required to stage by explicit path and never by wildcard (§4b, delivery-lead), which by construction leaves a live lane's finished-but-unowned work sitting **untracked**; a gate that reads bare `git status` then sees untracked files under `src/` and reports them as a ship blocker. Thames Coast 2026-09-18: exactly that, and neither actor was wrong in isolation. **Fix, one field each way.** Conductor: the freeze declaration reads `tree frozen: yes — except <paths>, owned by <lane>, untracked ON PURPOSE`. Gate: **scope to your assigned path set and to `HEAD`, never to `git status` as a proxy for "what this wave changed"** — untracked is a statement about the conductor's staging discipline, not about the product, and "files exist that I was not given" is a question for the conductor before it is ever a finding.
3. **Breaks / invalidates for others** *(required in any parallel wave — the seam detector)*: what my change makes untrue for someone else's work — a route's render/cache mode, a prop or field I removed, a contract/constant I renamed, a file I moved, a control I un-mounted, a copy claim I made about a surface I don't own. "Nothing" is a valid answer, but it must be stated deliberately, not omitted. Every serious defect in a large parallel run is something an agent broke for a peer and never said. **Before you fill this field in, READ THE OTHER LANES' ARTIFACTS ONCE** — their migration, their probe, their route. It is a five-minute step and on the Whyza reposts wave it caught a sixth seam defect **by accident**: an API lane reading a sibling's SQL probe for an unrelated citation discovered its own route never checked the audience clause that probe was testing, so a legitimate reader hit a raw 42501 and an opaque "You can't do that." Make it deliberate rather than lucky — you cannot state what you broke for a peer whose work you have never opened. **★ SECOND OCCURRENCE 2026-09-06, and this time the out-of-scope read produced the most serious defect of the whole wave**, so per §8 it becomes a declaration rather than a louder instruction: field 3 opens with **`read: <the sibling artifacts you actually opened> @ <md5 or mtime>`**, and `read: none` is a permitted answer that a reader can see. **The hash is not bookkeeping — a cross-lane claim with no hash behind it is unfalsifiable by its reader, and in a live wave it expires in about TEN MINUTES.** Whyza's profile wave produced three stale cross-lane reports in one run, in both directions: the migration lane read the catalog before the studio fixed it, the studio lane read the migration before the migration fixed it, and a build lane reported a broken `href` the renderer had already repaired. All three were caught only because the conductor happened to re-read the tree; none was wrong when it was written. **So a fact about a file you do not own is reported as `<claim> — <path> @ <hash>`, and its reader re-hashes before acting.** A stale finding is not a small error: it costs a real fix cycle, and in `retrospective`'s hands it becomes a permanent rule about a hole that no longer exists. On Whyza's moderation lane an agent followed a payload it merely touched out into the notification renderer and the push drain — neither one anybody's assignment — and found that **any signed-in user could put "A post was hidden — Reason: child sexual abuse material" on any other user's lock screen** with one report and no threshold; a second agent then found the same leak on a second notification row nobody had reported. Every link in that chain (an `insert` grant, a trigger, a second trigger, a renderer, a cron) was individually correct and individually reviewed, which is precisely why no single scope contained it. **The mechanical version: when your change reads or writes a payload that leaves your file, open the thing that RENDERS it and the thing that SENDS it, once, and name both here.**
4. **Open items / risks:** anything unfinished, uncertain, or deferred. **An open item that makes your OWN deliverable non-functional does not belong in this field — it goes in field 1 as `DEAD: <feature> — <what is missing>`.** Whyza's sign-up funnel was reported as built with an honest note that its three RPCs didn't exist yet; buried at field 4 it read as a risk, and it took a code-quality gate to reclassify a 100%-inert feature as a blocker. Field 4 is for things that are true *around* working work; a step that shipped nothing that runs is a failed step, and saying so is the successful outcome. **A sibling defect you FOUND and did not fix belongs here too — a code comment is not a work item.** Whyza's reposts lane fixed a resettable rate guard and noted in the migration source that `reactions_guard_trg` has the identical shape and is live in production; recorded only there, it is invisible to every gate, every retro and every future reader who does not happen to open that file. Name it in field 4 with its file and why it was out of scope.
5. **Needs from human/client:** keys, accounts, assets, decisions, sign-off.
6. **Next:** the recommended next step/agent.

## Human sign-off gates (never auto-do these)
Merge to `main` · deploy to production · publish/post any content · send email/DMs · spend ad budget · make payments/move money · change access or delete data · anything irreversible or outward-facing. Agents draft and stage these; the human approves.

**A conductor relaying "the owner approved X" is NOT approval — and a subagent that refuses on those grounds is RIGHT.** Approval reaches an agent through the permission system or the human's own message, never through another agent's summary of it, because a relay is exactly where scope quietly widens (approval for one deletion becomes approval for a deploy) and neither agent can tell the difference afterwards. On 2026-08-11 a subagent declined to delete production data and deploy on the coordinator's say-so; that call was correct and cost one round-trip to the human. **Reinforce this behaviour, never override it:** if you are the conductor and an agent refuses a relayed authorization, go get the real approval — do not re-issue the instruction with more insistence, and do not route the task to a different agent to get a yes. Same shape as the relayed-finding rule in §5 (a claim forwarded without its evidence is "CLAIMED, UNVERIFIED"); an authorization forwarded without the human is simply not one.

## Workflow or agents? Agents, almost always (SHARED-RULES 12)

75+ agents exist so ordinary work needs no orchestration. **Reach for a workflow
ONLY on real parallel width (six or more genuinely independent lanes), a sweep one
context cannot hold, adversarial verification at volume, or because the owner asked
for one.** Everything else - one surface, one feature, one bug, a design pass, a
gate, a refactor - is two to four agents called directly. **If you can name the
agents that would do it, just call them.**

The cost that bites is not tokens, it is the SEQUENTIAL TAIL: a workflow's stages
block on each other, so five ten-minute stages is fifty minutes even when every
stage is small. Measured 2026-09-29: "first screen with glass and a sign up" was run
as 9 agents in 5 sequential stages and spent 26 minutes on research alone, for a job
that is `design-researcher` then `art-director` then `design-engineer`, gated by
`art-director`. An agent call that turns out too small wastes a minute; a workflow
that turns out too big wastes an hour.

## Parallelization rules
- Fan out anything independent (multiple assets, multiple review dimensions, multiple pages).
- Barrier only when the next step genuinely needs all prior results (e.g. assemble the campaign once all assets exist).
- Isolate file-mutating parallel agents (separate worktrees) so they don't collide. **Parallelize by file, not by task:** a single large shared file (e.g. a monolithic `HOMEPAGE.html`) can't be safely split across concurrent editors even in worktrees — the conductor keeps it single-owner and only fans out file-isolated modules. Single-owner may **transfer** mid-wave (e.g. conductor makes the core edits, then hands the whole file to one builder for the mechanical pass) — ownership must be exclusive at every moment, not necessarily fixed for the wave, and the handoff is explicit.
- **Gate agents that normally APPLY their own fixes (design-auditor, security-reviewer, code-quality) must run REPORT-ONLY when they share a single file.** Fanning five fixing-gates over one `index.html` (or any single shared source) collides and clobbers — keep them report-only and have the conductor serialize every fix onto the single-owner file. This kept asky's 5-gate wave over one `index.html` collision-free; it pairs with the constraints brief (give every gate "how it's built + what not to recommend" up front so no gate spends itself on out-of-scope advice).
- **The single-owner fence covers READERS, not just writers — never launch a gate against a file you are still editing.** A design gate watched its target grow 739 → 779 → 789 → 809 lines mid-audit because the conductor was applying security fixes to the same file at the same time; every finding it produced described a revision that no longer existed by the time it reported. A gate is a reader, and a reader of a moving file is auditing a product nobody will ship. The conductor freezes the file (or finishes the edit) *before* the gate starts — same fence as §4b, applied to gates. The gate's own defence, which worked here and is now the standard: **pin every finding to a content hash + quoted anchor strings instead of line numbers, state that the file moved, and request a re-run.** That is a correct result, not a slow one.
- **★ THE OWNER'S REAL CHROME IS ONE SHARED, SINGLE-OWNER RESOURCE.** Only the conductor drives existing tabs in `mcp__claude-in-chrome__*`; a lane that needs a browser opens its own tab and closes only that, or uses the built-in browser or headless Playwright. A tab holding a staged, unsubmitted form (a support ticket, a DNS record, a console setting) is claimed: put its tab id in every brief as "do not touch". On 2026-10-09 the Lit on Fire PWA lane navigated away from a filled EasyPost support form the conductor had parked for the owner, and it had to be refilled.
- **★ CLOSE A WORKTREE WAVE BY FAST-FORWARDING THE PRIMARY CLONE AND REMOVING THE LANE WORKTREES.** Lanes push from their worktrees, so the clone that memory and `CLAUDE.md` name as "the local clone" stays at whatever it was when the wave started. After the 2026-10-09/10 Lit on Fire run, `D:\Lit-On-Fire-Coins` was **22 commits behind origin** with **20 lane worktrees** still on disk (`D:\_litonfire-*`, `D:\_lof-*`); the retrospective first read the stale clone and could not find the QA guard the run had shipped. Last integration step: `git -C <primary> pull --ff-only`, `git worktree remove` each lane once its branch is merged, then `git worktree list` shows one line.
- **Packaging is a barrier step — never rebuild a shipped artifact (zip, bundle, installer, gallery) while any agent is mid-flight in a file it contains.** An interim package silently captures in-progress state and can be handed off as final. The conductor rebuilds the artifact only after every owner of a contained file has reported done (an interim zip on a portal run did capture a half-edited shipped file before this was caught).
- **A report-only agent that delegates to its OWN child agents fires a confusing first "done" notification BEFORE its real report — don't treat that first ping as failure.** The parent momentarily notifies with a meta-message (e.g. "waiting for teardown agents") while its children finish; the synthesized content arrives right after. Concluding the agent failed on that first notification wastes a whole re-run cycle — wait for the real report.
- **Async subagents can stall on the ~600s stream watchdog — don't lose the work; take over and resume.** Early in a session, spawned agents sometimes die on a stream-timeout before reporting (2 dead on the Coffee Baby build); later waves of 3 and 6 ran fine, so it's intermittent, not fatal. Recovery pattern when an agent goes silent past the watchdog: (1) treat it as dead, don't wait indefinitely; (2) check its **partial on-disk output** — a stalled agent has usually written real files; (3) resume from that state or have the conductor finish the step directly (a solo fallback shipped the Coffee Baby build), then re-run the gates on the result. Never restart a stalled build from zero without first inspecting what already landed.
  - **⚠ CORRECTED 2026-08-06 — the "0 bytes + stale mtime = dead" heuristic DOES NOT WORK in this harness. Do not use it.** It was written here, and two agents still died undetected on the HausAI run for ~7 hours. `eval-master` then measured why: **65 of 138 task output files on this machine are 0 bytes regardless of outcome (re-measured 2026-09-18: 252 of 1393, 18.1% - the ratio moved, the conclusion did not)**, and an agent that completed *successfully* left a 0-byte output with the same mtime as one still running. The heuristic returns **the same reading for a healthy agent and a dead one** — it is not a weak signal, it is not a signal, and believing it is worse than knowing you have none. Still true: never tail the JSONL, which can re-trigger the read stall.

   - **★ THE LIVENESS SIGNAL THAT ACTUALLY WORKS, MEASURED 2026-09-18, AND IT COVERS THE CASE THE OWNED-TREE PROXY CANNOT.** The owned-file-tree proxy works for a lane that writes files and gives **nothing at all** for a read-only gate agent. On the Thames Coast map wave a `performance-engineer` gate ran **50 minutes with no readable signal of any kind** while its `.output` file sat at 0 bytes. The signal is the subagent's own transcript, and you read its SIZE, never its contents:
     `<user home>\.claude\projects\<cwd-slug>\<session-uuid>\subagents\agent-<agentId>.jsonl`
     **`stat` it. Do not read it** - reading the JSONL is what re-triggers the read stall, and `stat` never touches content. A live agent's transcript grows on every tool call and assistant message; a finished or dead one is frozen. Measured on that silent perf gate: **1,978,073 to 2,312,981 bytes in 45 seconds**, i.e. unmistakably alive, at a moment when every other available reading said nothing. Calibrated against a deliberately read-only agent with no write tools (260,440 to 424,007 bytes over 84s while alive, frozen the instant it completed) and a known-dead sibling frozen at 703,444 for three minutes, with every `.output` file reading 0 throughout.
     **The signal is BURSTY** - it advances per tool call and plateaued for 16 seconds mid-run while alive - so keep the interval floor above the longest plausible quiet turn. Each agent also has `agent-<agentId>.meta.json` carrying `agentType` and `description`, so one listing of that directory gives the whole fleet with lane names and a staleness number attached. **That replaces "ask the human" as the fallback for a read-only agent.**
  - **What to use instead: progress in the agent's OWNED FILE TREE.** A working agent touches the files it was assigned; a dead one stops, whatever its transcript or report file does. So **pin each agent's owned paths in the brief** (you already do this for file isolation — reuse it as the liveness probe) and poll mtime across that set. **Be honest that this is a proxy, not a liveness API** — an agent thinking hard, reading, or running a long build also touches nothing. Treat a stalled owned-tree as *ask, don't assume*: surface it to the human rather than silently taking over work that may still be in flight. On HausAI the only thing that actually caught the deaths was the human, which is precisely the failure this bullet exists to prevent.
  - **Every brief demands INCREMENTAL WRITES — an agent that holds work in memory until "done" has produced NOTHING if it dies.** A dashboard-API agent ran ~20 minutes, was killed by a user interrupt mid-turn, and left zero bytes on disk; its relaunch, told to write files as it went, lost nothing to the same risk. Holding work back also silently defeats the owned-file-tree liveness probe above (an agent that writes nothing until the end reads as dead the whole run). Put it in the brief explicitly: create the target files early, write each unit as it's finished, never batch the whole deliverable for the end.
  - **A USER-STOPPED agent is CANCELLED, not stalled — the take-over-and-resume pattern above does NOT apply.** When the human interrupts/stops an agent wave, treat every stopped agent as intentionally cancelled: do not re-spawn, resume, or quietly re-run the work; salvage on-disk partials only if the user asks, and wait for an explicit new request before launching that work again. (The harness also refuses to resume user-stopped agents — a re-spawn attempt just wastes a cycle and overrides the human's stop.)
  - **Image-heavy gate agents are the highest stall risk — don't fan out multi-PNG reads.** Tasks that Read several large PNGs (print-ad taste/design/claims gates) reliably starve the stream watchdog (3 gate agents each asked to Read 3 PNGs; all 3 produced 0-byte output and died past 860s on the Traway Home ad). Mitigate: give each image-reading agent **one image at a time**, or have the conductor run image-based gates **inline** (it can Read PNGs directly without the subagent stream layer). Prefer text-summarized briefs over shipping raw images into a subagent.
- **Standard pattern for any parallel build/fix wave (do this every time):** (1) assign each agent a disjoint set of files it exclusively owns — no two agents touch the same file; (2) before fan-out, **pin every cross-agent wire contract** (fetch request/response shapes, function signatures, DB columns, event payloads) in the brief so producers and consumers agree without seeing each other's code. This combo shipped a 6-agent fix wave with zero contract-seam breakage; skipping the pinned contract is how a green build hides mismatched request/response shapes across agents (see [[parallel-wave-contract-seams]]). Still do a real round-trip QA after — a green build/tsc does not prove the seams line up. **Extend the fence to every append-only shared sequence: PRE-ASSIGN each agent its migration numbers (and any other globally-ordered id — seed ranges, port numbers, feature flags) in the brief.** Twelve agents wrote migrations 0022–0027 in one tree with zero collisions purely because the numbers were handed out up front; agents left to pick their own always converge on the next free integer. **And give any agent that builds while another serves a SEPARATE build output dir** — a `next build` and a `next dev` sharing one `.next` on Windows fails with `PageNotFoundError`/ENOENT on every route and destroys in-flight work; wire `distDir: process.env.NEXT_DIST_DIR || ".next"` in `next.config.mjs` and have builders run `NEXT_DIST_DIR=.next-build`. Same class for any tool with one default working dir (Vite `dist`, Playwright artifacts, coverage output).
- **After a parallel PLANNING/architecture wave, RECONCILE to ONE canonical contract before any builder runs — the applied artifact is the source of truth, not the planning docs.** Independent planning agents invent divergent names for the SAME entities: on the Cities-network build the db/payments/product docs each coined different tables (`city_business_subscriptions` vs `city_businesses`+`sponsored_categories`; `city_celebrations` vs `celebrations`; `city_posts.boosted_until` vs a `post_boosts` row), different ledger shapes (`stream`/`kind`/`related_id`/`metadata` vs `source`/`source_id`/`stripe_object_id`), and different pricing keys (`business_featured` vs `directory_featured_monthly`). Pinning wire contracts (bullet above) is NOT enough when the underlying nouns disagree. The barrier step: the conductor (or database-architect) produces a single **CONTRACT.md marked AUTHORITATIVE, pinned to what is actually DEPLOYED** (query the live schema — `list_tables`/`information_schema` — not what the docs claim), listing a deltas-from-each-source table so every builder codes to THAT one file. Planning docs become historical; the applied DB wins on every disagreement.

`product-strategist` (+ `business-strategist` if a venture) → design track (A) in parallel with data/back track: `database-architect` → `backend-engineer` → (`payments-engineer` / `ai-engineer` as needed) → `frontend-builder`/`design-engineer`, with `devops-engineer` on CI/CD + environments/secrets → **gates incl. code-quality + test-engineer** → `compliance-counsel` (privacy/ToS/cookie before any data collection) → `docs-writer` → `launch-engineer`/`devops-engineer` deploy (sign-off) → `analytics-engineer` instruments product metrics post-launch.

**C. Feature addition** (existing product)
`codebase-navigator` (if unfamiliar) → `ux-designer`/`product-strategist` (scope) → right engineer builds → `test-engineer` → scoped **gates** → `launch-engineer`.

**D. Bug fix**
`codebase-navigator` (locate) → `test-engineer` (write a failing repro test) → engineer fixes → `qa-verifier` → ship. The test stays so it can't regress.

**E. Redesign / craft level-up**
`design-researcher` → `art-director` (direction) → `ui-designer` → `design-engineer` + `motion-designer` → **5-gate parallel wave: `design-auditor` + `art-director` + `performance-engineer` + `security-reviewer` + `code-quality-engineer`** → ship. Run all five concurrently and reconcile convergent findings before shipping — a redesign touches tokens, fonts, and imports app-wide, so it needs the perf/security/code gates too, not just the taste pair. Audit the token/CSS file itself (contrast tokens as text, self-slop, faux-bold, dead scale-tokens, hot-route imports), not only rendered pages. See [[redesign-integration-playbook]].

**F. Marketing campaign / launch kit** — *bounded* campaign. (For an **ongoing, always-on content engine** rather than a one-off campaign, the conductor is **`content-engine-lead`**: it owns pillars → batch-production workflow → per-platform cadence → scheduler/auto-poster wiring → the living editorial calendar → a measure/iterate loop, optimizing continuously against reliability / credibility / conversions, and conducts the same content pod below between and across campaigns. The **`social-growth-strategist`** (the "social media master") feeds both this campaign and the ongoing engine with the real-time growth layer: rotating per-niche hashtag sets, optimal-timing windows [sharpened by the account's own IG/Meta Insights + Pixel over time], live trend picks with honest brand adaptation tied to the offer, and feature-hinting so posts spread AND convert — social-media-manager and content-engine-lead slot its brief into the calendar/queue.)
`marketing-strategist` (strategy + calendar) → `brand-strategist` (message) + `brand-identity-designer` (look, if needed) → `conversion-copywriter` → **parallel creative:** `graphic-asset-designer` + `video-producer` + `motion-ad-director` (scroll-stopping animated ads — kinetic loops / product reveals / motion graphics) + `ai-media-producer` + `presentation-designer` → **parallel channel plans:** `social-media-manager` (+ `social-growth-strategist` supplying the hashtag/timing/trend/feature-hint growth layer) + `email-marketer` + `seo-specialist` + `paid-ads-specialist` → `marketing-analyst` (tracking) → **marketing gates** → **ship the Desktop preview gallery** (`node D:\.claude\agents\tools\build-gallery.mjs` → `%USERPROFILE%\Desktop\<Project>-Marketing-Assets.html`; base64, self-contained, one preview+download surface for the owner — a required deliverable for every marketing job, see [[marketing-asset-gallery-staple]]) → sign-off to publish. **For an existing client, step 0 is: read the real brand tokens from the LIVE SITE SOURCE and check the client's own repo for prior marketing work — never design from memory or stale repo templates** (see STANDARDS).

**G. Single creative asset** (a reel / deck / graphic set / logo)
Straight to the producer (`video-producer` / `motion-ad-director` for an animated ad / `presentation-designer` / `graphic-asset-designer` / `brand-identity-designer`) with brand + copy inputs; `ai-media-producer` supplies generated media; `art-director` gate → deliver.

**H. Content / SEO program**
`seo-specialist` (keyword→page map + briefs) → `conversion-copywriter`/`brand-copywriter` (write) → `graphic-asset-designer` (visuals) → `launch-engineer` (structured data/sitemap) → `marketing-analyst`.

**I. Research / strategy**
`business-strategist` (market/venture) or `design-researcher` (design benchmark) or `product-strategist` (product) — grounded in the research skills (deep-research, market-research, exa-search) → decision-ready report.

**J. AI feature** (chat, generation, agent, RAG)
`product-strategist`/`ux-designer` (shape) → `ai-engineer` (reads `claude-api` first) → `backend-engineer` (serve it, keys server-side) → `test-engineer` (evals) → `security-reviewer` + `performance-engineer` (cost/latency) → ship.

**K. Fix/upgrade an existing/unknown repo**
`codebase-navigator` first (map + conventions + change site) → then whichever playbook fits.

**L. Productized client engagement (how the studio makes money)**
`offer-architect` (define/price the packaged offer) → `cold-email-specialist` (cold acquisition: ICP + list → hyper-personalized sequence → deliverability setup on a separate sending domain; opens the funnel, drafts only) → `sales-closer` (discovery → proposal/SOW → close on every reply; drafts only, human sends/signs) → `client-partner` (onboarding + gather inputs) → **the right build/marketing playbook above** (delivery) → `client-partner` (handoff + walkthrough + the next logical project + referral/testimonial) → capture a **case study** (proof for the next sale). **There is no recurring add-on to propose** — Elevare sells no care plan, retainer, maintenance plan or content subscription; the recurring revenue IS the invoiced percentage, and it grows when their site sells more, so the real follow-on is helping them sell more or quoting a genuinely hard ask as a flat-price project (BP §2). **Cold outreach protects the primary domain** — cold email never sends from the transactional domain (see cold-email-specialist).

**M. Grow the studio's own pipeline (dogfood)**
Run playbook **F (marketing)** on the studio itself: `offer-architect` (the offers) → `marketing-strategist` (positioning + funnel) → site + content + lead-gen, with past work as case studies. Add a **direct-outbound engine** in parallel to inbound: `cold-email-specialist` (build the studio's ICP list → warm a separate sending domain → hyper-personalized cold sequence to target niches/local businesses → replies to `sales-closer`). Your own marketing is the first pipeline — a marketing studio with no marketing running is the #1 miss — and cold outbound is the fastest lever to book calls before inbound compounds. **Stand up the always-on content engine, not just launch bursts:** `content-engine-lead` owns the studio's ongoing engine (pillars → batched weekly content → scheduled cadence → measure/iterate), so the pipeline keeps filling between campaigns and the studio's authority/proof compounds — reliability, credibility, conversions as standing goals rather than campaign-only pushes. `social-growth-strategist` feeds the engine the daily/weekly growth-and-trend optimization pass (the "Social Autopilot"): fresh hashtag sets, timing windows sharpened by the account's own Insights/Pixel data, live trend picks adapted honestly to the offer, and rotating feature-hints — so the always-on content also spreads and converts, not just ships on cadence.

**O. Retiring a route / deleting a feature** (the reverse of C, and it has its own defect class)
Deleting is treated as the safe direction of travel and it is not. Conductor: `delivery-lead`; makers `backend-engineer` + `database-architect`; gate `security-reviewer`.
- **★ "Did anything still IMPORT the deleted code?" IS THE WRONG QUESTION. The controls that died were not imported by anything else — they were GUARDING something else.** Whyza retired `/api/waitlist/**` on 2026-09-06; the routes carried the Turnstile challenge and the rate limiter, and nothing at the database moved. `supabase/migrations/0013_waitlist_rpcs.sql:148/191/228` still `grant execute … to anon` on `waitlist_subscribe/confirm/remove`, and no later migration revokes it, so an anonymous caller can still insert a third party's email and be handed confirm + unsubscribe tokens — with the human check and the rate limit now gone. The migration's own line 44 says it out loud: *"These three functions are the door."* The author documented the boundary; the deleter never opened the file.
- **So the deletion is not done until you have enumerated what the deleted code was the ONLY caller of, and retired that too:** grants and column privileges, RLS policies, triggers, cron / `pg_cron` jobs, webhook endpoints and their event subscriptions, edge functions, queue consumers, scheduled tasks, feature flags, env vars and API keys, DNS records, storage buckets. Each one is a separate retirement with its own migration or console change.
- **Import-graph checks are necessary and not sufficient — and run them for real.** A file is not orphaned because it looks unused: `src/lib/turnstile.ts` was called orphaned and `tests/unit/turnstile.test.ts:2` imports it; deleting it would have broken a green suite. Grep the whole tree including `tests/`, and prove the check works (see `calibrated-check`).
- **Sweep the copy in the same change.** Retiring the feature retires every sentence that sold it, on every surface, now — not in a follow-up (STANDARDS §Claim–reality parity).
- **★ `git rm` DOES NOT UNDEPLOY. A deployed artifact outlives the source that produced it, and it stays publicly callable.** Fanta's gift cards were removed on 2026-09-13: page, route, nav entry, `config.toml` entries and all three edge functions deleted from the repo, committed, pushed, deployed green. All three functions were still **ACTIVE** on Supabase afterwards and still answering — including `create-gift-card-payment`, which was `verify_jwt = false`, unauthenticated, unrate-limited, and created PaymentIntents carrying a 50% application fee. Deleting the source removed the only thing that made them *visible*. The retirement is a separate API call per function (management API `DELETE /v1/projects/<ref>/functions/<slug>`), and it is not done until the endpoint answers 404 **against a live control** — a function you expect to survive must answer differently, or "404" only proves you typed the URL wrong. Same shape for anything else deployed out of band: Vercel functions, cron entries, webhook endpoints, storage buckets, scheduled tasks.
- **★ RE-REQUEST THE DEAD URL FROM THE INTERNET, because the build output is not the routing table.** The same removal produced a perfectly clean build — 10 routes instead of 11, no gift-card artifact, no sitemap entry — while `vercel.json` still carried a rewrite for `/gift-cards` and still listed it in the SPA catch-all. The live URL returned **HTTP 200 serving the home page's prerendered head**: a soft 404 on a URL that had been in the sitemap and was therefore indexed, so Google would have kept it. Nothing on disk was wrong; the host config was. After any route retirement, curl the removed path on the real domain and require a 404 or a deliberate redirect, and grep the host config (`vercel.json` rewrites/redirects/headers, middleware matchers, `next.config` redirects) for the dead path by name. A green build is evidence about the bundle, never about what the CDN serves.
- **Close with `security-reviewer` briefed specifically on the deletion**, not on the new code. The exposure created by a deletion is invisible to typecheck, tests and the build, because nothing is broken — something is merely unguarded.

## Compounding the studio (do this every job — it's where leverage comes from)
- **Run the `retrospective` agent LAST.** It finds the blind spots the other agents missed this job, distills them into durable rules, and writes them back into the agent definitions / STANDARDS / CRAFT / PLAYBOOK / memory — so the same mistake can't recur. This is the flywheel; skipping it is how the team stops improving.
- **Harvest reusable assets:** after each job, pull anything reusable (a component, template, boilerplate, prompt, offer, design token set, campaign structure) into a library so the next job is faster. Job #10 should take a fraction of job #1.
- **Capture learnings:** use `continuous-learning` + memory to turn what worked into a new skill/rule/note, so the system gets smarter over time — don't re-solve solved problems.
- **Turn work into proof:** every shipped result becomes a case study/testimonial (client-partner) that feeds the next sale (sales-closer, growth-marketer).
- **Dogfood:** keep the studio's own marketing engine running (playbook M) — your pipeline is an asset, not an afterthought.
- **Throughput:** on the Max plan the constraint is attention, not tokens — run independent jobs in parallel and push recurring work (lead-gen, content, monitoring) to scheduled/background routines built by **automation-engineer**.

## Definition of done
Built and **verified in a browser with zero console errors** · all relevant **gates passed** — the seven build gates (code-quality, test, design-auditor, security, QA, performance, art-director taste) plus the seam pass and the merge gate; name each one and its verdict, because "all gates ran" is unfalsifiable otherwise · **docs updated** · every site we build ships a **"Powered by Elevare Studio" footer credit linking to https://elevarestudio.co** (marketing name, no `LLC` — the filed entity is `ELEVARESTUDIO LLC`, one word, and that form is used only where a document must name the entity) (default on all builds; client white-label only if explicitly agreed) · on `dev` with **sign-off obtained before production** · outcomes reported honestly (placeholders and unverified items named).

**A substantial job is NOT done until the WHOLE flow has run — not a build+gates subset** (this recurs; see [[full-studio-flow-required]]). Before you call it shipped, confirm all four have happened or been *explicitly* skipped with a reason:
1. **Marketing wave** — `marketing-strategist` ran (launch kit / owned-channel + SEO plan), or an explicit "no marketing this round" from the human.
2. **Compliance** — **any site that collects PII or takes payments MUST get `compliance-counsel` (privacy policy + ToS, cookie/consent as needed) BEFORE launch.** This is a hard gate for data/payment sites, not optional; it was nearly missed on a live e-commerce build.
3. **Automated regression tests** — `test-engineer` wrote durable tests, and every bug a gate found got a repro test so it can't come back.
4. **LEARN loop** — `retrospective` + `eval-master` (+ `pattern-librarian`, `memory-curator`) closed the run. Skipping this is how the same class of bug reappears.
5. **Seam pass + taste gate, at the right TIME** — every parallel wave closed with the §4b seam pass (Breaks-declaration diff + claims ledger + real round-trip), and `art-director` reviewed the first user-visible surface as a **wave barrier**, not after the technical gates. Both were skipped on a run that was tsc-clean with 503 passing tests and still had five DO-NOT-SHIP blockers and a dead paid feature.

### Busy-day gate — REQUIRED for anything that takes orders, bookings, payments or runs a live event
Owner, 2026-10-10: "pen test with having a bunch of orders to fully see where the app will fail should be a step in
Elevare's process". Normal gates test one order at a time; a real Saturday is 60 orders in two hours on one venue's
Wi-Fi. Coffee Baby's busy-day test the night before her first pop-up found a BLOCKER (a bare "ready" text closed a
real customer's Sunday order), taps silently dropped while a Ready was sending, the kiosk resetting mid-payment and
a rate limit that starved ~12 phones on one Wi-Fi. Every gate before it had passed. Before shipping, run BOTH and
name each verdict:
1. **Busy-day stress** (`qa-verifier`): many orders at once (40-80), concurrent taps on two devices, double taps,
   slow/late payment webhooks, end-of-day close with orders mid-checkout, the UI at 0/10/30/60 orders (owner and
   customer screens, light and dark), polling load from 80 phones on ONE IP vs every rate limit, and notification
   volume vs provider caps. Database logic exercised inside rolled-back transactions, never persisted.
2. **Pen test** (`security-reviewer`): every new server action/route for auth, enumeration and rate limits; kiosk or
   shared-device escape paths; anything a stranger can trigger (SMS, webhooks, public boards); XSS via names/notes.
Re-run both after a redesign or any change to an order path, even a "visual only" one.

### Longevity gate — for anything meant to survive without its author (offline tools, portals, hand-off deliverables)
"User-proof for years" is a distinct review lens normal gates miss. Before calling such a job done, confirm:
- **Destructive actions are recoverable:** confirm + undo + a real recovery path (restore-from-backup **UI**, not just files sitting on disk that a non-author would never find).
- **Data is recoverable by a non-author** — a stranger can get their content back through the product, without the original builder.
- **Single points of failure are loudly documented** — an encryption pepper/key, a required env value, a one-way migration: if losing it bricks the app, say so at the top of the handoff doc.
- **The handoff/architecture doc SHIPS IN THE REPO** (MAINTAINER.md / NOTICE.md / README), not in session memory — session memory does not travel with the code. Owner: docs-writer; qa-verifier confirms the recovery UI actually works.

## Using the skills
Agents read `%USERPROFILE%\.claude\skills\<name>\SKILL.md` directly (authored on `D:\.claude\skills`; **`C:` is what loads**). [SKILLS-MAP.md](SKILLS-MAP.md) is the index — every skill grouped by domain and mapped to the agent that owns it, plus the industry-vertical skills to pull for client work in that sector.

**Every agent file now ends in a generated skill block, and the 68 of them cover all 207 installed skills between them** (2026-09-10). That changed what the map is FOR. It used to be the only place most skills were routed, which made "the whole library is in play" conditional on somebody reading the map and choosing to act — and that is the step that got skipped for a full day. Now each agent arrives already knowing what it owns, and the map is the index you consult when a job needs something **outside** the owning agent's block, or when you are deciding which agent to spawn at all. Both still matter; only the default changed.

**Reading the SKILL.md is the act — naming the skill is not.** A report that says "applied `calibrated-check`" without having opened the file is the same class of claim as a comment asserting a control in another file: it reads as done to every reviewer and nothing was checked. If a skill is named in the `skills:` receipt line, someone read it.
