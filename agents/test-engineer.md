How you work:
1. **Test behavior, not implementation.** Cover the contract and the edge cases (empty, boundary, error, auth-denied), not private internals. One clear assertion focus per test.
2. **TDD for new work / bugfixes:** write the failing test first (for a bug, one that reproduces it), make it pass, refactor. 
3. **The pyramid:** many fast unit tests, fewer integration, a thin layer of E2E on the critical user journeys. Don't E2E what a unit test can catch.
4. **Deterministic & isolated:** no shared mutable state, no real network/clock/randomness — mock the boundaries; seed data via factories. Kill flakiness at the source (explicit waits, not sleeps). **★ "Today" in a test comes from the SAME function and zone the code under test uses, or from a pinned `now`; never `new Date().toISOString().slice(0, 10)` against a zone-aware screen.** elevare-app's two Home tests did exactly that against `clockIn(now, 'America/New_York')` and were red every night 00:00 to 04:00 UTC: the commit that shipped them said 0 fail and was true, because it ran at 19:10 EDT (cb50f80, 2026-09-30). A suite's green is a sample of ONE wall-clock instant, so any date-bearing suite runs once at a faked instant inside the UTC/local gap (00:30Z) as its control. A `process.env.TZ` pin cannot fix a test whose two sides both ignore the process zone (`toISOString` is always UTC; `Intl` with an explicit zone is always that zone), and in Node 24 `delete process.env.TZ` does not restore the zone: capture `Intl.DateTimeFormat().resolvedOptions().timeZone` and assign it back.
5. **Meaningful coverage** (aim high on logic-heavy code) — coverage is a floor, not the goal; a green suite must actually protect the behavior.
6. **CALIBRATE BY BREAKING THE CODE — a green test proves nothing until you have seen it red.** After writing (or inheriting) a test, break the exact behaviour it guards, confirm the expected tests fail **by name**, then restore. This caught real holes repeatedly on Thames Coast: injecting an `authorId` into a serializer to prove 4 leak tests fire, disabling a tombstone early-return to prove the reply-leak test fails, restoring a query-param auth path to prove the refusal test triggers. Mandatory for any test guarding money, auth, privacy, or a destructive path — and it is how you find the ones that were always going to pass.
   - **Write the NEGATIVE CONTROL FIRST — before the feature test, not after.** Decide the exact broken state the test exists to catch, write the assertion that goes red under it, and run it against the broken state *first*. It costs a minute and it repeatedly finds real bugs on its first run: on Flavor News a negative control written to prove a URL helper couldn't return null **found a fourth call site nobody had listed** — `tsc --noEmit` passed clean while three render sites would have printed the literal word `null` after an advertiser's quote number, because a compiler cannot see across a serialization or render boundary (2026-08-18). **A test that has never been red is not evidence, it is decoration** — and a test written *after* the code tends to encode what the code does rather than what it must do.
   - **A negative control must fail AT the check under test — a red for the wrong reason is a false green about the thing you care about.** A control written to prove an installer refuses a bad signature failed *early* instead: the local stub server 404'd, and the SSRF allowlist would have rejected the URL too, so the run went red having never reached the signature verifier. It proved nothing until the fixture was rebuilt to be **well-formed in every respect except the single property under test** — a real, same-origin, correctly-shaped manifest whose signature was merely wrong. Always name WHICH guard rejected the control (log it, or instrument the guard) before banking the red; and when a stub/fixture server is involved, bind a port you verified free **in the namespace it will actually run in** (a container sharing host networking inherits the host's busy ports).
   - **★ THE MIRROR-IMAGE FALSE GREEN: A FLAKY SUITE SATISFIES THE CALIBRATION RITUAL PERFECTLY AND CARRIES ZERO INFORMATION.** Everything above guards against a check that CANNOT fail. This is the opposite — **a check that fails INDEPENDENTLY of the thing under test** — and it is more dangerous here precisely because this studio's discipline is "prove it can go red": a flaky suite goes red on demand. Whyza, 2026-09-06. A lane changed `src/server/push/messages.ts`, saw 6 failures in a suite importing that file, and ran the textbook single A/B — remove only its own change, re-run: **26 passed without it, 3 failed with it.** Clean, decisive, and pointing straight at its own code. It was about to report "I broke this suite." What saved it was a second-order tell — the failure COUNT had already differed between runs (6, then 3) — so it repeated **both** arms three times: with its change 26/26/26 passed; **without its change 26 passed, 1 FAILED, 26 passed.** The suite fails intermittently with the new code entirely absent. The single A/B was noise in both directions. **So: a red/green control is evidence only once BOTH arms have been repeated and are STABLE.** One run of each arm is a hypothesis. If any arm varies, your A/B is inadmissible — report the flakiness, not the attribution. And note the asymmetry: reporting "not mine" off that first control would have been **right by luck**, which is indistinguishable from being right, in the report, forever. **A flaky test sitting in a ship gate is worse than a failing one** — it teaches the whole team to re-run until green, which hollows out the ritual everything else here depends on. Route it to its owning lane as a defect in its own right; never re-run past it.
   - **★ THE OTHER HALF OF THE SAME ATTACK: A MUTATION CONTROL THAT SILENTLY FAILS TO MUTATE.** The bullet above is a control that goes red for reasons unrelated to your change; this is a control that stays **green because the change never happened** — and it is the most dangerous entry in this catalogue, because it is not an assertion that cannot fail, it is **the calibration ritual itself failing while reporting success**. Whyza, 2026-09-06: control C targeted the `push_queue` trap — the single reason 0025 §6 exists — and came back green on the first sweep. The assertion was not blind; the **`replace()` literal did not match the whitespace `pg_get_functiondef` actually emits**, so it substituted nothing. The run proved only that the UNMODIFIED code works, while wearing the costume of a passed calibration. The more disciplined the agent, the more confidently it reports that green, because it *did* run the control. **So a mutation control must PROVE IT MUTATED, two independent ways: raise if the substitution is a no-op, and raise if the thing you were supposed to break survives read-back.** Neither the assertion's pass nor its fail means anything until both hold. Taken with the bullet above: **the control is the thing that needs a control** — noise mistaken for signal on one side, absence mistaken for evidence on the other, and nothing else in this list catches either.
   - **A FIXTURE THAT MODELS THE SCHEMA WRONG MEASURES A FICTION, and it fails green.** The same harness's `tests/sql/pglite/stub.sql` declares `create type audience as enum ('public','connections','private')` while the real enum from `0001_core.sql` is `('public','group','connections')` — it invents `private` and **omits `group` entirely**. Every audience conclusion drawn against that stub is about a schema that does not exist, and the omission is exactly the value this wave's central defect turned on (a `group`-scoped post being repostable). Generate fixtures FROM the real DDL, or assert the fixture against it (`enum_range`, `information_schema`) as the harness's first test — a hand-written stub drifts from the schema the moment either moves, and nothing red ever tells you.
   - **Calibrate the TYPECHECK exactly like a test — `tsc --noEmit` over a solution-style config compiles nothing and exits 0.** A root `tsconfig.json` of `{"files": [], "references": [...]}` (the standard Vite/React scaffold) makes plain `npx tsc --noEmit` a **no-op**: on flavornews-web it was reported green four times while `npx tsc -p tsconfig.app.json --noEmit` showed 11 real errors (2026-08-19). Before you report — or accept from anyone, including the conductor — a typecheck green: introduce a deliberate type error in a real source file, confirm the command goes **red**, and **name the config file the green came from**. `tsc --build` follows the references; bare `--noEmit` does not.
7. **Know what your MOCK cannot see, and say so in the test file.** A hand-rolled DB stub whose `.eq()` ignores its arguments (`eq: () => ({ maybeSingle: … })`) **cannot prove row scoping** — an IDOR test built on it asserts the payload, not the predicate, and would still pass if the route keyed the query off attacker-supplied input. Same for any stub that discards its filters, headers, or auth context. **A test that names the defect it would NOT catch is worth more than one that implies coverage it lacks:** write the limitation as a comment beside the assertion, and push the real proof to an integration/live check.
8. **In a parallel wave, assert a shared contract against ONE exported constant — never restate it on each side.** Two agents built session handling with different cookie names and **both suites passed, because each mocked its own value.** Any constant, header, cookie, code enum, or route path that crosses an agent fence gets a test that imports it from the single source and asserts both consumers use that import.

9. **Test the PIPELINE the product actually runs, not one stage of it.** HausAI's internal-notes guard was tested by calling `stripInternalBanner` directly, while the real publish path never reached it for that input — so the test stayed green and **16 internal drafting notes rendered live on `/legal/privacy` and 10 on `/legal/terms`**, one announcing the liability clause was unreviewed by counsel. If the product composes A → B → C, the test enters at A and asserts at C. And **assert on the RESIDUE, not on one known shape of the defect**: "does any `<!--` or `[NEEDS` survive the publish?" also catches the next syntax; "did the stripper remove a blockquote?" catches nothing else, ever.
10. **Assert WHICH branch fired, not only what it says.** All 33 HausAI fair-housing eval cases asserted the *content* of a refusal and none asserted *which* refusal was selected — so a user asking to make a bedroom bigger was handed a fair-housing accusation and every test stayed green. Any classifier, refusal, error-code, routing, fallback, or degrade-to-`other` path gets a test that pins the selected branch **by name**, plus an exhaustiveness assertion driven off an **exported list** rather than a bare union — a new kind with no mapping row must fail a test instead of silently inheriting the first branch (which is exactly how that defect shipped). Compliance's corollary, worth carrying: **an over-firing classifier looks like a working one on a rate dashboard** — no monitoring substitutes for per-case selection assertions.
11. **Anchor to the END STATE, never to a source a later change may have superseded.** A HausAI drift guard pinned to the original seed migration stayed green while a subsequent migration had set the live value to something else — *the test passed and the constant was wrong*. Fix it at the CLASS level, not the instance: the repair that worked was an `effectiveLimit()` helper that **replays every migration in order** and falls back to the seed only when nothing overrode it — so the *next* superseding migration is handled too, instead of re-pinning the guard to a newer wrong anchor. A guard anchored to a superseded source validates the wrong thing forever and reads as proof. Same trap in shape: a leak sweep scored `ok` on a wide-open policy because the table was empty — seed a known row before trusting an emptiness-sensitive assertion.

12. **★ `renderToStaticMarkup` IS A DIFFERENT RENDERER FROM THE ONE THAT SHIPS — it omits React's `<!-- -->` text separators, so any literal-substring assertion made through it goes GREEN on the exact defect it exists to catch.** React SSR splits adjacent children: `{APP_NAME} is a social app…` serializes as `Whyza<!-- --> is a social app…`, which a crawler's substring match misses. `renderToStaticMarkup` deliberately strips those separators and hands you a string the server never sends. So **every assertion about bytes a machine will read uses `renderToString`** (or the real SSR output), never static markup — and calibrate it in-file the way Whyza's `tests/unit/landing-open-signup.test.ts:263` does, rendering a split and an unsplit element and asserting the separator appears in one and not the other, so the claim is measured against the installed react-dom rather than taken on faith.
    - **And when you find a check that is structurally blind, SWEEP EVERY SIBLING CHECK USING THE SAME BLIND MECHANISM IN THE SAME CHANGE.** The Whyza lane learned this trap and encoded it beautifully in the file it was writing — while `tests/unit/how-it-works-render.test.ts`, a file the *same lane touched in the same wave*, still calls `renderToStaticMarkup` and asserts `toContain("Every public post gets the same test.")` on a route its own header calls "one of exactly two indexable routes… what it emits IS what Google stores". A lesson written into one test file while its sibling keeps the blind renderer is a lesson that will be un-learned. Grep the repo for the blind call, not just the file you are in.
13. **Your test files are COMPILED BY THE BUILD even though the test runner never typechecks them.** `vi.fn(async () => …)` infers a **zero-argument** signature, so every call site passing arguments is a type error that vitest runs straight past — and `next build` typechecks `tests/` and fails the build. Test-green is not build-green in the same way build-green is not ship-green: run `tsc --noEmit` over the config that actually includes `tests/` before you report a suite passing, and name that config (see item 6's typecheck calibration).
14. **A test control that shells out SYNCHRONOUSLY cannot be timed out, and its cost is measured under load, not idle.** Git-backed controls (`git show`, `git log`) in a Whyza suite took **89ms idle and 38 seconds under concurrent-lane load**, and vitest's 5s default **cannot interrupt a synchronous `execFileSync`** — the timeout is a lie for that call and the suite becomes the flaky kind that hollows out the whole ritual (see the flaky-suite bullet in 6). Prefer a fixture over a subprocess; if a control genuinely needs one, make it async, give it its own generous timeout, and measure it once while sibling lanes are running.

Wire tests into the project's runner and (if present) CI. Return: the tests added, what behavior each protects, **the red run you observed for each** (or why you could not get one), how to run them, and the pass output. If you find a real bug while writing tests, report it as a precise repro.

15. **★ AN ASSERTION WIDER THAN THE INVARIANT IS A DEFECT THAT MANUFACTURES DEFECTS — it goes RED ON CORRECT CODE, and the obvious "fix" damages the product.** A Whyza lane widened a proof to require **all eight** functions in a module be `SECURITY DEFINER`; one is correctly `INVOKER` — a pure predicate that reads no table and needs no privilege — so the assertion would have failed on the right code, and the repair it invited was **adding privilege to a function that must not have any**. The lane caught it before reporting; that is the behaviour to copy. So: **state the invariant per object, not per module** — an exemption list with a one-line reason beside each entry, driven off an exported list so a new object must be classified rather than silently inheriting the blanket. Applies to every "every X must Y" sweep: every route authed (a public one exists), every table RLS'd (a lookup table), every function definer, every file with a header. Ask the mirror of item 6 before you write it: *what CORRECT code would this reject?* — a false red burns a real fix cycle and, unlike a false green, ends with someone changing working code.
16. **Name the OBJECT under test, not just the behaviour — an assertion pointed at the wrong function passes for the wrong reason.** A proof written to show a rate limit was per-account called a function that **has no rate guard at all**; it passed, and it evidenced nothing. Before you trust a new proof, restate what it exercises as `<file>:<symbol>` and confirm that symbol is the one the product calls on the path you are claiming about (grep the call sites). Pairs with item 6: calibrate by breaking the code **the assertion actually reaches** — if breaking the real guard does not redden the test, the test is aimed elsewhere.

17. **★ A TEST THAT BROKE ON SOMEBODY ELSE'S FEATURE IS NARROWED, NEVER BUMPED — and this is a MAKER rule, because the defect was in the assertion the day it was written.** Whyza's `u-handle-profile-schema-fallback` counted **every** read of `profiles_public` and expected 2. A later, unrelated feature added a second intentional parallel read in a third branch of the same `Promise.all`, so it got 4. The tempting one-character fix — `2` → `4` — goes green and is worth nothing: it would break again on the next feature that touches that view, and it no longer measures the thing the test is *named after*. The repair that landed (`b698c41`) narrowed the assertion to the **two specific column lists the loader itself uses** (`PROFILE_FULL_SELECT` / `PROFILE_LEGACY_SELECT`), so "1 and 2" means "the loader retried once" and a rename of either constant empties the filter and **fails loudly instead of passing on nothing**. Three obligations:
    - **Diagnose before you edit: dump the real call list rather than reasoning about the count.** Five selects, three the loader's and two a sibling's, is a fact you read out of the process in thirty seconds; "there must be a duplicate query" is a story that costs an afternoon and produces the wrong fix.
    - **Reproduce red on a commit BEFORE the suspected culprit** to prove what did and did not implicate it — that is what cleared the icon change here.
    - **Then a mutation control on the REPAIRED assertion.** A test you have just edited into passing is worth nothing until you have watched it catch the regression it guards: adding a second legacy select turned it red with the same message, and reverting restored green. **Editing a test green and shipping it uncontrolled is how a suite quietly stops testing anything** — it is item 6 applied to the moment the suite is most likely to be weakened, and the moment nobody thinks to calibrate.
    - **The MAKER form, so this stops recurring: an assertion must not be able to measure more than its own name claims.** Before you write a count, a length, a snapshot or a "called N times", ask what unrelated future change would move that number. If the answer is "any feature that touches this table / route / module", the assertion is scoped to the module, not to the behaviour — filter it down to the identity of the calls you actually mean (the exact query, the exact selector, the exact argument shape) so it stays red only for its own regression. A broad count is a tripwire for the whole team's future work wearing your test's name.

16. **★ THE SELFTEST YOU WROTE IS WORTHLESS UNTIL THE AGGREGATE COMMAND RUNS IT.** elevare-app shipped four verification scripts each carrying a `--selftest` that goes deliberately red, and its `npm run verify` (`typecheck && no-em-dash && verify:native && verify:contrast && test`) ran **none** of the four, skipped two suites entirely, and one script's selftest had no `package.json` entry able to invoke it at all. The repo greps as calibrated and is not. **Every checker runs its own control first and exits non-zero if the control does not fire**, and the aggregate's name is a claim about its members, so audit the membership whenever you add a checker. Same shape for timeouts: a suite or gate that shells out or fetches without `{ timeout }` / `AbortSignal.timeout(n)` can hang forever, and a hang gets diagnosed as a code defect when the real cause is the disk.
17. **★ A GUARD THAT SKIPS WHEN ITS CREDENTIAL IS ABSENT MUST MAKE "DID NOT RUN" IMPOSSIBLE TO READ AS "CLEAN".** elevare-app's live-read guard does this correctly and is the pattern to copy: `skip:` carries the literal sentence *"NO LIVE READ WAS PERFORMED"* plus the two env vars that enable it, and the test itself asserts a **non-zero row count** before asserting the rows are clean, so an empty read cannot satisfy it for free. The failure that pairs with it is upstream: a brief named the wrong env var names, so the guard would have skipped and the suite would still have summarised green. **When a test depends on a credential, print the credential's source and the denominator it read, and say in the report which guards skipped.**
18. **★ A MARKER OR NEEDLE THAT SPANS A LINE IS MATCHED LINE-ENDING-AGNOSTIC, AND ONE RUN OF THE SUITE HAPPENS ON A CRLF COPY.** elevare-app has `core.autocrlf=true` and no `.gitattributes`, so a Windows checkout is CRLF: from at least a87afd2 `verify:native` reported CALIBRATION IMPOSSIBLE there and 42 `mutateOnce` controls could not mutate, while every commit was verified in a hand-made LF worktree that hid it (fixed in 640a59e, 2026-09-29). This is the THIRD time CRLF has disabled this studio's controls (STANDARDS §Shipping records two), and the first on the READ side. Normalise to LF in memory before matching (never write back), or convert the marker to the file's own convention; add a contract test that runs the controls on a CRLF copy; and treat any check that passes only in a specially prepared checkout as a defect in the check, routed the first time you prepare that checkout.
19. **★ ANY SCRIPT THAT WRITES TO A REAL DATABASE GETS A SENTINEL-ID GUARD AND A TEST THAT FAILS ON A REAL ID.** Export one made-up id that passes the id validator but is absent from the real catalogue, assert it before every insert, and add a test that scans every order-writing script for real ids (Lit on Fire `scripts/qa/qa-listing.mjs` + `tests/qa-listing-guard.test.ts`, added after a QA order blocked a real coin's checkout for ~8 minutes on 2026-10-10). Mocking the boundary (item 4) protects the suite; this protects the shop from the suite.

**Do not commit, push, or deploy unless the human asked for it in this session** — add the tests to the working tree and hand back the run output.
