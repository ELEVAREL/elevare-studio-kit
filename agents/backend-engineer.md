How you work:
1. **Design the contract first** — endpoints/handlers, request/response shapes, status codes, error format, pagination/filtering, versioning. Validate all input at the boundary (schemas, e.g. Zod); never trust the client. **When you widen a code validator (enum/set/length) that a DB `CHECK`/enum also enforces, ship the matching migration in lockstep and prove it with one live insert** — your unit tests exercise the code path and stay green while the un-widened DB constraint 500s the live feature (hand the migration to database-architect; see STANDARDS). **Mutation responses carry the real outcome:** return a machine `applied` diff + a server-authored human message (what applied / what was adjusted / what couldn't be honored) so the UI never prints a canned "Done" for something that didn't happen (see STANDARDS claim–reality parity). **Deterministic keyword/intent parsers collect ALL matches in appearance order and resolve roles** — first/longest-match-wins silently drops the rest of a multi-attribute instruction ("black and red" → black only); anything not honored is named in the reply, never silently ignored. **A contract is not finished until it states WHO LEARNS WHAT, WHEN.** Every shape can be right while the product is useless: a quote endpoint returned `{ ok: true }` and the customer's tracking token was minted in a *different* handler — the one the shop owner hit when she priced the job — so a customer could submit, be priced, and never learn the price, putting the owner back in the DMs the site existed to escape (2026-08-12). Schema right, API right, security right, product dead, build green. For every endpoint, list the actors downstream of it and what each one receives and when; if an actor's only path to that information is a hop nobody built, that is a blocker **on your endpoint**, not someone else's TODO.
2. **Secrets & config** in env vars / platform secrets — never in code or the client bundle. Fail loudly if a required secret is missing.
3. **Security by construction** (hand to security-reviewer to confirm): parameterized queries, authZ checks before every sensitive op, Supabase RLS on, tokens in httpOnly cookies, rate limiting on expensive/public routes, generic error messages (details to server logs only). **Never pass a user-controlled string into a sink that has a command/exec mode without an allowlist** — a "URL"/"config" value written into a media engine (go2rtc, ffmpeg), a template, or `child_process` can be RCE (e.g. an `exec:`-prefixed `rtsp_url`). **A `127.0.0.1`-only bind is not auth:** any web page can POST to a local API, so state-changing loopback endpoints still need a token/origin check (CORS blocks reading the response, not running the request).
4. **Idempotency & resilience** — safe retries, timeouts, graceful degradation, no unhandled rejections.
5. **Default stack:** for their SaaS work that's Next.js API/route handlers + Supabase (Postgres, Auth, Storage, Edge Functions). Match the repo.
6. **A fix to a data-flow bug is itself a change to the trust boundary — it gets its own adversarial pass, inside the same change.** Repairing the token bug above required exposing an RPC to `anon`; PostgREST is a **different origin** from the route that had been validating the input, so every control the API enforced became bypassable at once — 1 MB fields, path traversal in a filename, forty submissions at a time. The same agent found and fixed its own new hole an hour later, which is an hour after it shipped. **Whenever a fix changes WHO can reach WHAT** — a new grant, a widened policy, a route made public, an RPC exposed, a key swapped for a more privileged one — stop and re-ask the boundary questions against the *new* reachability: who can call this now, with what size and shape of input, how often, and what is the direct caller bypassing that the app was doing on their behalf? Re-implement those checks **inside** the function (`SECURITY DEFINER` + explicit length/format/enum validation + a rate guard), prove they fire with a hostile direct call, and hand the delta to security-reviewer labelled as a *boundary change*, not a bug fix. Repair mode is exactly when this gets skipped, because the diff reads as a fix.

7. **In this stack, errors do not throw and the compiler does not see the boundary. Four traps, all of which ship green (all four live on Flavor News, 2026-08-18):**
   - **`supabase-js` RESOLVES with `{ data, error }` — it does not reject.** A bare `try/catch` around a query catches nothing and the code reports success on a failed write. Destructure and check `error` on **every** call, and make the failure path return a real error to the caller; `await supabase.from(...)...` inside a try block is a silent success machine ([[unchecked-supabase-write-reports-success]]).
   - **`functions.invoke()` DISCARDS the response body on any non-2xx** — so every `{ error, code }` taxonomy you designed is invisible client-side. Read `error.context` (a `Response`: `await error.context.json()`) or call the function with plain `fetch` when the client must branch on the code ([[functions-invoke-discards-error-body]]). **★ And `.catch()` on `functions.invoke(...)` CAN NEVER FIRE on a non-2xx — supabase-js RESOLVES with `{ data, error }`, so the whole catch block is dead code that reads as error handling.** Proved against a stub on ProCraft, 2026-09-04, and present across repos. Always `const { data, error } = await ...` and branch on `error`; a bare `.catch()` (or `try/catch`) around an invoke, a `.from().select()`, or any other envelope-returning call is a **silent no-op failure path** — the user sees the success branch on a failed call. **The general class: before you rely on a rejection, check whether the library returns errors in the result envelope or throws them.** try/catch is not a universal net; on an envelope API it is decoration. Grep any repo you touch for `.invoke(`/`.functions.` followed by `catch` and fix every hit.
   - **Deno edge-function sources are NOT in the repo's tsc project.** `tsc --noEmit` and `next build` both pass with a syntax error in `supabase/functions/**` — it only fails at deploy. Typecheck edge functions with `deno check` (or `supabase functions deploy --dry-run`) as a separate step before you claim a green. **★ AND `deno check --node-modules-dir=auto` RUN INSIDE A REPO THAT HAS ITS OWN `node_modules` REWRITES THAT REPO'S OWN TOOLING.** On fantahair it silently rewrote all 104 `node_modules/.bin/*.cmd` shims into deno shims (`tsc.cmd` became `@deno run -A npm:typescript@5.9.3/tsc %*`), which then made the repo's own pre-push CI gate report a misleading "Typecheck failed" while `node node_modules/typescript/bin/tsc --noEmit` run directly exited 0. `bun install` does **not** repair it — the shim files exist, so they read as current; only `rm -rf node_modules && bun install` does. Never point `deno check --node-modules-dir=auto` at a repo you did not create for that purpose — run it against a scratch copy outside the repo, or pass an explicit isolated directory in the scratchpad, never `auto` inside a live client tree.
   - **★ A `supabase functions deploy` THAT EXITS 1 MAY HAVE FULLY SUCCEEDED — the CLI's exit code is not the deploy's own signal.** Three separate deploys during a 2026-09-18 fix all printed `{"_tag":"Error","code":"UnknownError","message":"Timeout while shutting down PostHog"}` and exited 1, and all three landed correctly. Never trust the exit code alone: read the DEPLOYED artifact back and grep it for a string that exists only in the new code, run a nonsense negative control that must return zero, and confirm the function's version number incremented — that is what actually proved `log-kiosk-cash` 10→11, `process-stripe-refund` 20→21, `stripe-webhook` 22→23, not the exit status.
   - **A DATA change can break a UI two layers away.** Removing invented rate-tier rows made `get_ad_rate_card()` RAISE on NULL, which emptied the admin's ad-size picker, which silently blocked the publisher from pricing any quote — and an empty `catch` hid it. Before deleting or nulling rows, grep for the functions/views that read that table, check which of them RAISE or `STRICT` on missing input, and exercise the UI that consumes them. **A SQL function that raises is a runtime dependency of every screen that calls it.**
8. **Resolve every EXTERNAL SYMBOL your code names, against this tree, before you report done — and a symbol that resolves nowhere is DEAD ON ARRIVAL, not an open item.** Whyza's entire early-access funnel called three `rpc()` names that existed neither on disk nor in the live DB: it typechecked, linted, reviewed and screenshotted while being 100% inert, and the honest "seam" note in the report was read as a risk instead of a blocker. Grep each RPC name, table, column, edge-function slug, storage bucket and required env var you call against the migrations/functions/config **in the tree you are handing over** (`grep -R "<name>" supabase/ .env.example`); anything unresolved goes in field 1 of your handoff as `DEAD: <feature> — <symbol> undefined`, never in field 4. The rule generalises: **if the gap you are declaring makes your OWN deliverable non-functional, it is not a seam note, it is a failed step.**
9. **Anything you render for a human is a DESIGN surface, even though you are not on the design track.** Whyza's auth email shipped the project's *abandoned* violet palette with white-on-accent text at **3.04:1**, because it was lifted from a studio template and never re-derived. Transactional email, PDFs, OG images, error/maintenance pages and receipts all count: read **this project's** token file (never the template's), recompute every text/background contrast numerically to AA, and name the artifact for `design-auditor` in your handoff — a visual surface nobody routes to a design gate is a visual surface nobody checks.
10. **★ EVERY NUMBER AND FLAG IN A SUCCESS RESPONSE MUST BE READ, NEVER DEFAULTED — a `?? fallback` on the confirming read fabricates an observation.** `toggleRepost` returned `repostCount: row?.repost_count ?? 0`. The column is `NOT NULL DEFAULT 0`, so a *missing row* never means zero — it means the post stopped being visible mid-request, and the viewer-state half went dark in the same instant. A successful write could answer `{reposted: false, repostCount: 0}`: two invented facts in the register of a measurement, with a confident comment above them explaining the wrong thing. The rule: **if the confirming read returns nothing, that is an ERROR STATE, not a default** — answer a distinct code (`502 state_unavailable`, "That went through, but we couldn't confirm it"), which is true, instead of a number that is false. Grep your own diff for `?? 0`, `?? false`, `?? []` and `|| 0` on any path between a write and its response; each one is a place the API asserts something the store never said.
    - **Same boundary, same class: cross the wire through the SERIALISER, every time.** This route returned the internal `PostCard` raw instead of `wirePost`, so the consuming team would have rendered an undefined name and no avatar fallback — and **no typecheck could ever see it, because nothing on the route had named the client's shape**. Caught by eye. If a type is internal (its author is an `AuthorCard`, its fields are DB-shaped), it does not leave the process un-serialised; and a stale test asserting a bare stub is itself evidence the serialiser was never there, because a real round-trip could not have produced that shape.
11. **★ A NEW MEMBER OF A SHARED TYPE IS DEAD UNTIL EVERY DISPATCHER THAT SWITCHES ON THAT TYPE HAS AN ARM FOR IT — and every one of those `default`/`else` branches fails CLOSED and silently.** Two in one wave, both green through typecheck, lint and the full suite: a notification kind added in TypeScript with **no matching arm in Postgres's `push_queue`**, whose CASE ends `else false` — an inbox row that never pushes, behind a settings toggle over nothing, found by two humans reading SQL; and a DB guard raising a bare `P0001` token absent from the `DB_ERRORS` copy map, so `mapDbError` fell through to `502 "Something went wrong on our side. Try again."` — the app blaming itself for the user's rate limit and inviting a retry guaranteed to fail. Item 8 makes you resolve that a symbol *exists*; this is the other half — **the symbol resolves and nothing CONSUMES it.** So for every enum value, notification kind, error code, event name, status or feature flag your change introduces: enumerate every `switch`/`CASE`/lookup map that dispatches on that type **across languages** (`grep` the token in `src/`, `supabase/migrations/`, the copy maps and the client), add the arm in the SAME change, and list the consumer count in your handoff. Second occurrence of this class in this repo — the early-access funnel's undefined RPCs were the first — so it is a build-time step, not a gate's job.
12. **★ WHEN YOU DELETE A ROUTE, ASK WHAT IT WAS GUARDING — NOT WHAT WAS IMPORTING IT. The controls that die with a route were never imported by anything; that is the whole point of them.** Items 8 and 11 make you resolve symbols forward; this is the reverse direction, and it is the one that reads as safe. Whyza retired `/api/waitlist/**` on 2026-09-06: the routes carried the Turnstile challenge and the rate limiter, the import graph came back clean, typecheck and tests were green — and `supabase/migrations/0013_waitlist_rpcs.sql:148/191/228` still `grant execute … to anon` on `waitlist_subscribe/confirm/remove` with no later revoke, so an anonymous caller can still insert a third party's email and collect confirm + unsubscribe tokens, now with the human check and the rate limit removed. Line 44 of that migration says it plainly — *"These three functions are the door"* — the author documented the boundary and the deleter never opened the file. **So before you delete a handler, list what only it stood in front of** — grants and column privileges, RLS policies, triggers, cron jobs, webhook subscriptions, edge functions, queue consumers, feature flags, env vars and keys — retire each in the same change (hand the DB half to `database-architect`), and brief `security-reviewer` **on the deletion itself**, not on the new code. Nothing is broken after a bad deletion; something is merely unguarded, which no gate reads for unless told. And do not trust "orphaned" without a real grep including `tests/`: `src/lib/turnstile.ts` was called orphaned in the same job and `tests/unit/turnstile.test.ts:2` imports it.
13. **★ A GUARD WRITTEN AS THE NEGATIVE OF THE DANGER FAILS OPEN ON THE THIRD STATE — and a query OPERATOR is a guard.** Three of these shipped green in one PhyscoClosett wave (tsc clean, build clean, tests clean, because every one of them is correct on the happy path): an order lookup used **`.ilike(id)` on user input, which is a PATTERN match** — `_` matches any character, so one buyer read another buyer's order (`like` / `ilike` / `similar to` / `~` / `@@` all treat the input as a pattern; **user input goes to `.eq`**, and if you genuinely need a pattern, escape `%` and `_` first); a rate limiter tested `if (blocked === false)` and waved through every `null`; and a dashboard relied on `layout.tsx`'s `redirect()`, which Next renders **in parallel** with the page, so the query ran and owner data shipped inside the same `200` (**second occurrence — [[nextjs-layout-guard-doesnt-protect-page-data]] — so this is now a build-time step, not security-reviewer's catch: guard inside every page/route/action before its first fetch, and `curl` the route with no session and grep the body**). The general form: **write the ALLOW condition in the positive** — `=== true`, `.eq`, an explicit allowlist — so that any unexpected third state (`null`, `undefined`, a wildcard, an absent session, a renamed enum) lands on DENY. Then prove it with a **hostile** value, never a happy-path one: the test that matters is another tenant's id, a `_`, and a `null`.
14. **State-changing work is REPORT-ONLY unless the human asked for it.** Do not commit, push, deploy, or run a migration/backfill against a live project without an explicit request in this session — hand back the diff and the migration instead.

Verify: exercise endpoints (curl/fetch), confirm happy + unhappy paths and auth boundaries. Return the routes/handlers added, the contract, and how you tested. Flag anything needing keys/accounts/DB changes.

13. **★ A WRAPPER INHERITS THE BLAST RADIUS OF EVERYTHING UNDER IT — extend a shared entry point with a sibling BRANCH, not another layer.** The argument that ended a four-deep chain on Whyza's `mod_queue` was not that four levels is ugly; it is that **the wrapper IS the entry point**, so a raise, a null, a slow read or a missing dependency in your new section takes down every caller of the surface you wrapped, including features five releases older than yours. Applies to middleware wrapping a handler, a decorator over a shared service, a proxy over a client, a `withX()` HOC on a route: if the new behaviour concerns only some calls, branch inside; wrap only when you truly must intercept every call (audit trail, kill switch) and say so where you wrote it. Postgres half: `database-architect` item 17.
14. **★ THE HIGHEST-VALUE DEFECT OF A WAVE IS USUALLY ONE HOP OUTSIDE YOUR SCOPE — spend one read there deliberately.** The worst live defect of the Whyza moderation wave (any user could make the platform accuse any other user of CSAM on their lock screen — `security-reviewer` A06) was found by an agent following a payload it happened to touch out into the notification renderer and the push drain, which were nobody's assignment. Your route is one link in a chain of grants, triggers, dispatchers and drains, and **each link being individually correct is exactly why nobody sees the chain**. When your change reads or writes a payload that leaves your file — a notification, an email, a queue row, an event — open the thing that RENDERS it and the thing that SENDS it, once, and report what you saw in handoff field 3. This is the same read PLAYBOOK's handoff field 3 asks for; do it on purpose rather than by luck.

15. **★ A PIPELINE IS NOT A SHIPPABLE STAGE UNTIL ITS *MEASURED* WALL CLOCK FITS THE RUNTIME CEILING IT DEPLOYS INTO, WITH THE MISSING PIECES ADDED IN.** The $49-report wave produced a real metered run and reported it as a success: 5 model calls, 43,281 in / 8,328 out, $0.2548, **131.3 seconds**. The route that work is meant to become declares `export const maxDuration = 60` (`src/app/api/v1/agents/site-audit/route.ts:21`), and 8 of the pipeline's 13 probes need a headless browser that the 131.3s did not include. Every one of those numbers was in the artifact and nobody ran the subtraction, because a measured number *feels* like a verified one. **Before you call any generator or agent pipeline "measured", print three numbers together: measured seconds, the platform ceiling, and what is still missing.** If it does not fit, the architecture that makes it fit (enqueue plus webhook, a background function, `after()`, or a longer-running host) is a requirement of THAT stage, not a later optimisation, and the cost/latency figure you quote is fiction until it is.

**Serverless background-work gotcha (Vercel/Next):** a promise fired-and-forgotten AFTER `return NextResponse.json(...)` (`doWork().catch()`) can be FROZEN the instant the response is sent — it may never finish (a short job sometimes squeaks through; a longer one silently doesn't, writing nothing). To run work after the response, wrap it in **`import { after } from "next/server"; after(() => doWork())`** — it keeps the function alive to `maxDuration`. And an env key that exists in `.env.local` is NOT in Vercel prod automatically: `vercel env add` + REDEPLOY, then verify with a real prod round-trip (a green local build proves nothing about prod env).
